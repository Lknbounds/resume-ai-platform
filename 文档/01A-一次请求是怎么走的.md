# 01A · 一次请求是怎么走的（小白必读）

> 这篇不讲设计，只讲**一件具体的事**：你在前端点了个按钮，数据是怎么变成数据库里一行的，结果又是怎么回到屏幕上的。
>
> 全部内容都能用 `DemoController` 那三个接口验证。建议一边读一边照做。

---

## 一、先建立最基本的概念：HTTP 就是"一问一答"

浏览器和后端之间，**只会做两件事**：

1. 浏览器发一个**请求**（穿一串文本过去）
2. 后端回一个**响应**（也穿一串文本回来）

没有"函数调用"，没有"对象传递"。所谓"前端调用后端接口"，本质就是**发一段特定格式的文本**。

### 请求长什么样（原始文本）

```http
GET /api/demo/ok HTTP/1.1
Host: localhost:8080
Accept: application/json
X-Trace-Id: my-test-123
```

拆开看：

| 部分 | 内容 | 说明 |
|---|---|---|
| 方法 | `GET` | 想干什么。GET=读、POST=创建、PUT=改、DELETE=删 |
| 路径 | `/api/demo/ok` | 找哪个资源 |
| 协议版本 | `HTTP/1.1` | 固定写法 |
| 请求头 | `Host:` `Accept:` ... | 一堆 `键: 值`，给后端的附加信息 |
| **空行** | （这里有个空行） | 分隔符，下面才是请求体 |
| 请求体 | （GET 没有） | POST/PUT 才有，装真正要传的数据 |

### 响应长什么样

```http
HTTP/1.1 200
Content-Type: application/json
X-Trace-Id: d70beb5bd41d47c1

{"code":0,"message":"ok","data":"hello","traceId":"d70beb5bd41d47c1","timestamp":1795006553458}
```

结构一模一样：状态行 + 响应头 + 空行 + 响应体。

> **关键认识**：所谓"前后端分离"，就是两边约定好——请求用什么路径、什么格式；响应是什么结构。这个约定我们写在了 `附A-错误码与接口总表.md` 里。

## 二、完整旅程：以 `GET /api/demo/ok` 为例（8 步）

### 第 1 步：前端发起请求

**你在前端代码里只写这一行**（步骤 4 会写真实的 `http.js`）：

```js
const res = await fetch('/api/demo/ok')
const body = await res.json()
console.log(body.data)     // "hello"
```

如果用 Axios（我们实际用的），还要更短：

```js
const data = await http.get('/api/demo/ok')
console.log(data)          // "hello" —— 注意拦截器已经把外层剥掉了
```

**这一刻发生了什么：**

浏览器读取你写的路径 `/api/demo/ok`，结合当前页面的域名端口（`localhost:5173`，前端开发服务器），拼出完整 URL。然后打开一个 TCP 连接，把上面那段文本发出去。

> ⚠️ 这里有个新手常困惑的点：前端在 `5173`，后端在 `8080`，为什么能连通？
> 因为 `vite.config.js` 里配了代理：
> ```js
> proxy: { '/api': { target: 'http://localhost:8080' } }
> ```
> 意思是"凡是以 `/api` 开头的请求，帮我转发到 8080"。Vite 开发服务器收到请求后自己再转发一次。
> **在浏览器看来，它一直在跟 5173 说话**，所以不存在跨域问题。

---

### 第 2 步：Tomcat 接到请求

8080 端口上跑着一个 **Tomcat**（Spring Boot 内嵌的）。

- Tomcat 是**Servlet 容器**：它的工作是"监听端口、接收 HTTP 请求、把请求交给 Java 代码处理"
- 它把浏览器发来的那串**纯文本**，解析成一个 **`HttpServletRequest` 对象**
  - 请求头 → `req.getHeader("X-Trace-Id")`
  - 路径 → `req.getRequestURI()`
  - 请求体 → `req.getInputStream()`

从这一刻起，后面所有代码操作的都是**Java 对象**，不用再管原始文本。

---

### 第 3 步：穿过过滤器链（Filter Chain）

Tomcat 不直接调 Controller，中间有一串 Filter，像安检通道：

```
HttpServletRequest
   ↓
① TraceIdFilter                ← 贴上 traceId（我们的代码）
   ↓
② CorsFilter                   ← 处理跨域
   ↓
③ JwtAuthenticationFilter      ← 验 token（步骤 3 加）
   ↓
④ ... Security 的其他 Filter
   ↓
DispatcherServlet
```

`TraceIdFilter` 干的事，用代码看最清楚：

```java
String traceId = req.getHeader("X-Trace-Id");   // 前端传了就沿用
if (traceId == null) traceId = randomId();      // 没传就生成
MDC.put("traceId", traceId);                    // 塞进当前线程
res.setHeader("X-Trace-Id", traceId);           // 回写响应头
try {
    chain.doFilter(req, res);                   // 放行：继续往下走
} finally {
    MDC.remove("traceId");                      // 请求结束后清理
}
```

> **`chain.doFilter` 是个分界线**：
> - 它**之前**的代码 = 请求进来时执行
> - 它**之后**的代码 = 响应回去时执行
> 所以 `finally` 里的清理发生在 Controller 跑完之后。

⚠️ 如果 `TraceIdFilter` 在注册时没加 `@Order(HIGHEST_PRECEDENCE)`，它会排到 Security 的几个 Filter 后面去 —— 那些 Filter 打的日志就没有 traceId，链路开头断了。

---

### 第 4 步：DispatcherServlet 找"该调哪个方法"

`DispatcherServlet` 是 Spring MVC 的核心调度器。它做的第一件重要的事叫 **HandlerMapping（路由匹配）**。

Spring 启动时，会扫描所有标注了 `@RestController` / `@Controller` 的类，把**每个方法**的路径登记成一张路由表：

| 方法（HTTP） | 完整路径 | 对应哪个 Java 方法 |
|---|---|---|
| GET | `/api/demo/ok` | `DemoController.ok()` |
| GET | `/api/demo/biz-error` | `DemoController.bizError()` |
| GET | `/api/demo/boom` | `DemoController.boom()` |

完整路径是**拼出来的**：

```
类上的 @RequestMapping("/api/demo")   +   方法上的 @GetMapping("/ok")
                    ↓                                    ↓
                     └──────────  /api/demo/ok  ─────────┘
```

DispatcherServlet 拿着 `GET /api/demo/ok` 一查表，就找到了 `ok()`。

> **匹配不上会怎样**：抛 `NoResourceFoundException` → 被 `GlobalExceptionHandler.handleNoResource` 接住 → 返回 `{"code":10003,...}`。
> 这就是验证第 ⑥ 条在做的事。

---

### 第 5 步：参数绑定（GET 没有参数，先跳过）

如果方法需要参数，Spring 会从请求里"抠"出来塞给你。四种情况：

| 写法 | 从请求哪里取 | 什么时候用 |
|---|---|---|
| `@PathVariable Long id` | 路径里的 `{id}` 占位符 | `GET /resumes/31` → id=31 |
| `@RequestParam(required=false) String sort` | URL 问号后面的 `?sort=hot` | 筛选、分页 |
| `@RequestBody XxxRequest req` | 请求体里的 JSON，反序列化成对象 | POST/PUT 提交数据 |
| `@RequestHeader("Authorization") String auth` | 请求头 | 取 token |

**这一整套叫"参数解析器"（ArgumentResolver）**，是 Spring 自动做的。

> 步骤 3 我们会自己写一个 `@CurrentUserId`，也属于这个机制 —— 详见步骤 3。

---

### 第 6 步：执行 Controller 方法

```java
@GetMapping("/ok")
public ApiResponse<String> ok() {
    return ApiResponse.ok("hello");
}
```

执行完，方法返回一个 **`ApiResponse` 对象**（在内存里，JVM 的堆上）。

**注意：到这一刻为止，还没有任何 JSON 出现。** 这个对象长这样：

```
ApiResponse 实例
├── code      = 0
├── message   = "ok"
├── data      = "hello"
├── traceId   = "d70beb5bd41d47c1"
└── timestamp = 1795006553458
```

---

### 第 7 步：对象 → JSON（HttpMessageConverter）

DispatcherServlet 拿到返回值后，发现：

1. 方法所在类上有 `@RestController`（= 有 `@ResponseBody` 语义）
2. 返回值是个普通对象，不是 `ResponseEntity`，也不是视图名

于是它调用 **`HttpMessageConverter`**（默认实现是 `MappingJackson2HttpMessageConverter`），用 Jackson 库把对象序列化成 JSON：

```java
// 实际发生的事，你不用手写
String json = objectMapper.writeValueAsString(apiResponse);
```

转换规则很简单：**对象的每个字段变成 JSON 的一个键**。

```json
{"code":0,"message":"ok","data":"hello","traceId":"d70beb5bd41d47c1","timestamp":1795006553458}
```

> **`record` 能用吗？** 能。Jackson 2.12+ 原生支持 record，不用加任何配置。
> 但 record 没有 setter —— **反序列化时**（前端 JSON → 后端对象）Jackson 会调它的**全参构造器**，所以字段顺序必须一致。

---

### 第 8 步：写回响应，前端解析

Tomcat 把状态码、响应头、JSON 文本拼成 HTTP 响应发回浏览器。

前端拿到后：

```js
const res = await fetch('/api/demo/ok')
// res 是 Response 对象，此时 body 还是一串文本（流）
const body = await res.json()      // ← 解析 JSON 成 JS 对象
console.log(body.data)             // "hello"
```

如果用 Axios + 我们的拦截器（步骤 4 会写）：

```js
http.interceptors.response.use(res => {
  const body = res.data                          // axios 已经帮我们 JSON.parse 过了
  if (body.code === 0) return body.data          // ← 直接把 data 剥出来
  return Promise.reject(body)
})
```

所以业务页面里写的是：

```js
const data = await http.get('/api/demo/ok')
// data 直接就是 "hello"，不用 .data.data
```

## 三、换个视角：POST 请求带 JSON 是怎么传的

GET 只传路径参数，真正复杂的是 POST。以"登录"为例（步骤 3 会实现）。

### 前端

```js
const result = await http.post('/api/auth/login', {
  username: 'alice',
  password: 'Passw0rd1'
})
```

### 生成的 HTTP 请求

```http
POST /api/auth/login HTTP/1.1
Host: localhost:8080
Content-Type: application/json      ← ★ 这一行至关重要
Authorization: Bearer eyJhbGciOi...
Content-Length: 47

{"username":"alice","password":"Passw0rd1"}
```

**`Content-Type: application/json` 是干嘛的？**

告诉后端："我的请求体是用 JSON 格式写的，你按 JSON 解析。"

如果少了这一行，后端不知道该怎么解析请求体，可能当成表单或者纯文本处理，字段全是 null。
**Axios 在你传对象时会自动加上这个头** —— 但用 curl 时必须手动写 `-H "Content-Type: application/json"`，否则会得到奇怪的 400 错误。

### 后端接收

```java
@PostMapping("/login")
public ApiResponse<TokenResponse> login(
        @RequestBody @Valid LoginRequest req) {     // ← 关键在这里
    // req 已经是 Java 对象了：req.username() == "alice"
    return ApiResponse.ok(authService.login(req));
}
```

`@RequestBody` 背后做的事（全是 Spring 自动的）：

```
请求体文本 {"username":"alice","password":"Passw0rd1"}
   ↓  Jackson 反序列化
   ↓  找到 LoginRequest 的构造器
   ↓  按字段名匹配赋值
LoginRequest 对象 (username="alice", password="Passw0rd1")
```

**字段名怎么对上的？** JSON 的键名 ↔ record/类 的字段名，**必须完全一致**（区分大小写）。
前端传 `userName`、后端字段叫 `username`，就会得到 null —— 这是最高频的联调 bug 之一。

### `@Valid` 在做什么

```java
public record LoginRequest(
        @NotBlank String username,
        @NotBlank String password
) {}
```

`@Valid` 触发校验：如果 `username` 是空字符串，Spring 直接抛 `MethodArgumentNotValidException`，
**根本不会进到方法体里**，直接跳到 `GlobalExceptionHandler.handleValid`，
返回：

```json
{
  "code": 10000,
  "message": "参数校验失败",
  "data": [{"field":"username","message":"不能为空"}]
}
```

> 所以你不用担心"参数没传导致 NPE"，前置校验帮你挡住了。

## 四、再换个视角：数据怎么进 MySQL 的

还是登录的例子，从 Controller 往下：

```java
// Controller：只管收参和返回
@PostMapping("/login")
public ApiResponse<TokenResponse> login(@RequestBody @Valid LoginRequest req) {
    return ApiResponse.ok(authService.login(req));       // 交给 Service
}

// Service：业务逻辑 + 事务
@Service
public class AuthService {

    private final UserRepository userRepository;          // 数据访问

    @Transactional
    public TokenResponse login(LoginRequest req) {
        AppUser user = userRepository.findByUsername(req.username())    // ← 就是这一行查库
                .filter(u -> passwordEncoder.matches(req.password(), u.getPasswordHash()))
                .orElseThrow(() -> new BizException(ErrorCode.BAD_CREDENTIALS));
        return issueTokens(user);
    }
}

// Repository：一个接口，没有实现类
public interface UserRepository extends JpaRepository<AppUser, Long> {
    Optional<AppUser> findByUsername(String username);
}
```

### 那个"没有实现类"的接口是怎么查出数据的？

这是 Spring Data JPA 最神奇的地方——**方法名即 SQL**。

Spring 启动时扫描到 `UserRepository`，看到：

- 名字以 `findBy` 开头
- 后面跟 `Username`
- 实体类 `AppUser` 里有个字段叫 `username`

于是它在内存里**动态生成一个实现类**，等价于：

```sql
SELECT * FROM app_user WHERE username = ?
```

然后把这个实现类注册成 Bean，注入到 `AuthService` 里。

**常见的方法名规律：**

| 方法名 | 生成的 SQL |
|---|---|
| `findByUsername(String u)` | `WHERE username = ?` |
| `findByUsernameAndPasswordHash(...)` | `WHERE username = ? AND password_hash = ?` |
| `existsByUsername(String u)` | `SELECT 1 ... WHERE username = ? LIMIT 1` |
| `findByUserIdOrderByCreatedAtDesc(...)` | `WHERE user_id = ? ORDER BY created_at DESC` |
| `countByPostId(...)` | `SELECT COUNT(*) WHERE post_id = ?` |

> 方法名拼错（比如写成 `findByUserName`），**启动时就会报错**，不会等到运行时。这是好事。

### 查询结果怎么变回 Java 对象

`userRepository.findByUsername("alice")` 内部执行 SQL，拿到结果集（一行行的字符串和数字），
再通过 JPA 的映射关系，把 `username` 列填到 `AppUser.username` 字段里。

映射关系是 **`AppUser` 类上的 `@Entity` + `@Column` 注解**定义的：

```java
@Entity
@Table(name = "app_user")            // ← 对应数据库表 app_user
public class AppUser {
    @Column(name = "password_hash")  // ← 字段 passwordHash 对应列 password_hash
    private String passwordHash;
    ...
}
```

> 这就是为什么 `ddl-auto: validate` 这么有用：启动时它会把每个注解和真实表结构对一遍，
> 少一个列、名字差一个字母，**启动就失败**，而不是等到用户点登录才发现。

## 五、异常路径：出错时数据怎么回去

正常流程是一条直线，出错时多了两个转折。以"发布帖子命中手机号"为例：

```
① PostService.publish()
      ↓
   检测到手机号
      ↓
   throw new BizException(POST_PRIVACY_REJECTED, {hits: [...]})   ← 方法在这里中断
      ↓
② 异常向上冒泡，穿过 Service、Controller
      ↓
③ DispatcherServlet 拦住，查 @ExceptionHandler
      ↓
④ GlobalExceptionHandler.handleBiz(e)
      ↓
   ResponseEntity.status(422)              ← HTTP 状态码来自 ErrorCode
       .body(ApiResponse.fail(ec, e.getData()))
      ↓
⑤ 响应：
   HTTP/1.1 422
   {"code":43002, "message":"内容包含个人信息...", "data":{"hits":[...]}, "traceId":"..."}
      ↓
⑥ 前端拦截器：
   if (body.code === 43002) {
       return Promise.reject(body)      // 不弹通用提示，交给页面处理
   }
      ↓
⑦ 发布页 catch 到，弹出 PrivacyHitDialog，把 hits 渲染成列表
```

**几个关键点：**

1. **`throw` 之后，方法里剩下的代码一行都不会执行** —— 这就是为什么业务代码不需要层层 if-return。
2. **HTTP 状态码不是 200** —— 是 422。这样 Nginx 日志、监控系统能正确统计"有多少次内容被拒"。
3. **`data` 字段携带了结构化信息** —— 光有"审核失败"这句话没用，前端需要知道"命中了什么、在第几个字符"，才能高亮定位。

## 六、自己动手验证（建议现在做一遍）

打开一个终端（Git Bash），按顺序执行：

```bash
# ① 看正常响应长什么样
curl -s http://localhost:8080/api/demo/ok
# 观察：code/message/data/traceId/timestamp 五个字段

# ② 看业务异常
curl -s -i http://localhost:8080/api/demo/biz-error | head -3
# 观察第一行 HTTP/1.1 404，然后看响应体的 code=10003
# ★ 注意：HTTP 是 404，但响应体是标准 JSON —— 不是 Spring 默认的错误页

# ③ 看未知异常（对比响应和日志）
curl -s http://localhost:8080/api/demo/boom
# 响应里：{"code":50000,"message":"系统繁忙"}  ← 没有堆栈
# 然后去看 start-backend.bat 的窗口：
#   ERROR [traceId] ... IllegalStateException: 故意炸的   ← 有完整堆栈

# ④ 验证 traceId 贯穿
curl -s -H "X-Trace-Id: my-test-123" http://localhost:8080/api/demo/ok
# 响应里 traceId 应该是 my-test-123
# 再到日志窗口里 grep 一下 my-test-123，确认有对应的日志行

# ⑤ 验证不存在的路径也返回统一格式
curl -s http://localhost:8080/api/not-exist
# 期望 {"code":10003,...} 而不是 Spring 默认的 {"timestamp":...,"status":404,...}
```

**做完这 5 步，你就真正理解"统一响应 + 统一异常 + 链路追踪"是干什么的了。**

## 八、常见疑问

**Q：为什么 Controller 的返回值要用 `ApiResponse<T>` 包一层，不能直接 `return "hello"`？**
可以 `return "hello"`，但那会让每个接口格式不统一。前端拦截器就没法写通用逻辑：
它无法区分"这是数据"还是"这是错误信息"。包一层之后，`code` 字段就是唯一判断依据。

**Q：`@RestController` 和 `@Controller` 到底差在哪？**
差在返回值怎么处理。`@Controller` 会把返回值当"页面模板名"，去 templates 目录找 HTML；
`@RestController` 会把返回值当"要转成 JSON 的数据"。前后端分离项目只用后者。

**Q：前端传的 JSON 字段名和后端 record 的字段名必须一模一样吗？**
必须。除非你用 `@JsonProperty("userName")` 显式指定映射。
我们项目统一用驼峰，前后端保持一致，不需要额外注解。

**Q：为什么我在 Postman 里能调通，浏览器里却报 CORS？**
Postman 不是浏览器，不执行同源策略，所以它不受 CORS 限制。
浏览器会检查响应头里有没有 `Access-Control-Allow-Origin`。
我们通过 Vite 代理（开发）和 Nginx 同域转发（生产）绕开了这个问题，所以生产环境不需要配 CORS。

**Q：日志里的 `[d70beb5bd41d47c1]` 和响应里的 `traceId` 为什么一样？**
因为它们是同一个值——`TraceIdFilter` 放进 MDC 的那一个。
日志格式 `%X{traceId}` 从 MDC 读，`ApiResponse` 也是从 MDC 读。

**Q：改了代码之后为什么没生效？**
`spring-boot:run` 默认不会热更新。改完 Java 代码要**停止再重新启动**。
（IDEA 专业版可以配 DevTools 自动重启，本项目为了简单没有引入。）
