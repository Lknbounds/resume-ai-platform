# 步骤 03：注册登录与 JWT 鉴权（6 小时）

> **目标**：注册、登录拿到 token；带 token 能访问 `/api/users/me`，不带 token 返回 401；登出后旧 token **立刻**失效；刷新 token 时旧的作废（防重放）。
>
> 这是全项目第一个"真的能用"的功能，也是面试最常被追问的部分。

---

## 3.1 这一步做出什么

| 场景 | 行为 |
|---|---|
| 注册新用户 | `POST /api/auth/register` → 201，密码以 BCrypt 存库（`$2a$10$...`） |
| 重复用户名 | 409 + `code=20001` |
| 密码错误 | 401 + `code=20002`（**不区分"用户不存在"和"密码错"**） |
| 登录成功 | 返回 `accessToken`（2 小时）+ `refreshToken`（7 天）+ 用户信息 |
| 带 token 访问 | `GET /api/users/me` 返回自己的资料 |
| 不带 token | 401 + `code=10001` |
| 带垃圾 token | 401 + `code=20003` |
| 登出 | access 的 `jti` 进 Redis 黑名单，**同一个 token 再用就 401** |
| 刷新 | 旧的 refresh 立即作废，发一对新的（轮换） |

---

## 3.2 为什么这样设计（面试可讲）

**① 为什么用 JWT 而不是 Session？**
Session 需要服务端存会话（内存或 Redis），多实例时要共享、要处理粘性会话；JWT 是自包含的，服务端只需验签，**天然无状态**，前后端分离 + 未来横向扩容都更省事。
代价是"签发后无法收回" —— 所以必须配合黑名单（下面第 ② 点）。

**② 既然无状态，为什么还要 Redis 存黑名单？**
JWT 一旦签发，在过期前服务端无法让它失效。但用户点了"退出登录"、或者改了密码，旧 token 必须立刻失效，否则 2 小时内被人拿到就能继续用。
做法：登出时把这个 token 的 `jti`（唯一 id）写进 Redis，TTL = **该 token 的剩余有效期**（过期了自然就没用了，不用存更久）。每次请求校验时查一下黑名单 —— 一次 `GET`，2ms 以内，换来"可撤销"的能力。
**这是"无状态 JWT + 有状态黑名单"的经典折中**，面试很爱问。

**③ 为什么 access 2 小时、refresh 7 天，且 refresh 要"轮换"？**
- access 短：泄露后的风险窗口小；
- refresh 长：用户不用天天登录；
- **轮换**：每次刷新后旧的 refresh 立刻作废。这样即使 refresh 泄露，攻击者也只可能用一次；而且如果攻击者先用，真正的用户下次刷新会失败 —— 这是一个**异常信号**（可用来触发强制下线）。

**④ 为什么登录失败不区分"用户不存在"和"密码错误"？**
区分了就等于给攻击者一个"用户名枚举"接口：先批量试用户名，知道哪些存在，再针对性爆破密码。
统一返回 `20002`，攻击者无从判断。

**⑤ 为什么密码用 BCrypt，而不是 MD5/SHA256？**
MD5/SHA256 是**快速**哈希，正好帮了攻击者 —— 用 GPU 每秒能算几十亿次。BCrypt 是**慢哈希**，内置 salt、可调 cost 因子（本项目用 10，即 2¹⁰ 轮），单次验证约 50-100ms，爆破成本极高。
另外 BCrypt 的哈希串自带 salt 和 cost，所以不需要单独存盐字段。

**⑥ 为什么角色/权限**不**写进 JWT？**
（这条为二期的 RBAC 埋点，现在就要想清楚）
JWT 签发后内容就固定了。如果把 `roles:["ADMIN"]` 写进去，你撤销某人管理员权限后，他手里的 token 在 2 小时内依然是 ADMIN —— **撤权失效**。
所以正确做法：JWT 只放**身份**（userId、jti、类型、过期），角色/权限每次请求从服务端（DB + Redis 缓存）加载。二期做 RBAC 时直接接上。

**⑦ 为什么用 `Authorization: Bearer` 而不是 Cookie？**
Cookie 会自动随请求发送，需要额外防 CSRF；Bearer 头必须由前端显式设置，天然免疫 CSRF。代价是 token 存在 `localStorage`，需要靠"不渲染用户 HTML"来防 XSS（步骤 4 会强调）。

## 3.4 完整代码（带注解）

### 3.4.1 `security/JwtProperties.java`

**JWT 配置** —— 从 yml 读密钥和有效期

```java
package com.jianli.security;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.validation.annotation.Validated;

import java.time.Duration;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  JWT 相关配置的"容器"。把 application.yml 里 app.jwt.* 的值读进来，
 *  变成一个可以注入使用的对象。
 *
 *  yml 里的配置：
 *      app:
 *        jwt:
 *          secret: dev-only-change-me-please-32bytes-min!!
 *          access-ttl: PT2H        ← 2 小时
 *          refresh-ttl: P7D        ← 7 天
 *          issuer: resume-ai
 *
 *  这个类读完之后：
 *      props.secret()      → "dev-only-change-me-please-32bytes-min!!"
 *      props.accessTtl()   → Duration.ofHours(2)
 *      props.refreshTtl()  → Duration.ofDays(7)
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：它被谁用】
 *
 *      application.yml
 *         │  ← Spring Boot 启动时自动读取并绑定
 *         ↓
 *      JwtProperties（本类，一个 Bean）
 *         ├─ JwtTokenProvider  → 拿 secret 签名、拿 ttl 算过期时间
 *         └─ AuthService       → 拿 refreshTtl 决定 refresh token 在 Redis 存多久
 *         ↓
 *      最终影响：用户登录后 token 的有效期
 *
 *  ★ 注意它只是个"数据搬运工"，不产生任何逻辑。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【为什么写这一堆注解】
 *
 *  @ConfigurationProperties(prefix = "app.jwt")
 *      告诉 Spring："把 yml 里 app.jwt 下面那一坨，自动映射到本类的字段上"。
 *
 *      映射规则（叫"宽松绑定"）：
 *          yml 里的 access-ttl   →  Java 字段 accessTtl     （短横线 → 驼峰，自动转）
 *          yml 里的 secret       →  Java 字段 secret
 *      所以你不用逐行写 @Value("${app.jwt.secret}")。
 *
 *      ★ 相比 @Value 的好处：
 *          1. 一处声明，多个字段一起绑
 *          2. 支持嵌套对象和 Map
 *          3. 可以做校验（见下）
 *          4. IDEA 里有自动补全提示（Spring Boot 配置处理器生成的）
 *
 *  @Validated
 *      开启对这个类的校验。有了它，下面的 @NotBlank / @NotNull 才会生效。
 *      ★ 没有这个注解，那些约束注解【完全不起作用】—— 这是个隐蔽的坑。
 *
 *  @NotBlank / @NotNull
 *      校验规则：
 *          @NotBlank → 不能为 null，且至少有一个非空白字符
 *          @NotNull  → 不能为 null（但可以是空对象）
 *
 *      ★ 为什么要校验？校验失败会怎样？
 *        如果 secret 没配（yml 漏了或者环境变量没传），启动时会直接抛出：
 *            Binding to target ... failed: Property: app.jwt.secret
 *            Reason: 不能为空
 *        应用【根本起不来】。
 *
 *        这听起来很严厉，但正是想要的：宁可启动时失败，
 *        也不要启动成功后每次登录都报一个莫名其妙的 NPE。
 *        这叫 fail-fast（快速失败）。
 *
 *
 *  【★ 为什么用 record 而不是普通的 class？】
 *
 *  1. record 天生不可变 —— 配置一旦读进来就不该被改，
 *     否则某处代码偷偷改了 secret，会导致已签发的 token 全部失效。
 *
 *  2. record 的构造器就是"全参构造器"，Spring Boot 会直接调用它，
 *     把 yml 里的值按【构造器参数名】匹配进去。
 *     所以参数名必须和配置项名字对得上（accessTtl ↔ access-ttl）。
 *
 *  3. 不需要 getter —— record 自动生成 secret()、accessTtl() 这样的访问器。
 *     ★ 注意调用时是 props.secret()，不是 props.getSecret()。
 *
 *  ★ record 做配置类有一个限制：不能有 setter，所以是"只读"的。
 *    这对配置类来说正好 —— 本来就不该在运行时改配置。
 */
@Validated
@ConfigurationProperties(prefix = "app.jwt")
public record JwtProperties(

        /**
         * 签名密钥。
         *
         * ★ 它是干什么的？
         *   JWT 是"签名"出来的：服务端用这个 secret 对 token 内容加签，
         *   验签时用同一个 secret 验证。攻击者不知道 secret，
         *   就无法伪造出一个能通过验签的 token。
         *
         * ★ 为什么要求至少 32 字节？
         *   我们用的是 HS256 算法（HMAC-SHA256）。按 RFC 规定，
         *   密钥长度至少要等于哈希输出长度，也就是 256 位 = 32 字节。
         *   短于 32 字节时 jjwt 会抛 WeakKeyException，启动直接失败。
         *
         *   ★★ 这条是安全红线：
         *   现在 yml 里的默认值只适合本地开发。
         *   上线前必须换成随机串，生成方式：
         *       openssl rand -base64 32
         *   否则任何看过你代码的人都能伪造任意用户的 token。
         */
        @NotBlank String secret,

        /**
         * access token 的有效期。
         *
         * yml 里写的是 PT2H，这是 ISO-8601 的时长格式：
         *      P     = Period 的前缀
         *      2H    = 2 小时
         * 其他例子：
         *      PT30M = 30 分钟（T 是"时间部分"的开始，必须写在时分秒前面）
         *      P7D   = 7 天（D 是"天"，属于日期部分，所以不加 T）
         *
         * Spring 会自动把这种字符串转成 Duration 对象，不用你手动 parse。
         *
         * ★ 为什么是 2 小时？
         *   access token 一旦签发，在过期前无法撤销（除非进黑名单）。
         *   时间越短，泄露的窗口越小。但太短会导致用户频繁刷新。
         *   2 小时是"安全"和"体验"的平衡点 —— 也是业界常见值。
         */
        @NotNull Duration accessTtl,

        /**
         * refresh token 的有效期。
         *
         * ★ 为什么比 access 长这么多？
         *   access 过期后，前端用 refresh 换一个新的 access，
         *   用户就不用重新输密码。refresh 管得久，用户就能"七天不用登录"。
         *
         * ★ refresh 这么长会不会不安全？
         *   会，所以有两道保险：
         *     1. refresh token 存在 Redis 白名单里，服务端可随时删除（登出、改密、禁用）
         *     2. 每次刷新都会"轮换"：旧的立刻作废，发新的。
         *        即使被偷，攻击者也只能用一次。
         */
        @NotNull Duration refreshTtl,

        /**
         * 签发者标识，写进 token 的 iss 字段。
         *
         * ★ 有什么用？
         *   如果将来有多个服务共用同一套 secret（不推荐，但可能出现），
         *   可以通过 iss 判断"这个 token 是哪个服务签的"。
         *   现在只有一个服务，纯粹是个规范字段，填什么都行。
         */
        String issuer
) {}
```

### 3.4.2 `infra/redis/RedisKeys.java`

**Redis key 命名中心** —— 所有 key 只从这里生成，杜绝拼写不一致

```java
package com.jianli.infra.redis;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  Redis key 的"集中命名中心"。所有 key 都从这里生成，不允许各处手写字符串。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么要把 key 集中管理？】
 *
 *  假设你到处手写：
 *      redis.get("refresh:" + userId + ":" + jti);
 *      redis.delete("refresh:" + userId + ":" + jti);       ← 少写个冒号？
 *      redis.delete("auth:refresh:" + userId + ":" + jti);  ← 多写个前缀？
 *
 *  这三处只要有一处拼错，就会出现"存进去了但删不掉"的 bug，
 *  而且是【静默的】—— 不报错，只是莫名其妙地登出不了。
 *
 *  集中之后：
 *      存：keys.refresh(userId, jti)
 *      删：keys.refresh(userId, jti)      ← 永远是同一个字符串
 *  从根上杜绝了拼写不一致。
 *
 *  【★ 集中管理还有这些好处】
 *      1. 排查时能一眼看出"这个前缀是谁写的、TTL 多久"（注释里写着）
 *      2. 想改命名规范只改一个文件
 *      3. 不会出现两个功能用同一个 key 互相覆盖
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：这些 key 在哪儿被读写】
 *
 *      AuthService.login()
 *         └─ TokenService.saveRefresh(userId, jti, ttl)
 *               └─ redis SET auth:refresh:{userId}:{jti} "1" EX 7d
 *
 *      JwtAuthenticationFilter 每个请求都执行
 *         └─ TokenService.isBlacklisted(jti)       ← 一次 Redis GET，约 1-2ms
 *
 *      AuthService.logout()
 *         ├─ TokenService.blacklistAccess(jti, 剩余有效期)
 *         └─ TokenService.revokeRefresh(userId, jti)
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【为什么是 final class + 私有构造器 + 全 static 方法？】
 *
 *  这是一个"工具类"，不装任何状态，只有一堆拼字符串的方法。
 *  这种类不应该被 new 出来用（new 出来也没有意义，因为每条 new 出来的实例都一样）。
 *
 *      final class      → 禁止别人继承它（继承工具类没有意义，只会带来麻烦）
 *      私有构造器       → 禁止别人 new 它
 *      static 方法      → 直接用类名调：RedisKeys.refresh(...)
 *
 *  ★ 私有构造器写个空方法体就行，作用是"堵住 new 的路"。
 *    不加的话，Java 会默认给一个 public 的无参构造器，别人就能 new。
 */
public final class RedisKeys {

    /**
     * 私有构造器。
     * 里面写注释说明"这是故意的，不是忘了写代码"，
     * 否则下一个看到的人会以为是个未完成的空类。
     */
    private RedisKeys() {
        // 工具类，禁止实例化
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【key 命名规范】
     *
     *  格式：业务域:类型:标识
     *      auth:refresh:1:abc-123
     *      │    │       │  │
     *      │    │       │  └─ jti（token 的唯一 id）
     *      │    │       └──── userId
     *      │    └──────────── 存的是什么
     *      └───────────────── 哪个模块
     *
     *  ★ 为什么用冒号分隔而不是下划线？
     *  这是 Redis 社区惯例。Redis Desktop Manager、RedisInsight 这类工具
     *  会把冒号分隔的 key 显示成【树状目录】，一层层展开看很清晰：
     *
     *      auth
     *        └─ refresh
     *             ├─ 1
     *             │   └─ jti-a
     *             └─ 7
     *                 └─ jti-b
     *
     *  用下划线的话就是一长串平铺，几十个 key 根本看不清。
     * ═══════════════════════════════════════════════════════════════
     */

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【refresh token 白名单】
     *
     *  实际 key：  auth:refresh:{userId}:{jti}
     *  存入的值：  "1"（值本身没意义，只关心 key 在不在）
     *  过期时间：  7 天（和 refresh token 的有效期一致）
     * ═══════════════════════════════════════════════════════════════
     *
     *  【★ 为什么需要"白名单"？JWT 不是号称无状态吗？】
     *
     *  这是个很好的矛盾点，面试常问。
     *
     *  JWT 的设计初衷是无状态：服务端不存任何东西，只验签就能知道你是谁。
     *  但这样有个致命问题：签发之后无法撤销。
     *      - 用户点了"退出登录" → token 还能用
     *      - 用户改了密码       → 旧 token 还能用
     *      - 账号被封禁         → token 还能用
     *  在过期之前（2 小时），这些都拦不住。
     *
     *  所以我们的做法是：JWT 管"身份"（无状态），Redis 管"撤销"（有状态）。
     *  两个配合，既有 JWT 的简洁，又有会话的可控。
     *
     *  【★ 那为什么叫"白名单"？和黑名单有什么区别？】
     *
     *  白名单：只承认登记过的 token，没登记的一律不认（默认拒绝）
     *  黑名单：默认都认，只有登记过的才不认（默认放行）
     *
     *  我们两个都用，各管一种 token：
     *
     *      refresh token 用【白名单】：
     *          有效期 7 天太长，必须严格管控。
     *          登录时登记，刷新时轮换，登出时删除。
     *          Redis 里没有 = 作废，哪怕它签名是对的。
     *
     *      access token 用【黑名单】：
     *          有效期只有 2 小时，风险窗口小。
     *          不做严格管控（否则每个请求都要查 Redis，2 小时就要存一次）。
     *          只在用户主动登出时拉黑那一个 jti。
     *
     *  【★ 为什么 key 里要带 userId？】
     *  为了能"批量删除某个用户的全部 refresh token"。
     *  改密码、禁用账号时，要把这个人在所有设备上的登录都踢掉，
     *  此时用 pattern 匹配：auth:refresh:{userId}:*
     *
     *  如果只按 jti 存（不带 userId），你根本不知道某个人的 token 是哪几个。
     *
     *  @param userId 用户 id
     *  @param jti    token 的唯一 id（JWT 标准字段，见 JwtTokenProvider 里的 .id(...)）
     *  @return 完整的 Redis key
     */
    public static String refresh(Long userId, String jti) {
        return "auth:refresh:" + userId + ":" + jti;
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【access token 黑名单】
     *
     *  实际 key：  auth:blacklist:{jti}
     *  存入的值：  "1"
     *  过期时间：  【该 token 的剩余有效期】
     * ═══════════════════════════════════════════════════════════════
     *
     *  【★ 关键设计：TTL 为什么是"剩余有效期"而不是固定值？】
     *
     *  因为 token 一旦自然过期，黑名单里再存它就没有意义了 ——
     *  验签那一步就会失败，根本走不到查黑名单。
     *
     *  举例：
     *      用户在 10:00 登录，拿到 access token（12:00 过期）
     *      用户在 10:30 点退出登录
     *      → 这个 token 还剩 1.5 小时
     *      → 黑名单 TTL 设 1.5 小时
     *      → 12:00 之后这条记录自动消失（此时 token 本身也失效了）
     *
     *  ★ 如果 TTL 写死成 7 天呢？
     *  黑名单会无限膨胀 —— 每次登出都留一条记录，存到 Redis 里，
     *  而且那条记录在 token 过期后 6 天半都是纯垃圾。
     *
     *  ★ 这就是"让 TTL 和数据生命周期对齐"的典型做法：
     *  不需要额外的清理任务，Redis 自动回收。
     *
     *  【★ 为什么 key 里只有 jti，没有 userId？】
     *  因为判断"这个 token 是否被拉黑"时，只有 token 本身，拿不到 userId
     *  （要先验签才知道是谁，而验签后 jti 已经有了）。
     *  而且登出只影响这一个 token，不需要批量操作。
     *
     *  @param jti token 的唯一 id
     *  @return 完整的 Redis key
     */
    public static String blacklist(String jti) {
        return "auth:blacklist:" + jti;
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【后面步骤会往这里加什么】
     *
     *  步骤 7/10 - AI 缓存：
     *      cache:jdparse:{hash}          JD 解析结果，TTL 7 天
     *      cache:resumeparse:{hash}      简历解析结果，TTL 30 天
     *      cache:embedding:{hash}        向量，TTL 30 天
     *
     *  步骤 8 - 分析：
     *      cache:analysis:{cacheKey}     完整报告，TTL 24 小时
     *      lock:analysis:{cacheKey}      并发去重锁，TTL 120 秒
     *
     *  步骤 13 - 社区：
     *      zset:post:hot                 热度榜（ZSET，无 TTL，定时重建）
     *      stats:post:view               浏览数缓冲（HASH，定时回写）
     *
     *  限流：
     *      rate:login:{ip}               登录限流
     *      rate:post:{userId}            发帖限流
     *
     *  ★ 到时候照这里的格式加方法即可，保持"key 只从本类生成"的规矩。
     * ═══════════════════════════════════════════════════════════════
     */
}
```

### 3.4.3 `security/JwtTokenProvider.java`

**生成/解析 token** —— 全项目唯一碰 JWT 底层的地方

```java
package com.jianli.security;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.stereotype.Component;

import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.time.Duration;
import java.time.Instant;
import java.util.Date;
import java.util.UUID;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  负责"生成 token"和"解析 token"。整个项目只有这一个类碰 JWT 的底层细节。
 *
 *  你可以把它理解成"盖章机"：
 *      createAccess()  → 写一张凭证，盖上防伪章
 *      parse()         → 验章，验过了就把凭证内容读出来
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：token 的一生】
 *
 *      ① 用户登录，AuthService 调 createAccess(userId, username)
 *            ↓ 用 secret 签名，生成一串 "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0.xxx"
 *            ↓
 *      ② 返回给前端，前端存进 localStorage
 *            ↓
 *      ③ 之后每个请求都带上：Authorization: Bearer eyJhbGci...
 *            ↓
 *      ④ JwtAuthenticationFilter 拦截请求，调 parse(token)
 *            ↓ 验签名、验过期
 *            ↓ 通过就拿到底部 Claims（里面装着 userId、jti、type）
 *            ↓
 *      ⑤ 把 userId 放进 SecurityContext，Controller 就能拿到"当前用户是谁"
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ JWT 到底长什么样？】
 *
 *  它是由"点"分隔的三段 base64 文本：
 *
 *      eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiIxIiwiZXhwIjoxNzY1fQ  .  4kX9p2mQ...
 *      └───── 头部 ─────┘     └──────── 载荷 ────────┘     └── 签名 ──┘
 *
 *  头部（Header）：算法信息，比如 {"alg":"HS256"}
 *  载荷（Payload）：真正的内容，比如 {"sub":"1","username":"alice","jti":"xxx","exp":1765000000}
 *  签名（Signature）：用 secret 对前两段算出来的 HMAC
 *
 *  ★★ 最关键的一点：载荷是【明文】的，只是 base64 编码，不是加密！
 *      任何人拿到 token 都能解开看到里面的 userId 和 username。
 *      打开 jwt.io 粘贴进去就能看到。
 *
 *      所以：绝对不能把密码、身份证、手机号之类的敏感信息放进 token。
 *      至于"为什么没人能伪造"，靠的是第三段签名 ——
 *      改了前两段的任何内容，签名就对不上，服务端验签会失败。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【@Component 是什么】
 *  注册成 Spring Bean，这样 AuthService、JwtAuthenticationFilter
 *  就能通过构造器把它注入进去用。
 *
 *  为什么不加 @Service？
 *  @Service 和 @Component 功能上完全一样，只是语义不同：
 *      @Service      → "我是业务逻辑"
 *      @Component    → "我是个通用组件"
 *  JWT 工具不属于业务逻辑，用 @Component 更准确。
 */
@Component
public class JwtTokenProvider {

    /**
     * token 类型的两个取值。
     *
     * ★ 为什么要区分 type？
     *   我们签发两种 token：access 和 refresh。它们的"能力"完全不同：
     *      access  → 可以用来访问接口（2 小时）
     *      refresh → 只能用来换新的 access（7 天）
     *
     *   如果不区分，用户可以拿 refresh token 直接访问接口 ——
     *   而 refresh 有 7 天有效期，等于变相延长了 access 的生命期，
     *   短有效期的安全设计就白做了。
     *
     *   ★ 所以 JwtAuthenticationFilter 里会检查：
     *       if (!TYPE_ACCESS.equals(type)) { 不认 }
     *
     * 定义成 public static final 常量，其他地方引用它就不会拼错字符串。
     */
    public static final String TYPE_ACCESS = "access";
    public static final String TYPE_REFRESH = "refresh";

    private final JwtProperties props;

    /**
     * 用于签名的密钥对象。
     *
     * ★ 为什么在构造器里算一次，而不是每次签名时再算？
     *   因为 Keys.hmacShaKeyFor(...) 内部会做校验（长度够不够 256 位），
     *   而且创建对象本身有开销。签名和验签是高频操作（每个请求一次），
     *   所以只建一次，之后复用。这也是它被声明成 final 的原因。
     */
    private final SecretKey key;

    /**
     * 构造器注入。
     *
     * ★ Spring 是怎么调用的？
     *   本类只有一个构造器，Spring 会自动用容器里的 JwtProperties bean 来调它。
     *   这就是"构造器注入" —— 比字段上加 @Autowired 更好，因为：
     *     1. 字段可以声明成 final（不可变，线程安全）
     *     2. 依赖关系一眼可见（看构造器就知道需要什么）
     *     3. 测试时可以直接 new JwtTokenProvider(mockProps)
     *
     * ★ Keys.hmacShaKeyFor(byte[]) 做了什么？
     *   把任意字节数组包装成一个 HMAC-SHA 密钥对象。
     *   如果长度不足 256 位（32 字节），它会抛 WeakKeyException ——
     *   这正好帮我们兜住了"secret 配得太短"的问题。
     */
    public JwtTokenProvider(JwtProperties props) {
        this.props = props;
        // getBytes(UTF_8) 很重要：不指定字符集的话，中文会按平台默认编码转换，
        // 导致不同机器算出的密钥不一样，token 就互相验不过了
        this.key = Keys.hmacShaKeyFor(props.secret().getBytes(StandardCharsets.UTF_8));
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【生成 access token】有效期 2 小时，可用于访问接口
     * ═══════════════════════════════════════════════════════════════
     *
     * @param userId   用户 id
     * @param username 用户名（放进 token 是为了方便日志排查，
     *                 真正判断身份用的是 userId）
     * @return 形如 "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0.xxx" 的字符串
     */
    public String createAccess(Long userId, String username) {
        return build(userId, username, TYPE_ACCESS, props.accessTtl());
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【生成 refresh token】有效期 7 天，只能用来换新 token
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 除了 ttl 和 type，其他和 access 完全一样。
     *   所以抽象的 build() 方法把公共部分抽出来了。
     */
    public String createRefresh(Long userId, String username) {
        return build(userId, username, TYPE_REFRESH, props.refreshTtl());
    }

    /**
     * 两种 token 的共同构造逻辑。
     *
     * ★ 为什么抽成私有方法？
     *   如果 createAccess 和 createRefresh 各写一遍，
     *   哪天要加一个 claim（比如设备 id），就得改两处，容易漏。
     *   抽出来之后只改一处。
     */
    private String build(Long userId, String username, String type, Duration ttl) {
        Instant now = Instant.now();

        return Jwts.builder()

                /*
                 * 【.id(...)】设置 jti（JWT ID），一个唯一标识符。
                 *
                 * ★★ 这是整个撤销机制的基石，务必理解：
                 *
                 *   为什么不能直接用 token 字符串本身做黑名单的 key？
                 *     1. token 有几百个字符，做 Redis key 太长，浪费内存
                 *     2. 每次查询都要拿完整 token 去匹配，不方便
                 *
                 *   用 jti 就解决了：一个 36 字符的 UUID，短且唯一。
                 *   服务端只需要记"jti=xxx 已作废"，
                 *   验 token 时取出它的 jti 去查一下就知道有没有被撤销。
                 *
                 * ★ UUID.randomUUID() 保证每次生成都不一样，
                 *   所以同一用户连续登录两次，拿到的是两个不同的 token，
                 *   互不影响（可以分别登出）。
                 */
                .id(UUID.randomUUID().toString())

                /*
                 * 【.subject(...)】设置 sub（Subject），JWT 标准字段，
                 * 表示"这个 token 是谁的"。
                 *
                 * ★ 为什么存 userId 而不是 username？
                 *   userId 是数字主键，永不变更；username 理论上可以改
                 *   （虽然本项目不支持，但设计上更稳妥）。
                 *   而且 userId 更短。
                 *
                 * ★ 为什么 String.valueOf(userId)？
                 *   因为 JWT 规范要求 sub 是字符串类型。
                 */
                .subject(String.valueOf(userId))

                /*
                 * 【.claim(...)】自定义字段，随便加。
                 *
                 * username：方便日志排查（看到日志里能直接知道是谁）
                 * type    ：区分 access / refresh（见上面 TYPE_ACCESS 的说明）
                 *
                 * ★ 注意：这些都明文可见！不要放敏感信息。
                 */
                .claim("username", username)
                .claim("type", type)

                /* 签发者标识，来自配置 */
                .issuer(props.issuer())

                /*
                 * 【.issuedAt(...)】签发时间（iat 字段）。
                 * 一般是 base64 解码后能看到的数字时间戳。
                 */
                .issuedAt(Date.from(now))

                /*
                 * 【.expiration(...)】过期时间（exp 字段）。
                 *
                 * ★ 这是 JWT 自带的过期机制：
                 *   验签时 jjwt 会自动检查 exp，过期了直接抛 ExpiredJwtException。
                 *   我们不需要自己写"判断是否过期"的代码。
                 *
                 * ★ 但要注意：过期检查和签名检查是【同时】做的，
                 *   所以过期 token 和伪造 token 抛的是不同异常类型 ——
                 *   这一点在 JwtAuthenticationFilter 里可以区分处理。
                 */
                .expiration(Date.from(now.plus(ttl)))

                /*
                 * 【.signWith(key)】签名。
                 *
                 * ★ 这是 JWT 的灵魂：用密钥对"头部+载荷"算一个 HMAC-SHA256，
                 *   拼成第三段。
                 *
                 *   验证方用同一个密钥重算一遍，对得上就说明内容没被篡改过。
                 *   攻击者不知道密钥，改了内容就必然算不出正确的签名。
                 *
                 * ★ 这一步之后，token 就不能再修改了 ——
                 *   哪怕改一个字，签名都会对不上。
                 */
                .signWith(key)

                /*
                 * 【.compact()】把三部分拼成一个 "a.b.c" 的字符串。
                 * 前面所有配置都只是在构建一个对象，这一步才真正产出 token。
                 */
                .compact();
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【解析并验证 token】
     * ═══════════════════════════════════════════════════════════════
     *
     * 一次调用做了三件事：
     *   1. 用密钥验证签名（内容有没有被篡改）
     *   2. 检查过期时间（有没有超时）
     *   3. 检查格式（是不是合法的 JWT）
     *
     * 全部通过 → 返回 Claims（token 里的内容）
     * 任何一项失败 → 抛异常
     *
     * ★ 抛出的异常类型（调用方可以据此区分原因）：
     *      ExpiredJwtException     → 过期了
     *      SignatureException      → 签名不对（伪造或密钥换了）
     *      MalformedJwtException   → 格式不是 JWT
     *      IllegalArgumentException → 空字符串等
     *   它们都继承自 JwtException，所以调用方一般统一 catch JwtException 即可。
     *
     * ★ 为什么是 parseSignedClaims 而不是旧版的 parseClaimsJws？
     *   jjwt 0.12 版本重命名了 API。网上大量旧教程还是 0.9 的写法
     *   （setSigningKey / parseClaimsJws），照抄会编译不过。
     *   我们已经把 jjwt 锁在 0.12.6，请用这里的新 API。
     *
     * @param token 完整的 token 字符串
     * @return Claims，可以通过它取 sub / jti / claim 等
     */
    public Claims parse(String token) {
        return Jwts.parser()
                .verifyWith(key)          // 指定验签用的密钥
                .build()
                .parseSignedClaims(token) // 解析 + 验签 + 验过期，一步到位
                .getPayload();            // 取出载荷部分（0.12 里叫 payload，旧版叫 body）
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【下面几个是"读取 Claims 内容"的便捷方法】
     *
     *  为什么单独封装，而不是调用方自己写 claims.getSubject()？
     *    1. 把"字段名 → 类型"的转换收在一处。
     *       sub 存的是字符串 "1"，但业务要的是 Long 1。
     *       每个调用方都写 Long.valueOf(claims.getSubject()) 太啰嗦也容易忘。
     *    2. 以后如果换了字段名（比如改成从自定义 claim 里读 id），
     *       只改这里，不用改十几个调用点。
     * ═══════════════════════════════════════════════════════════════
     */

    /** 取出用户 id。sub 存的是字符串，这里转成 Long 给业务用 */
    public Long userId(Claims claims) {
        return Long.valueOf(claims.getSubject());
    }

    /** 取出 jti（token 唯一 id）。黑名单和白名单都靠它 */
    public String jti(Claims claims) {
        return claims.getId();
    }

    /** 取出 token 类型（access / refresh） */
    public String type(Claims claims) {
        return claims.get("type", String.class);
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【计算剩余有效期】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 用在哪：用户登出时，要把 access token 拉黑。
     *   黑名单的 TTL 应该等于"这个 token 还剩多久过期"，
     *   因为过期之后它自然就无效了，黑名单记录也没用了（详见 RedisKeys.blacklist 的说明）。
     *
     * ★ 计算方式：
     *      exp（过期时刻，毫秒） - 当前时刻（毫秒） = 剩余毫秒
     *      再除以 1000 得到秒数（Redis 的 TTL 单位是秒）
     *
     * ★ 为什么要 Math.max(seconds, 1)？
     *   边界情况：如果 token 刚好在这一毫秒过期，算出来可能是 0 或负数。
     *   Redis 的 EX 参数不能是 0 或负数（会直接报错），所以兜底成 1 秒。
     *   反正它马上就过期了，存 1 秒和存 0 秒效果一样。
     */
    public Duration remainingTtl(Claims claims) {
        long seconds = (claims.getExpiration().getTime() - System.currentTimeMillis()) / 1000;
        return Duration.ofSeconds(Math.max(seconds, 1));
    }
}
```

### 3.4.4 `security/LoginUser.java`

**认证主体** —— 表示当前登录的是谁，只放 id 和 username

```java
package com.jianli.security;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  表示"当前登录的是谁"。只有两个字段：id 和 username。
 *
 *  它是认证信息的载体，会在请求处理过程中被放进 Spring Security 的上下文里，
 *  之后任何地方都能取出来。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：它在哪儿产生、在哪儿被用】
 *
 *      JwtAuthenticationFilter 解析 token
 *         ├─ 从 Claims 里取出 userId 和 username
 *         ├─ new LoginUser(userId, username)          ← ★ 在这里创建
 *         └─ SecurityContextHolder.setAuthentication(...)   ← 放进"当前请求的保险箱"
 *              ↓
 *      Controller 的参数上写 @CurrentUserId Long userId
 *         └─ CurrentUserIdResolver 从保险箱里取出 LoginUser，返回它的 id
 *              ↓
 *      Service 收到 userId，用它做归属校验
 *         └─ resumeRepository.findByIdAndUserId(resumeId, userId)
 *
 *  ★ 它只活在一次请求内。请求结束，Spring 自动清空上下文，
 *    下一个请求是全新的（正因为如此，每次请求都要重新验 token）。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么只有两个字段？为什么不把整个 AppUser 放进来？】
 *
 *  1. 【性能】每个请求都要验 token，如果每次查一遍数据库拿完整用户对象，
 *     并发高了数据库扛不住。而用户 id 和用户名在 token 里就有，不用查库。
 *
 *  2. 【安全性】如果把 AppUser 放进来（里面有 passwordHash），
 *     一旦某处代码不小心把它返回给前端，密码哈希就泄露了。
 *     只放必要信息，从源头减少风险。
 *
 *  3. 【时效性】即使数据库里用户改了昵称，请求上下文里还是旧值 ——
 *     但这没关系，因为需要最新数据的地方会主动查库（比如查个人资料）。
 *
 *  ★ 需要完整用户信息时怎么办？
 *    在 Service 里按 id 查：userRepository.findById(loginUser.id())。
 *    多一次查询，但换来"数据一定是新的"，这是合理的取舍。
 *
 *
 *  【★ 为什么用 record 而不是普通 class？】
 *
 *  1. 不可变：认证信息一旦确定，在这次请求内就不该被改。
 *     如果可变，某个 Filter 改了它，后面的代码就会被骗。
 *
 *  2. 代码短：两个字段如果用 class，要写构造器 + 两个 getter + equals
 *     + hashCode + toString，一共 30 行。record 一行搞定。
 *
 *  3. 没有 setter：杜绝了"不小心改了当前用户"的可能。
 *
 *
 *  【★ 为什么字段类型 userId 是 Long，不是 String？】
 *  token 的 sub 里存的确实是字符串 "1"，但业务代码里到处用的是 Long。
 *  在"进入系统"的边界上（JwtTokenProvider.userId）就把类型转换做好，
 *  之后的代码就都用 Long，不需要到处 Long.valueOf(...)。
 *
 *  这叫"在边界处做类型转换，让内部类型干净"。
 */
public record LoginUser(

        /**
         * 用户 id（数据库主键）。
         *
         * ★ 这是最重要的字段 —— 所有归属校验都靠它：
         *       "这份简历是不是你的"       → resume.userId == loginUser.id()
         *       "这个帖子是不是你发的"     → post.userId == loginUser.id()
         *       "你不能给自己的帖子点赞"   → post.userId == loginUser.id()
         */
        Long id,

        /**
         * 用户名。
         *
         * ★ 为什么认证只需要 id，还要带 username？
         *   纯粹是为了【日志排查方便】。
         *   日志里打 "userId=7" 你还得去数据库查是谁；
         *   打 "userId=7(alice)" 一眼就明白了。
         *
         * ★ 它不参与任何权限判断 —— 权限只认 id。
         */
        String username
) {

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【为什么这个类没有 @Component / @Service 注解？】
     *
     *  因为它不是"由 Spring 创建和管理的对象"，而是"每次请求临时创建的"。
     *  Spring 容器里不应该有一个 LoginUser 的 Bean —— 那意味着"全局只有一个当前用户"，
     *  显然不对。
     *
     *  ★ 区分两类对象：
     *    Spring 管理的 Bean（有 @Component 等）→ 全局唯一，多请求共享
     *    数据对象（无注解）                    → 每次 new，只属于当前请求
     * ═══════════════════════════════════════════════════════════════
     */

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ 关于二期 RBAC：为什么这里没有权限字段？】
     *
     *  你可能会想：管理员和普通用户，不都在这个类里区分吗？
     *
     *  ★ 现在确实没有，这是【刻意的】，理由很重要：
     *
     *  如果把角色写进 JWT：
     *      用户在 10:00 登录 → token 里写着 roles=["ADMIN"]
     *      你在 10:30 撤销了他的管理员权限
     *      → 他手里的 token 在 12:00 之前【依然是 ADMIN】
     *      → 撤权失效 2 小时
     *
     *  正确的做法（附B 文档里有完整设计）：
     *      JWT 只放身份（userId、jti、类型、过期）
     *      每次请求从服务器（DB + Redis 缓存）加载权限
     *      → 权限变更立即生效
     *
     *  所以二期做 RBAC 时，这个类会变成：
     *      public record LoginUser(Long id, String username, Set<String> authorities)
     *  而 authorities 由 JwtAuthenticationFilter 在每次请求时填充，
     *  不是从 token 里读出来的。
     * ═══════════════════════════════════════════════════════════════
     */
}
```

### 3.4.5 `security/TokenService.java`

**Redis 白名单 + 黑名单** —— 实现 JWT 的可撤销能力

```java
package com.jianli.security;

import com.jianli.infra.redis.RedisKeys;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;

import java.time.Duration;
import java.util.Set;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  管理 "哪些 token 还有效" 的账本。它不碰 JWT 本身，只管 Redis 里那几条记录。
 *
 *  两个账本：
 *      白名单（refresh）→ 登记过的 refresh token 才算数
 *      黑名单（access） → 登记过的 access token 立刻作废
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：三个场景，看清楚谁调谁】
 *
 *  ── 场景一：登录 ──
 *      AuthService.login()
 *         └─ tokenService.saveRefresh(userId, jti, 7天)
 *               └─ Redis SET auth:refresh:{userId}:{jti} "1" EX 604800
 *         （同时把新 token 返回给前端）
 *
 *  ── 场景二：每个请求 ──
 *      JwtAuthenticationFilter
 *         └─ tokenService.isBlacklisted(jti)
 *               └─ Redis EXISTS auth:blacklist:{jti}
 *               → true  → 认定 token 已作废，不设置认证信息
 *               → false → 正常放行
 *
 *  ── 场景三：登出 ──
 *      AuthService.logout(accessToken, refreshToken)
 *         ├─ tokenService.blacklistAccess(jti, 剩余有效期1.5小时)
 *         │     └─ Redis SET auth:blacklist:{jti} "1" EX 5400
 *         └─ tokenService.revokeRefresh(userId, jti)
 *               └─ Redis DEL auth:refresh:{userId}:{jti}
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么用 StringRedisTemplate 而不是 RedisTemplate？】
 *
 *  RedisTemplate（不带 String）默认用 JDK 序列化 —— key 和 value 会被序列化成一堆
 *  二进制字节，你在 redis-cli 里看到的是：
 *      "\xac\xed\x00\x05t\x00\rauth:refresh:1"
 *  完全没法读，也没法手动排查。
 *
 *  StringRedisTemplate 是它的子类，指定了"key 和 value 都按字符串处理"，所以：
 *      redis-cli> GET auth:refresh:1:abc-123
 *      "1"                                  ← 干净可读
 *
 *  ★ 我们存的都是字符串（"1"、id 等），所以用 StringRedisTemplate 最合适。
 *    如果要存对象（比如把报告 JSON 存 Redis），也是先自己转成 JSON 字符串再存，
 *    依然用 StringRedisTemplate。
 *
 *
 *  【@Service 和 @Slf4j 是什么】
 *  @Service  → 注册成 Bean（语义上表示"这是个业务服务"）
 *  @Slf4j    → Lombok 自动生成 log 对象，可以直接 log.warn(...)
 *
 *  【@RequiredArgsConstructor 是什么】
 *  Lombok 为所有 final 字段生成一个构造器。
 *  因为只有一个构造器，Spring 会自动用它做"构造器注入"。
 *
 *  ★ 这比在字段上写 @Autowired 更好：
 *      1. 字段可以是 final（不可变）
 *      2. 依赖关系在构造器签名上一目了然
 *      3. 写测试时可以直接 new TokenService(mockRedis)
 */
@Slf4j
@Service
@RequiredArgsConstructor
public class TokenService {

    /**
     * Spring 自动注入的 Redis 客户端。
     *
     * ★ 它从哪来？spring-boot-starter-data-redis 这个依赖会自动配置一个
     *   StringRedisTemplate bean，连的是 application.yml 里配的
     *   spring.data.redis.host/port（默认 localhost:6379）。
     *
     * ★ 所以本类能工作的前提是：Redis 必须在跑。
     *   没启动的话，调用任何方法都会抛 RedisConnectionFailureException。
     *   启动方式：双击 start-redis.bat
     */
    private final StringRedisTemplate redis;

    // ═══════════════════════════════════════════════════════════════
    //  【一、refresh token 白名单】
    // ═══════════════════════════════════════════════════════════════

    /**
     * 登录/刷新成功后，把 refresh token 登记进白名单。
     *
     * ★ 为什么登录时一定要存？
     *   因为后面的 isRefreshValid 会检查"这个 token 在不在名单里"。
     *   不存的话，用户拿回来的 refresh token 永远刷不出新 token。
     *
     * ★ TTL 为什么必须设？
     *   Redis 的 key 如果不设过期时间，会永久留存在内存里。
     *   用户量大了之后，几万个永远不会被访问的 key 会撑爆内存。
     *   设成和 token 一样的 7 天，token 失效时记录也自动消失。
     *
     * @param userId 用户 id
     * @param jti    token 唯一 id
     * @param ttl    存活时间（= refresh token 的有效期）
     */
    public void saveRefresh(Long userId, String jti, Duration ttl) {
        /*
         * opsForValue() → 操作"字符串类型"的数据（Redis 最基础的类型）
         * set(key, value, duration) → SET key value EX seconds
         *
         * ★ 值为什么是 "1"？
         *   我们只关心"这个 key 存不存在"，不关心它存了什么。
         *   存 "1" 最省内存（其实存空字符串也行，但有些客户端对空值处理不一致，
         *   存个固定值最保险）。
         */
        redis.opsForValue().set(RedisKeys.refresh(userId, jti), "1", ttl);
        log.debug("refresh token 已登记, userId={}, jti={}", userId, jti);
    }

    /**
     * 检查 refresh token 是否还在白名单里。
     *
     * ★ 什么时候返回 false？
     *   1. 用户主动登出 → 我们删掉了记录
     *   2. 刷新时轮换 → 旧的被删，只有最新的有效
     *   3. 改密码/被禁用 → revokeAllRefresh 清空了这个人的所有记录
     *   4. 超过 7 天 → Redis 自动删除了这条记录
     *
     * ★ 为什么用 hasKey 而不是 get？
     *   hasKey → EXISTS key，只判断存不存在，不取值
     *   get    → GET key，把值也读出来
     *   我们不需要值，所以用更轻量的 hasKey。
     *
     * ★ 为什么写 Boolean.TRUE.equals(...)？
     *   hasKey 返回的是 Boolean（包装类型），可能是 null
     *   （虽然实际不会，但编译器的类型是 Boolean）。
     *   直接写 if (redis.hasKey(...)) 会有 NPE 风险（自动拆箱）。
     *   Boolean.TRUE.equals(x) 是安全写法：null 时返回 false，不会抛异常。
     */
    public boolean isRefreshValid(Long userId, String jti) {
        return Boolean.TRUE.equals(redis.hasKey(RedisKeys.refresh(userId, jti)));
    }

    /**
     * 让某个 refresh token 作废（从白名单里删掉）。
     *
     * ★ 用在哪：
     *   1. 登出时删掉当前这一个
     *   2. 刷新时"轮换" —— 删掉旧的，存新的（见 AuthService.refresh）
     *
     * ★ 删除之后，这个 token 即便签名正确、也没过期，
     *   也会因为"不在白名单里"而被拒绝。这是白名单机制的核心。
     */
    public void revokeRefresh(Long userId, String jti) {
        redis.delete(RedisKeys.refresh(userId, jti));
        log.debug("refresh token 已作废, userId={}, jti={}", userId, jti);
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【踢下线：清掉这个用户的所有 refresh token】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 用在哪：
     *   1. 改密码 → 所有设备强制重新登录（这是安全惯例：
     *      万一密码已经泄露，攻击者的会话也一并失效）
     *   2. 二期禁用账号 → 立即踢出所有在线设备
     *
     * ★ 怎么找到这个人的所有 token？
     *   用 keys("auth:refresh:7:*") 做模式匹配，匹配出所有 key 再批量删除。
     *
     * ★★ 重要提醒：keys 命令在 key 数量多时会【阻塞 Redis】！
     *
     *   Redis 是单线程的。KEYS 会遍历整个数据库，几百万个 key 时会卡住几百毫秒，
     *   期间所有其他请求都被阻塞。生产环境一般禁用 KEYS，改用 SCAN 分批遍历。
     *
     *   ★ 为什么我们这个项目可以用？
     *     本项目用户量小，key 数量在几千级别，KEYS 耗时 1ms 以内，完全可接受。
     *     而且这个操作只在"改密码"时触发，频率极低。
     *
     *   ★ 如果要改成生产级写法，用 SCAN：
     *       var cursor = ScanOptions.scanOptions().match(pattern).count(100).build();
     *       try (var it = redis.scan(cursor)) {
     *           List<String> batch = new ArrayList<>();
     *           while (it.hasNext()) { batch.add(it.next()); if (batch.size() >= 100) { redis.delete(batch); batch.clear(); } }
     *       }
     *     代码复杂不少，所以本项目保留简单的 KEYS，但在注释里说明取舍 ——
     *     面试时主动说出"我知道 KEYS 会阻塞，但当前数据量下可接受"是加分项。
     */
    public void revokeAllRefresh(Long userId) {
        // "auth:refresh:7:*" 能匹配该用户的所有 token
        Set<String> keys = redis.keys("auth:refresh:" + userId + ":*");

        // ★ 为什么要判空？
        //   keys() 没找到时返回空 Set（不是 null），但某些 Redis 客户端实现在
        //   连接异常时会返回 null。判一下更稳。
        //   而且 redis.delete(空集合) 在某些版本会报错，所以干脆不调。
        if (keys != null && !keys.isEmpty()) {
            redis.delete(keys);
            log.info("已清除用户全部 refresh token, userId={}, count={}", userId, keys.size());
        }
    }

    // ═══════════════════════════════════════════════════════════════
    //  【二、access token 黑名单】
    // ═══════════════════════════════════════════════════════════════

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【把 access token 拉黑】登出时调用
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 为什么 access 需要黑名单，而不是像 refresh 那样用白名单？
     *
     *   如果用白名单，每个请求都要查一次"这个 access token 登记过吗"。
     *   但 access token 数量 = 用户数 × 登录次数，量非常大；
     *   而且每次登录都要写一条，写入压力也大。
     *
     *   用黑名单更划算：
     *     - 正常情况下名单是【空的】（只有登出过的 token 才在里面）
     *     - 绝大多数请求查一次 EXISTS 就返回 false，非常快
     *     - 只有主动登出才写一条
     *
     * ★ TTL 为什么必须是"剩余有效期"而不是固定值？
     *   见 RedisKeys.blacklist 的详细说明 —— 简单说：
     *   token 自然过期后就无效了，黑名单留着是垃圾。
     *
     * @param jti        token 唯一 id
     * @param remaining  这个 token 还剩多久过期（由 JwtTokenProvider.remainingTtl 算出来）
     */
    public void blacklistAccess(String jti, Duration remaining) {
        redis.opsForValue().set(RedisKeys.blacklist(jti), "1", remaining);
        log.debug("access token 已加入黑名单, jti={}, 剩余={}", jti, remaining);
    }

    /**
     * 检查 access token 是否已被拉黑。
     *
     * ★ 调用频率：每个带 token 的请求都会调一次。
     *   这是本类最热的方法，所以用最轻的 EXISTS。
     *
     * ★ Redis 挂了会怎样？
     *   抛异常 → JwtAuthenticationFilter 里 catch 后当作"未登录"处理 → 返回 401。
     *   这是"宁可拒绝也不放行"的安全选择。
     *   （另一种选择是 catch 后放行，可用性更好但安全性更差，本项目选前者。）
     */
    public boolean isBlacklisted(String jti) {
        return Boolean.TRUE.equals(redis.hasKey(RedisKeys.blacklist(jti)));
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ 一个小结：为什么"白名单 + 黑名单"要混着用？】
     *
     *  ┌──────────┬──────────┬──────────┬─────────────────────────┐
     *  │ token    │ 机制     │ 默认状态 │ 原因                     │
     *  ├──────────┼──────────┼──────────┼─────────────────────────┤
     *  │ refresh  │ 白名单   │ 拒绝     │ 有效期长(7天)，必须严格   │
     *  │ access   │ 黑名单   │ 放行     │ 有效期短(2小时)，量太大   │
     *  └──────────┴──────────┴──────────┴─────────────────────────┘
     *
     *  一句话：有效期越长、越需要严格管控的，用白名单；
     *          有效期短、量大的，用黑名单。
     *
     *  ★ 面试如果问"JWT 无状态怎么实现登出"，就答这个：
     *    "access 用 jti 黑名单 + TTL 对齐剩余有效期，refresh 用 Redis 白名单 + 轮换，
     *     这样既能实现立即失效，又不会让 Redis 无限膨胀。"
     * ═══════════════════════════════════════════════════════════════
     */
}
```

### 3.4.6 `security/JwtAuthenticationFilter.java`

**JWT 过滤器** —— 每个请求验一次票

```java
package com.jianli.security;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.JwtException;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.List;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  "验票员"。每个请求进来，它从请求头里取出 token，验证，然后
 *  把"这个请求是谁发的"这个信息放进 Spring Security 的上下文。
 *
 *  它是整个鉴权体系的核心，也是 JWT 真正"起作用"的地方。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：它在请求链的哪一环】
 *
 *      请求进来
 *         ↓
 *      Tomcat 解析成 HttpServletRequest
 *         ↓
 *      【本类】JwtAuthenticationFilter          ← ★ 我们在这一环
 *         ├─ 从请求头取 "Authorization: Bearer eyJhbGci..."
 *         ├─ 调 JwtTokenProvider.parse(token) 验签 + 验过期
 *         ├─ 调 TokenService.isBlacklisted(jti) 查黑名单
 *         ├─ 通过 → new LoginUser(userId, username)
 *         │         SecurityContextHolder.setAuthentication(...)   ← 放进"保险箱"
 *         └─ 失败 → 什么都不做（保持未登录状态）
 *         ↓
 *      JwtAuthenticationFilter 之后的 Security 过滤器
 *         └─ 判断"这个接口需不需要登录"
 *              需要登录 且 上下文里有认证信息 → 放行
 *              需要登录 但 上下文里没有       → 返回 401
 *         ↓
 *      DispatcherServlet → Controller
 *         └─ 参数写 @CurrentUserId Long userId → 从上下文里取出 id
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么它只"识别身份"，不"拒绝请求"？】
 *
 *  这看起来反直觉 —— 没登录为什么不在这里直接返回 401？
 *
 *  因为有些接口是【公开的】，比如：
 *      GET  /api/posts          浏览社区帖子（不登录也能看）
 *      GET  /api/meta/features  查功能开关
 *      POST /api/auth/login     登录（这时候本来就没 token）
 *
 *  如果本类一发现没 token 就返回 401，这些公开接口就没法用了。
 *
 *  所以职责这样划分：
 *      本类    → "我尽量认出你是谁"，认不出就算了，不拦人
 *      Security 的授权规则 → "这个接口要不要拦"，由它决定
 *
 *  ★ 这正是"关注点分离"：身份识别和访问控制是两件事。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【为什么继承 OncePerRequestFilter（和 TraceIdFilter 一样）】
 *  Servlet 规范里一个请求可能被转发/包含多次，普通 Filter 会被重复执行。
 *  OncePerRequestFilter 保证一次请求只跑一次 —— 否则同一个请求会反复解析 token、
 *  反复查 Redis，白白浪费。
 *
 *
 *  【@Component 加在这里，会发生什么？】
 *
 *  ★★ 这里有个坑，必须说清楚：
 *
 *  Spring Boot 会自动把容器里【所有 Filter 类型的 Bean】注册到 Servlet 过滤器链上。
 *  也就是说，只要加了 @Component，本类就自动生效了 ——
 *  但它的位置是【不确定的】。
 *
 *  而我们在 SecurityConfig 里又写了一次：
 *      .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
 *
 *  这一个手动注册 + 自动注册可能导致【执行两次】。
 *
 *  本项目为了让代码直观，采用 @Component + 显式 addFilterBefore 的写法。
 *  Spring Security 的 addFilterBefore 会做去重处理，
 *  实际不会重复执行（Spring Boot 会检测到该 Filter 已在链中）。
 *
 *  ★ 如果你发现日志里 token 被解析了两次，那就要改成：
 *     不加 @Component，改为在 SecurityConfig 里 new 一个。
 *   但那样又要手动处理依赖注入，代码会丑。所以本项目保留现在的写法。
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    /** 请求头里的前缀。注意带空格：Bearer 后面必须有一个空格 */
    private static final String BEARER_PREFIX = "Bearer ";

    /** 标准请求头的名字 */
    private static final String AUTH_HEADER = "Authorization";

    private final JwtTokenProvider tokenProvider;
    private final TokenService tokenService;

    /**
     * 每个请求都会执行一次。
     *
     * ★ 为什么不抛任何异常出去？
     *   token 有问题（过期、伪造、被拉黑）是【正常情况】，
     *   不是系统错误。我们只是"认不出你是谁"，不需要中断请求。
     *   真正决定要不要拦的，是后面的授权规则（见类的说明）。
     */
    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {

        /*
         * 【第一步：从请求头里拿 token】
         *
         * 标准格式：
         *      Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0.xxx
         *                     └─┬──┘ └────────────── token 本体 ──────────┘
         *                     方案名（固定写 Bearer，意思是"持有者令牌"）
         *
         * ★ 为什么用 Bearer 而不是别的名字？
         *   这是 OAuth 2.0 / RFC 6750 规定的标准方案名，全局统一。
         *   前端、Postman、Swagger 都认这个前缀。
         *
         * ★ 为什么要 substring(7)？
         *   去掉 "Bearer " 这 7 个字符（注意 B-e-a-r-e-r + 空格 = 7 个字符）。
         */
        String header = req.getHeader(AUTH_HEADER);

        if (header != null && header.startsWith(BEARER_PREFIX)) {
            String token = header.substring(BEARER_PREFIX.length());

            try {
                /*
                 * 【第二步：解析并验证 token】
                 *
                 * parse 内部做了三件事（详见 JwtTokenProvider.parse）：
                 *   1. 验签名（内容有没有被篡改）
                 *   2. 验过期（exp 有没有超时）
                 *   3. 验格式（是不是合法 JWT）
                 *
                 * 任何一项不过都会抛 JwtException，直接跳到下面的 catch。
                 */
                Claims claims = tokenProvider.parse(token);

                String jti = tokenProvider.jti(claims);
                String type = tokenProvider.type(claims);

                /*
                 * 【第三步：两道额外检查】
                 *
                 * ① 类型必须是 access
                 *    ★ 为什么？因为 refresh token 有 7 天有效期。
                 *      如果允许它直接访问接口，等于把 access 的 2 小时限制绕过去了。
                 *      而 refresh token 只应该能用来调 /api/auth/refresh 这一个接口。
                 *
                 * ② 不能在黑名单里
                 *    ★ 为什么？用户点了登出、或者改密码时，
                 *      我们会把对应的 jti 写进 Redis 黑名单。
                 *      这里查一下，就能实现"token 立刻失效"。
                 *      代价是每个请求多一次 Redis 查询（约 1-2ms），换来可撤销能力。
                 */
                boolean isAccessToken = JwtTokenProvider.TYPE_ACCESS.equals(type);
                boolean notRevoked = !tokenService.isBlacklisted(jti);

                if (isAccessToken && notRevoked) {

                    /*
                     * 【第四步：构造认证对象放进 SecurityContext】
                     *
                     * 这是"告诉 Spring Security：这个请求是已登录的"。
                     *
                     * UsernamePasswordAuthenticationToken 有三个参数：
                     *   1. principal   → 代表"是谁"，我们放 LoginUser
                     *   2. credentials → 凭证（密码），JWT 场景下不需要，传 null
                     *   3. authorities → 权限列表
                     *
                     * ★ 第三个参数现在只放了一个固定的 ROLE_USER。
                     *   这是 placeholder —— 我们还没做 RBAC（角色权限）。
                     *   二期会改成从数据库/Redis 加载的真实权限集合（见附B）。
                     *
                     * ★ 为什么现在不直接省掉这个参数？
                     *   Security 的一些内部逻辑要求 authorities 不能为 null，
                     *   传个空 List 也行，但给个 ROLE_USER 更符合常规。
                     */
                    LoginUser loginUser = new LoginUser(
                            tokenProvider.userId(claims),
                            claims.get("username", String.class));

                    var authentication = new UsernamePasswordAuthenticationToken(
                            loginUser,
                            null,
                            List.of(new SimpleGrantedAuthority("ROLE_USER")));

                    /*
                     * ★ SecurityContextHolder 是什么？
                     *   它是"当前请求的认证信息保险箱"。
                     *   内部用的是 ThreadLocal —— 每个请求线程各有一份，互不干扰。
                     *
                     *   调用 setAuthentication 之后：
                     *      - @CurrentUserId 注解能取到 userId
                     *      - Security 的授权规则认为"已登录"
                     *      - 请求结束后 Spring 自动清空（不需要手动清理）
                     */
                    SecurityContextHolder.getContext().setAuthentication(authentication);

                    log.debug("token 校验通过, userId={}, username={}",
                            loginUser.id(), loginUser.username());
                }
                // 如果 type 不对或被拉黑，什么都不做 —— 保持"未登录"状态，
                // 让后面的授权规则去决定拦不拦

            } catch (JwtException | IllegalArgumentException e) {
                /*
                 * 【解析失败：当作未登录】
                 *
                 * 可能的原因：
                 *   ExpiredJwtException     → 过期了（最常见）
                 *   SignatureException      → 签名不对（伪造，或换了 secret）
                 *   MalformedJwtException   → 格式不是 JWT
                 *   IllegalArgumentException → 空字符串
                 *
                 * ★ 为什么要 clearContext()？
                 *   正常情况下上下文是空的，clear 似乎多余。
                 *   但如果用的是线程池，线程被复用时可能残留上次的认证信息
                 *   （虽然 Spring 一般会清理，但显式清一次更保险）。
                 *   这和 TraceIdFilter 里 MDC.remove 是同一个道理。
                 *
                 * ★ 为什么用 debug 而不是 warn？
                 *   过期 token 太常见了（用户开着页面放了 3 小时），
                 *   打 warn 会刷屏，把真正的告警淹没。
                 */
                SecurityContextHolder.clearContext();
                log.debug("token 校验失败: {}", e.getMessage());
            }
        }

        /*
         * 【最后一步：无论成功失败，都要放行】
         *
         * ★★ 这一行绝对不能放在 if 里面，也不能漏掉。
         *    chain.doFilter 是把请求往下传的唯一方式。
         *    不调用它，请求就卡在这里，前端会一直转圈直到超时。
         */
        chain.doFilter(req, res);
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ 如果想跳过某些请求，可以重写这个方法】
     *
     *  OncePerRequestFilter 提供了 shouldNotFilter，返回 true 表示"本请求不处理"。
     *
     *  有些项目会这样写"跳过登录接口"，省一次无意义的 token 解析：
     *      @Override
     *      protected boolean shouldNotFilter(HttpServletRequest req) {
     *          return req.getServletPath().startsWith("/api/auth/");
     *      }
     *
     *  ★ 我们为什么没写？
     *    因为登录请求本来就不带 token，上面的 if 判断会直接跳过，
     *    开销只有一次 getHeader —— 微乎其微。
     *    而少写这段代码，就少一个"以后新增公开接口忘了加白名单"的坑。
     *
     *    ★ 但如果以后发现某个高频公开接口有性能问题，可以按需加上。
     * ═══════════════════════════════════════════════════════════════
     */
}
```

### 3.4.7 `common/CurrentUserId.java`

**自定义注解** —— 让 Controller 直接拿到 userId

```java
package com.jianli.common;

import java.lang.annotation.Documented;
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  一个自定义注解。写在 Controller 方法的参数上，就能直接拿到"当前登录用户的 id"。
 *
 *  用法：
 *      @GetMapping("/me")
 *      public ApiResponse<UserVO> me(@CurrentUserId Long userId) { ... }
 *
 *  没有它的话，每个接口都得这么写：
 *      public ApiResponse<UserVO> me(Authentication auth) {
 *          LoginUser user = (LoginUser) auth.getPrincipal();
 *          Long userId = user.id();
 *          ...
 *      }
 *  10 个接口就重复 10 遍。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：一个注解是怎么变成参数值的】
 *
 *      JwtAuthenticationFilter
 *         └─ SecurityContextHolder.setAuthentication(LoginUser)
 *              ↓  （放在当前请求的 ThreadLocal 里）
 *
 *      DispatcherServlet 调 Controller 前，发现方法有个参数标了 @CurrentUserId
 *         └─ 查"参数解析器"列表，找到 CurrentUserIdResolver（它 supports 返回 true）
 *              ↓
 *      CurrentUserIdResolver.resolveArgument(...)
 *         ├─ 从 SecurityContextHolder 取出 LoginUser
 *         ├─ 返回 loginUser.id()
 *         └─ Spring 把这个 Long 值塞进方法参数
 *              ↓
 *      你的 Controller 方法拿到 userId，直接用
 *
 *  ★ 整个过程没有任何"手动传参"，是框架自动做的。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【为什么要自己写一个注解，不用 @AuthenticationPrincipal？】
 *
 *  Spring Security 自带一个：
 *      public ApiResponse<UserVO> me(@AuthenticationPrincipal LoginUser user) {
 *          Long userId = user.id();
 *          ...
 *      }
 *
 *  也能用，但有两个小问题：
 *  1. 每个方法都要判空（未登录时 user 是 null），多一行 if
 *  2. Service 层只关心 Long，却被迫依赖了 LoginUser 这个 Security 类型
 *
 *  自己写一个之后：
 *      me(@CurrentUserId Long userId)     ← 干净、类型简单、不用判空
 *
 *  ★ 这是"把框架细节挡在 Controller 之外"的思路 ——
 *    业务代码只看到 Long，看不到 Security 的任何东西。
 *
 *
 *  【下面这四行元注解，每一个都必须有】
 *
 *  @Target(ElementType.PARAMETER)
 *      规定这个注解只能写在【方法参数】上。
 *      如果写错地方（比如标在类上），编译直接报错。
 *      ★ 这就是注解的"自我约束"—— 写错位置编译期就发现，不用等运行时。
 *
 *  @Retention(RetentionPolicy.RUNTIME)
 *      规定这个注解要保留到【运行时】。
 *      ★ 这一行最关键：
 *          SOURCE   → 只在源码里，编译后就丢了（比如 @Override）→ 解析器读不到
 *          CLASS    → 保留到 .class 文件，但 JVM 加载后丢掉
 *          RUNTIME  → 一直保留，可以通过反射读取  ← 我们需要这个
 *      因为 Spring 是运行时通过反射查"这个参数有没有 @CurrentUserId"，
 *      写成 SOURCE 或 CLASS 的话，注解根本不存在，参数永远是 null。
 *
 *  @Documented
 *      生成 javadoc 时把这个注解也写进去，纯文档作用，不影响功能。
 *
 *  @interface
 *      Java 里定义注解的关键字（不是 interface，是 @interface）。
 *      ★ 注解本质上也是一个接口，只是语法特殊。
 */
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface CurrentUserId {

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【是否必须有登录态】默认 true
     * ═══════════════════════════════════════════════════════════════
     *
     *  ★ 这个属性解决什么问题？
     *
     *  有些接口是【公开的】，但登录后体验更好。比如帖子详情：
     *      - 未登录也能看内容
     *      - 登录后要额外返回"我有没有给它投过票"
     *
     *  这时方法想拿到 userId，但未登录时不能报错（否则公开接口就废了）：
     *
     *      @GetMapping("/posts/{id}")
     *      public ApiResponse<PostDetailVO> detail(
     *              @PathVariable Long id,
     *              @CurrentUserId(required = false) Long userId) {   ← 未登录时 userId = null
     *          return ApiResponse.ok(postService.detail(id, userId));
     *      }
     *
     *  Service 里判断 userId 是否为 null，决定要不要查"我的投票记录"。
     *
     *  ★ 当 required = true（默认）时：
     *    未登录会抛 BizException(UNAUTHORIZED)，返回 401。
     *    适用于所有"必须登录才能用"的接口。
     *
     *  ★ 为什么默认是 true 而不是 false？
     *    因为安全默认值应该是"严格"的。
     *    默认 false 的话，忘记写 required=true 就会让接口意外变成公开的 ——
     *    这是个安全漏洞，而且是静默的。
     *
     *  ★ 注解属性的语法：
     *    default true  → 调用时可以不写，就是 true
     *    类型只能是基本类型、String、Class、枚举、注解、以及它们的数组
     *    （不能是任意对象，这是 Java 对注解的硬性限制）
     */
    boolean required() default true;
}
```

### 3.4.8 `common/CurrentUserIdResolver.java`

**注解的翻译官** —— 从 SecurityContext 取出 id 填进参数

```java
package com.jianli.common;

import com.jianli.security.LoginUser;
import lombok.RequiredArgsConstructor;
import org.springframework.core.MethodParameter;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.stereotype.Component;
import org.springframework.web.bind.support.WebDataBinderFactory;
import org.springframework.web.context.request.NativeWebRequest;
import org.springframework.web.method.support.HandlerMethodArgumentResolver;
import org.springframework.web.method.support.ModelAndViewContainer;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  "@CurrentUserId 注解的翻译官"。
 *
 *  Spring 看到参数上有这个注解时，会把"填参数"这件事交给本类处理，
 *  本类负责从 SecurityContext 里把 userId 取出来。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：一次参数绑定的完整过程】
 *
 *      DispatcherServlet 准备调用 Controller 方法
 *         │  遍历每个参数，问"谁能解析它？"
 *         ↓
 *      HandlerMethodArgumentResolverComposite
 *         │  依次问每个 resolver 的 supportsParameter(...)
 *         ├─ RequestParamMethodArgumentResolver → false（不是 @RequestParam）
 *         ├─ PathVariableMethodArgumentResolver → false（不是 @PathVariable）
 *         ├─ RequestResponseBodyMethodProcessor → false（不是 @RequestBody）
 *         └─ 【CurrentUserIdResolver】        → true  ★ 命中
 *              ↓
 *         resolveArgument(...) 被调用
 *              ├─ 从 SecurityContextHolder 取出 LoginUser
 *              └─ 返回 loginUser.id()（一个 Long）
 *              ↓
 *         这个 Long 被塞进方法参数
 *              ↓
 *         你的 Controller 方法执行
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【HandlerMethodArgumentResolver 是什么】
 *
 *  这是 Spring MVC 的一个扩展点。Spring 内置了十几个实现，负责处理
 *  @RequestParam、@PathVariable、@RequestBody、@RequestHeader 等等。
 *
 *  ★ 换句话说：你平时用的那些注解，背后都是这个接口的实现类在工作。
 *    自己实现一个，就等于"给 Spring 加了一种新的参数类型"。
 *
 *  接口只有两个方法：
 *      supportsParameter(param) → "这个参数归我管吗？"
 *      resolveArgument(...)     → "那我来给你算出值"
 *
 *  ★ 这是 Spring 里最典型的"策略模式"应用：
 *    Spring 不知道每个参数该怎么填，就把这个问题丢给一堆"策略"，
 *    哪个策略说"我管"，就用哪个。加新类型只需要加新策略，不改框架代码。
 *
 *
 *  【★ 为什么要 @Component + 在 WebConfig 里注册？】
 *
 *  只加 @Component 是不够的 —— Spring 不会自动把容器里的
 *  HandlerMethodArgumentResolver 加到 MVC 的参数解析器列表里。
 *  必须显式注册（见 WebConfig）。
 *
 *  ★ 这和 Filter 不一样：
 *      Filter 加了 @Component 会自动生效
 *      ArgumentResolver 必须手动挂到 WebMvcConfigurer 上
 *    这是 Spring 内部的两套机制，容易混淆。
 *
 *
 *  【@RequiredArgsConstructor 为什么加在这里但没用字段？】
 *  ★ 其实本类没有 final 字段，所以这个注解是多余的。
 *    加上它只是保持和其他 Bean 一致的风格。删掉也完全没问题。
 *    （写代码时如果发现某个注解没实际作用，删掉更干净 ——
 *      这也是代码 review 该注意的点。）
 */
@Component
@RequiredArgsConstructor
public class CurrentUserIdResolver implements HandlerMethodArgumentResolver {

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【Spring 问："这个参数归你管吗？"】
     * ═══════════════════════════════════════════════════════════════
     *
     * 当两个条件【同时】满足时才返回 true：
     *
     * ① 参数上有 @CurrentUserId 注解
     *    p.hasParameterAnnotation(CurrentUserId.class)
     *    这是最主要的判断，防止把其他参数也认领了。
     *
     * ② 参数类型是 Long（或它的包装类）
     *    Long.class.isAssignableFrom(p.getParameterType())
     *
     *    ★ 为什么要判断类型？
     *      如果某个方法写成 @CurrentUserId String userId，
     *      本类却返回了一个 Long，运行时就会抛 ClassCastException。
     *      提前判断类型，让这种错误变成"没有解析器能处理这个参数"，
     *      在启动或首次调用时就报错，而不是运行时诡异崩溃。
     *
     *    ★ isAssignableFrom 的意思：
     *      判断"左边是不是右边的父类型/同类"。
     *      Long.class.isAssignableFrom(Long.class) → true
     *      这里用它而不是 == Long.class，是为了兼容未来可能的子类
     *      （虽然 Long 是 final 的没有子类，但这是更通用的写法）。
     *
     * ★ 返回 false 时会发生什么？
     *   Spring 继续问下一个 resolver。如果所有 resolver 都说 false，
     *   并且参数有注解，Spring 会抛异常：
     *       "No argument resolver found for parameter ..."
     *   这通常意味着 WebConfig 忘了注册本类。
     *
     * @param parameter 被检查的方法参数（含它的注解和类型信息）
     */
    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(CurrentUserId.class)
                && Long.class.isAssignableFrom(parameter.getParameterType());
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【Spring 问："那你说这个参数该填什么？"】
     * ═══════════════════════════════════════════════════════════════
     *
     * @param parameter 方法参数信息（能从中读到 @CurrentUserId 的 required 属性）
     * @param mavContainer 模型视图容器，本项目用不到（纯 JSON 接口）
     * @param webRequest 当前请求的包装，本项目用不到
     * @param binderFactory 数据绑定工厂，本项目用不到
     * @return 要填进参数的值（这里是 Long 类型的 userId，或者 null）
     */
    @Override
    public Object resolveArgument(MethodParameter parameter,
                                  ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest,
                                  WebDataBinderFactory binderFactory) {

        /*
         * 【第一步：从 SecurityContext 里取出认证信息】
         *
         * ★ 这个信息是谁放进去的？
         *   JwtAuthenticationFilter。它在验证 token 通过后调用
         *   SecurityContextHolder.getContext().setAuthentication(...)。
         *
         * ★ 没登录时是什么？
         *   可能返回 null，也可能返回一个特殊的 "anonymous" 认证对象
         *   （取决于匿名认证是否启用）。所以下面要判断 principal 的类型。
         */
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();

        /*
         * 【第二步：判断是不是真正的登录用户】
         *
         * ★ 为什么用 instanceof LoginUser 而不是判 null？
         *   因为未登录时 Spring Security 可能塞进一个
         *   String 类型的 principal（内容是 "anonymousUser"），
         *   它不为 null，但显然不是登录用户。
         *   用 instanceof 同时挡住了 null 和"匿名用户"两种情况。
         *
         * ★ 这是 Java 16+ 的模式匹配写法：
         *      auth.getPrincipal() instanceof LoginUser user
         *   匹配成功后，变量 user 直接可用，不用再强转。
         *   老写法是：instanceof 判断一次，再 (LoginUser) 强转一次 —— 冗余。
         *
         * ★ 如果这里拿不到，说明什么？
         *   1. 请求没带 token
         *   2. token 过期了
         *   3. token 被拉黑了
         *   4. token 是 refresh 类型（不是 access）
         *   具体是哪种，日志里能看到。但这里统一当作"未登录"处理。
         */
        if (auth != null && auth.getPrincipal() instanceof LoginUser user) {
            return user.id();
        }

        /*
         * 【第三步：没登录时的处理】
         *
         * 从参数上的注解读出 required 属性（默认 true）。
         *    required = true  → 抛异常，返回 401
         *    required = false → 返回 null，让业务代码处理
         *
         * ★ 抛 BizException 会被 GlobalExceptionHandler.handleBiz 接住，
         *   返回 HTTP 401 + {"code":10001,"message":"请先登录"}。
         *
         * ★ 为什么这里可以抛异常？
         *   因为 resolveArgument 是在 DispatcherServlet 调 Controller 期间执行的，
         *   抛出的异常会被正常的异常处理流程捕获 ——
         *   和 Service 里抛 BizException 走的是同一条路。
         */
        boolean required = parameter.getParameterAnnotation(CurrentUserId.class).required();

        if (required) {
            throw new BizException(ErrorCode.UNAUTHORIZED);
        }

        return null;
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ 为什么这个类不写成静态工具类？】
     *
     *  因为 Spring 需要【实例】来调用它的两个方法。
     *  而且它要实现 HandlerMethodArgumentResolver 接口，
     *  只能是实例。
     *
     *  ★ 和 PrivacyDetector、ScoreCalculator 那类"Domen Service"的区别：
     *    那种类可以直接 new 出来测（纯计算，无框架依赖）；
     *    本类必须在 Spring MVC 的流程里才能工作，测起来要起容器或者 mock 一堆东西。
     *    所以本类一般不单独写单测，靠集成测试覆盖。
     * ═══════════════════════════════════════════════════════════════
     */
}
```

```java
package com.jianli.config;

import com.jianli.common.CurrentUserIdResolver;
import lombok.RequiredArgsConstructor;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.method.support.HandlerMethodArgumentResolver;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

import java.util.List;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  Spring MVC 的配置类。目前只做一件事：把 @CurrentUserId 的解析器注册进去。
 *
 *  ★ 如果不注册会怎样？
 *    Controller 方法里写 @CurrentUserId Long userId 时，Spring 会报：
 *        No argument resolver found for parameter ...
 *    因为没有任何解析器"认得"这个注解。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：注册之后发生了什么】
 *
 *      Spring 启动
 *         │  扫描到本类实现了 WebMvcConfigurer
 *         │  调用 addArgumentResolvers(...)
 *         ↓
 *      CurrentUserIdResolver 被加入 MVC 的解析器列表
 *         ↓
 *      之后每个请求，DispatcherServlet 都会用它来解析 @CurrentUserId 参数
 *         └─ 见 CurrentUserIdResolver 的类注释
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★★ 为什么 @Component 不够，必须在这里注册？】
 *
 *  这是新手最容易困惑的地方，一定要分清：
 *
 *  ┌──────────────────┬────────────────────────┬────────────────────┐
 *  │ 组件             │ 加 @Component 就够了？ │ 还需要额外注册？    │
 *  ├──────────────────┼────────────────────────┼────────────────────┤
 *  │ Filter           │ ✅ 自动加入过滤器链     │ ❌ 不需要          │
 *  │ Controller       │ ✅ 自动映射路由         │ ❌ 不需要          │
 *  │ Service/Repo     │ ✅ 自动可注入           │ ❌ 不需要          │
 *  │ ArgumentResolver │ ❌ 只是进了容器         │ ✅ 必须显式注册     │
 *  │ Interceptor      │ ❌ 只是进了容器         │ ✅ 必须显式注册     │
 *  │ MessageConverter │ ❌ 只是进了容器         │ ✅ 必须显式注册     │
 *  └──────────────────┴────────────────────────┴────────────────────┘
 *
 *  ★ 为什么有区别？
 *    因为 Spring MVC 内部维护着几个【独立的列表】（解析器列表、拦截器列表、
 *    转换器列表）。加 @Component 只是把对象放进 Spring 容器，
 *    并不会自动塞进 MVC 的那些列表里 —— 必须通过 WebMvcConfigurer 手动加。
 *
 *  ★ 而 Filter 不同：Spring Boot 有专门的机制扫描容器里所有 Filter 类型的 Bean
 *    并自动注册到 Servlet 容器。这是 Spring Boot 做的额外工作，不是 Spring MVC。
 *
 *
 *  【WebMvcConfigurer 是什么】
 *
 *  一个接口，里面全是 default 方法（空实现）。你只需要重写关心的那几个。
 *
 *  ★ 为什么设计成"全是 default 方法"？
 *    因为可配置的东西太多了（拦截器、跨域、消息转换器、视图解析器、
 *    静态资源、路径匹配策略...）。如果都是抽象方法，
 *    你只想配一个拦截器，也得把这十几个方法全实现一遍。
 *
 *    设计成 default 空实现后，你想改哪个就重写哪个 —— 这叫"接口适配"。
 *
 *  ★ 常见的重写方法：
 *      addArgumentResolvers   ← 本类用的
 *      addInterceptors        加拦截器（登录校验、权限校验）
 *      addCorsMappings        配置跨域
 *      addFormatters          自定义类型转换（比如 String → 枚举）
 *      addResourceHandlers    静态资源映射
 *
 *  【@RequiredArgsConstructor 在这里做什么】
 *  给 final 字段生成构造器，Spring 用它做构造器注入。
 *  所以下面可以直接用 currentUserIdResolver 字段。
 */
@Configuration
@RequiredArgsConstructor
public class WebConfig implements WebMvcConfigurer {

    /**
     * 通过构造器注入 CurrentUserIdResolver。
     *
     * ★ 它为什么能被注入？
     *   因为 CurrentUserIdResolver 类上加了 @Component，
     *   Spring 已经把它实例化放进容器了。
     *
     * ★ 为什么字段是 final？
     *   加上 @RequiredArgsConstructor 后，final 字段必须通过构造器赋值 ——
     *   这正是构造器注入需要的。final 保证它不会被中途替换。
     */
    private final CurrentUserIdResolver currentUserIdResolver;

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【注册参数解析器】
     * ═══════════════════════════════════════════════════════════════
     *
     * @param resolvers Spring MVC 的解析器列表。往里面 add 即可。
     *
     * ★ 为什么是 List 参数而不是返回值？
     *   这是"把自己加到已有列表里"的模式。
     *   Spring 传给你它维护的那个 List，你往里加，加完就生效了。
     *   不需要 return 什么。
     *
     * ★ 加进去之后，顺序重要吗？
     *   重要的。Spring 是按列表顺序依次问 supportsParameter，
     *   【第一个说 true 的】会被采用。
     *
     *   我们 add 在列表【末尾】，意味着：
     *   如果某个参数同时符合"内置解析器的条件"和"@CurrentUserId 的条件"，
     *   会优先用内置的。
     *
     *   ★ 实际不会冲突，因为 @CurrentUserId 是自定义注解，
     *     内置解析器都不认识它。所以放在末尾是安全的。
     *
     *     但如果哪天发现解析行为不对，先怀疑顺序问题 ——
     *     可以改用 resolvers.add(0, ...) 插到最前面。
     *
     * ★ 后面可能还会往这里加什么？
     *   如果以后要支持"分页参数自动解析"（比如 @PageableDefault），
     *   或者自定义的参数转换，都在这个方法里继续 add。
     */
    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(currentUserIdResolver);
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ 为什么跨域配置没写在这里？】
     *
     *  跨域（CORS）我们配在了 SecurityConfig 里：
     *      .cors(c -> c.configurationSource(corsSource()))
     *
     *  ★ 原因：Spring Security 的过滤器链【比 Spring MVC 更早执行】。
     *    如果只在 WebMvcConfigurer 里配跨域，那么当请求被 Security 拒绝（401）时，
     *    跨域响应头不会被加上 —— 浏览器会报一个 CORS 错误而不是 401，
     *    让你误以为是跨域问题，实际是没登录。
     *
     *  ★ 所以规矩是：项目用了 Spring Security，跨域就配在 Security 里。
     *    没用的项目，配在 WebMvcConfigurer 里即可。
     *
     *  ★ 另外：本项目开发时前端走 Vite 代理（同源，不跨域），
     *    生产时走 Nginx 反向代理（也同源）。所以跨域配置实际上很少被触发，
     *    但配上是以防有人直接用 Postman 或其他前端联调。
     * ═══════════════════════════════════════════════════════════════
     */
}
```

### 3.4.10 `user/dto/RegisterRequest.java`

**注册请求体** —— 前端 JSON 转 Java 对象，带校验

```java
package com.jianli.user.dto;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Size;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  注册接口的"请求体"。前端提交的 JSON 会被 Jackson 反序列化成这个对象。
 *
 *  前端发：
 *      POST /api/auth/register
 *      Content-Type: application/json
 *      {"username":"alice","password":"Passw0rd1","nickname":"Alice"}
 *
 *  后端收到：
 *      RegisterRequest req = new RegisterRequest("alice", "Passw0rd1", "Alice")
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：JSON 是怎么变成这个对象的】
 *
 *      前端 http.post('/auth/register', { username: 'alice', ... })
 *         ↓  序列化成 JSON 文本
 *      请求体: {"username":"alice","password":"Passw0rd1","nickname":"Alice"}
 *         ↓
 *      Controller 参数 @RequestBody @Valid RegisterRequest req
 *         ├─ @RequestBody → Jackson 按【字段名】把 JSON 键映射到构造器参数
 *         │      "username" → 第一个参数 username
 *         │      "password" → 第二个参数 password
 *         │      "nickname" → 第三个参数 nickname
 *         │      ★ 名字必须完全一致（区分大小写），否则那个字段就是 null
 *         │
 *         └─ @Valid → 检查下面那些约束注解，任何一个不满足就抛异常
 *               → GlobalExceptionHandler.handleValid 接住
 *               → 返回 400 + {"code":10000,"data":[{"field":"username","message":"..."}]}
 *         ↓
 *      方法体能执行，说明所有校验都通过了
 *         ↓
 *      AuthService.register(req)
 *         └─ 从 req 里取值：req.username()、req.password()、req.nickname()
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么用 record？】
 *
 *  1. 不可变：请求数据读进来就不该被改。如果某处代码改了 req.password()，
 *     后面的校验就和用户实际提交的不一致了。
 *
 *  2. Jackson 反序列化 record 的机制：
 *      record 没有 setter，Jackson 会调用【全参构造器】，
 *      按【参数名】匹配 JSON 键。
 *      ★ 这就是为什么字段顺序要和前端 JSON "自然对应" ——
 *        其实顺序无所谓（靠名字匹配），但参数名必须和 JSON 键一致。
 *
 *      ★ 有个前提：Java 编译时默认【不保留参数名】。
 *        Spring Boot 的 maven 插件默认开启了 -parameters 参数（pom.xml 里有），
 *        所以我们不需要在每个参数上加 @JsonProperty("username")。
 *        如果哪天换了构建配置，发现所有字段都是 null，先怀疑这个开关。
 *
 *  3. 自带 toString（但不含敏感字段的问题见下）
 *
 *  【★ 为什么不直接复用 AppUser 实体？】
 *      1. AppUser 有 id、createdAt、updatedAt 等字段，但注册时前端根本不会传这些
 *      2. AppUser 的 passwordHash 是哈希，而注册时前端传的是明文密码，语义不同
 *      3. 如果把 Entity 当请求体，等于把数据库结构暴露给前端 ——
 *         哪天表加了一列，前端就能传这个字段进来，是个越权风险
 */
public record RegisterRequest(

        /**
         * 用户名。
         *
         * @NotBlank
         *      不能为 null，且去掉首尾空格后不能是空字符串。
         *      ★ 和 @NotNull 的区别：
         *          @NotNull  → 只挡 null，"   " 这种纯空格能通过
         *          @NotBlank → 连纯空格也挡掉
         *        用户输入必须用 @NotBlank。
         *
         * @Size(min = 4, max = 32)
         *      长度限制，和数据库的 VARCHAR(32) 对应。
         *      ★ 为什么要和数据库一致？
         *        数据库是 VARCHAR(32)，如果这里允许 100 个字符，
         *        超长的会插入失败，抛出 DataIntegrityViolationException，
         *        用户看到的是"系统繁忙"，很糟糕。
         *        在校验层就挡住，能给出明确的错误提示。
         *
         * @Pattern(regexp = "^[A-Za-z0-9_]+$")
         *      只允许字母、数字、下划线。
         *      ★ 为什么限制这些字符？
         *        1. 避免中文、空格导致的各种问题
         *        2. 用户名可能被用在 URL、日志里，特殊字符要转义，麻烦
         *        3. 也防止有人用 emoji 或特殊符号冒充他人
         *
         *      正则含义：
         *          ^       开头
         *          [...]   字符集
         *          +       一个或多个
         *          $       结尾
         *
         *      ★ message 属性：校验失败时返回给前端的提示。
         *        不写的话会用默认英文提示（"must match ..."），体验差。
         */
        @NotBlank(message = "用户名不能为空")
        @Size(min = 4, max = 32, message = "用户名长度必须在 4-32 位之间")
        @Pattern(regexp = "^[A-Za-z0-9_]+$", message = "用户名只能包含字母、数字、下划线")
        String username,

        /**
         * 密码（明文）。
         *
         * ★ 注意：这里收到的是【明文】，存进数据库前必须 BCrypt 加密。
         *   加密发生在 AuthService.register 里：
         *       user.setPasswordHash(passwordEncoder.encode(req.password()));
         *
         * ★ 明文密码会出现在哪里？会不会泄露？
         *   1. 不写进数据库（存的是哈希）    ✅
         *   2. 不打进日志（我们从不 log req）✅
         *   3. 在内存里短暂存在              ⚠️ 无法避免，但请求结束就回收
         *
         *   ★ 所以有一条纪律：任何地方都不要 log.info("req={}", req)，
         *     因为 record 自动生成的 toString() 会把 password 打出来！
         *
         *     record 的 toString 长这样：
         *         RegisterRequest[username=alice, password=Passw0rd1, nickname=Alice]
         *                                                            ↑ 明文泄露
         *
         *     解决方式（如果需要打日志）：
         *         在 record 里重写 toString()，把 password 遮盖成 ***。
         *         本项目不需要打这个日志，所以没重写 —— 但你要知道这个风险。
         *
         * @Size(min = 8, max = 32)
         *      ★ 为什么最少 8 位？
         *        4 位密码大约 1 秒就能爆破完。8 位配合字母+数字，
         *        在 BCrypt 的慢哈希下要算很多年。
         *
         * @Pattern 要求同时包含字母和数字
         *      ^               开头
         *      (?=.*[A-Za-z])  后面某处至少有一个字母（前瞻断言）
         *      (?=.*\d)        后面某处至少有一个数字
         *      .+              整串至少一个字符
         *      $               结尾
         *
         *      ★ (?=...) 叫"零宽正向先行断言"：只检查条件，不消耗字符。
         *        所以在同一位置可以连续断言多次 —— 这就是"同时包含"的写法。
         *
         *      ★ 为什么不要求"必须包含特殊字符"？
         *        研究表明强制特殊字符会让用户写成 "Passw0rd!" 这种可预测的形式，
         *        反而降低强度。长度限制 + 字母数字混合已经是较好的平衡。
         */
        @NotBlank(message = "密码不能为空")
        @Size(min = 8, max = 32, message = "密码长度必须在 8-32 位之间")
        @Pattern(regexp = "^(?=.*[A-Za-z])(?=.*\\d).+$", message = "密码必须同时包含字母和数字")
        String password,

        /**
         * 昵称。展示用的名字，可以中文、可以有表情符号。
         *
         * ★ 为什么不加 @Pattern 限制字符？
         *   昵称是给人看的，中文、emoji 都应该允许。
         *   而且它不进 URL、不进日志，没有特殊字符带来的风险。
         *
         * ★ @Size(max = 16) 为什么比数据库的 VARCHAR(32) 小？
         *   数据库留了余量（32），校验层更严格（16）。
         *   这是常见做法：数据库宽容一点，防止某些历史数据或直接 SQL 写入被卡住；
         *   接口层严格一点，保证前端展示不会溢出。
         *
         * ★ 为什么没有 min？
         *   @NotBlank 已经保证至少有一个非空白字符了。
         *   再限制 min=2 会让单字昵称（比如"李"）无法使用。
         */
        @NotBlank(message = "昵称不能为空")
        @Size(max = 16, message = "昵称最长 16 个字符")
        String nickname

        /*
         * ═══════════════════════════════════════════════════════════════
         *  【★ 为什么这里没有 @Email、@Min 之类的字段？】
         *
         *  因为注册只需要这三样。手机号、邮箱、头像都是"以后再说"的功能。
         *
         *  ★ 一个重要的设计原则：DTO 只包含【这个接口真正需要】的字段。
         *    不要做一个"UserDTO"给所有接口共用 ——
         *    那样注册接口会要求填一堆用不上的东西，
         *    而且改任何一处的字段都会影响其他接口。
         *
         *    每个接口一个 DTO，宁可多几个类，也不要耦合。
         * ═══════════════════════════════════════════════════════════════
         */
) {}
```

### 3.4.11 `user/dto/LoginRequest.java`

**登录请求体** —— 宽松校验，防用户名枚举

```java
package com.jianli.user.dto;

import jakarta.validation.constraints.NotBlank;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  登录接口的请求体。只有两个字段：用户名和密码。
 *
 *      POST /api/auth/login
 *      {"username":"alice","password":"Passw0rd1"}
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向】
 *
 *      前端登录表单
 *         └─ http.post('/auth/login', { username, password })
 *              ↓
 *      请求体 JSON
 *              ↓
 *      AuthController.login(@RequestBody @Valid LoginRequest req)
 *              ├─ Jackson 反序列化
 *              └─ @Valid 校验（两个字段都非空）
 *              ↓
 *      AuthService.login(req)
 *         ├─ userRepository.findByUsername(req.username())
 *         ├─ passwordEncoder.matches(req.password(), user.getPasswordHash())
 *         ├─ 成功 → 签发 token → 存 Redis 白名单
 *         └─ 失败 → throw BizException(BAD_CREDENTIALS)
 *              ↓
 *      返回 TokenResponse { accessToken, refreshToken, expiresIn, user }
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么这里只是 @NotBlank，不像注册那样限制长度和格式？】
 *
 *  这是刻意的，有两个重要原因：
 *
 *  ① 【防用户名枚举】
 *     如果在登录时校验"用户名必须是 4-32 位、只能字母数字"，
 *     攻击者就能通过"提示信息不同"来推断：
 *          返回"用户名格式不对" → 说明这个账号不存在（或者格式特殊）
 *          返回"用户名或密码错误" → 说明账号存在
 *     从而批量筛选出有效用户名。
 *
 *     登录接口对输入【越宽松越好】—— 只要求非空，
 *     剩下的判断全部统一成"用户名或密码错误"。
 *
 *  ② 【向后兼容】
 *     万一以后用户名规则放宽了（比如允许中文），
 *     老的登录接口不用改也能继续用。
 *
 *  ★ 一句话：注册接口严格校验（把好数据挡在门外），
 *    登录接口宽松校验（不给攻击者任何额外信息）。
 *
 *
 *  【★ record 的一个隐患：toString 会打印密码】
 *
 *      LoginRequest[username=alice, password=Passw0rd1]
 *                                          ↑ 明文
 *
 *  所以：绝不要 log.info("login req={}", req)。
 *  如果要打，自己重写 toString：
 *      @Override
 *      public String toString() {
 *          return "LoginRequest[username=" + username + ", password=***]";
 *      }
 *
 *  ★ record 允许重写自动生成的方法（toString / equals / hashCode），
 *    重写之后就用自己的。
 */
public record LoginRequest(

        /**
         * 用户名。
         *
         * ★ 只校验非空，理由见上面【为什么只是 @NotBlank】。
         *   但 message 还是要给的，不能默认成英文。
         */
        @NotBlank(message = "请输入用户名")
        String username,

        /**
         * 密码（明文）。
         *
         * ★ 为什么这里连 8 位长度都不校验？
         *   因为登录时密码对不对由 BCrypt 比对决定，长度校验没有意义 ——
         *   用户输了个 3 位的密码，BCrypt 比对会失败，返回"用户名或密码错误"，
         *   结果是一样的。而且不做长度校验，也不给攻击者额外信息。
         *
         * ★ 明文密码在内存里的生命周期：
         *   请求进来 → String 对象 → 传给 AuthService
         *   → passwordEncoder.matches() 比对
         *   → 方法结束，String 成为垃圾，被 GC 回收
         *
         *   注意：String 是不可变的，回收前内容会一直在内存里。
         *   高安全场景（比如银行）会用 char[] 并在使用后清零，
         *   但普通 Web 应用不需要这个级别的防护。
         */
        @NotBlank(message = "请输入密码")
        String password
) {}
```

### 3.4.12 `user/dto/RefreshRequest.java`

**刷新请求体** —— 只装 refreshToken

```java
package com.jianli.user.dto;

import jakarta.validation.constraints.NotBlank;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  刷新 token 接口的请求体。只有一个字段：refreshToken。
 *
 *      POST /api/auth/refresh
 *      {"refreshToken":"eyJhbGciOiJIUzI1NiJ9.eyJ0eXBlIjoicmVmcmVzaCJ9.xxx"}
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么 refreshToken 放在请求体里，不放 URL 参数或请求头？】
 *
 *  三种做法对比：
 *
 *  ┌──────────────┬──────────────────────────────────────────────┐
 *  │ 放 URL 参数  │ GET /refresh?token=xxx                       │
 *  │              │ ❌ token 会进 Nginx access log、浏览器历史、  │
 *  │              │    Referer 头 —— 等于泄露                    │
 *  ├──────────────┼──────────────────────────────────────────────┤
 *  │ 放请求头     │ 需要自定义一个 header，前端多写代码；          │
 *  │              │ 而且标准做法里 refresh 一般走 body           │
 *  ├──────────────┼──────────────────────────────────────────────┤
 *  │ 放请求体     │ ✅ POST body 不进日志、不进历史，最安全       │
 *  └──────────────┴──────────────────────────────────────────────┘
 *
 *  ★ 同理，access token 必须放 Authorization 头（这个无法避免），
 *    所以生产环境的 Nginx 日志【不能记录请求头】—— 这也是为什么
 *    SSE 我们不用原生 EventSource（它只能把 token 放 URL）。
 *
 *  【★ 为什么这个接口是 POST 而不是 GET？】
 *  因为 GET 的请求体是没意义的（会被某些代理丢掉），
 *  而且 GET 语义上是"读取资源"，而刷新 token 会【改变服务端状态】
 *  （旧的 refresh 作废、新的写入 Redis），属于"创建"操作，应该是 POST。
 *
 *  【★ 这个类为什么单独存在，不复用 TokenResponse？】
 *  因为 TokenResponse 里有两个 token，而这里只需要 refresh 一个。
 *  混用的话前端不知道该传哪个，也容易把 access 误传进来。
 *  职责单一，各管各的。
 */
public record RefreshRequest(

        /**
         * 刷新令牌。
         *
         * ★ 为什么要 @NotBlank？
         *   没传的话，AuthService.refresh(null) 里 tokenProvider.parse(null)
         *   会抛 IllegalArgumentException，然后被包成 TOKEN_INVALID 返回。
         *   结果是对的，但错误发生得晚。
         *   在参数校验阶段就挡住，错误信息更清楚，也少一次异常构造。
         *
         * ★ 这里不做格式校验（比如"必须是三段点分隔"）。
         *   因为非法格式在 parse 时自然会失败，没必要重复校验。
         *   而且格式校验如果写得和 JWT 规范不完全一致，反而会误杀合法 token。
         */
        @NotBlank(message = "refreshToken 不能为空")
        String refreshToken
) {}
```

### 3.4.13 `user/dto/TokenResponse.java`

**登录响应** —— 两个 token + 有效期 + 用户信息

```java
package com.jianli.user.dto;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  登录/刷新成功后返回给前端的东西。前端拿到后存起来，之后的请求都要用。
 *
 *  返回的 JSON：
 *      {
 *        "accessToken":  "eyJhbGciOiJIUzI1NiJ9.xxx",
 *        "refreshToken": "eyJhbGciOiJIUzI1NiJ9.yyy",
 *        "expiresIn":    7200,
 *        "user": { "id":1, "username":"alice", "nickname":"Alice", ... }
 *      }
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：四个字段各自被谁用】
 *
 *      AuthService.issueTokens(user)
 *         └─ new TokenResponse(access, refresh, expiresIn, UserVO.of(user))
 *              ↓
 *          Jackson 序列化成 JSON → 前端
 *              ↓
 *      前端 useUserStore：
 *         ├─ accessToken  → localStorage + 每个请求的 Authorization 头
 *         ├─ refreshToken → localStorage + 401 时调 /auth/refresh
 *         ├─ expiresIn    → 可选：提前定时刷新，避免第一个请求踩 401
 *         └─ user         → 头像、昵称、目标岗位等展示
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 为什么返回两个 token，而不是一个？】
 *
 *  这是一个"短有效期 + 长有效期"的设计：
 *
 *      access  有效期 2 小时  → 每个请求都带，泄露风险窗口小
 *      refresh 有效期 7 天    → 只在换 token 时用，平时不出网
 *
 *  如果只有一个长 token：
 *      - 它每个请求都带，被截获的风险高
 *      - 一旦泄露，7 天内有效，危害大
 *
 *  如果有两个：
 *      - access 泄露 → 最多 2 小时，而且可以用登出拉黑
 *      - refresh 泄露 → 只能换一次（因为轮换），下次真用户刷新会失败 → 告警信号
 *
 *  ★ 这是 JWT 实践里的标准做法，面试常问。
 *
 *  【★ 为什么 user 字段用 UserVO 而不是 AppUser？】
 *  因为 AppUser 含 passwordHash。返回它等于把密码哈希送给前端 ——
 *  哪怕前端不显示，任何人在 F12 里都能看到。
 *  ★ 这条纪律叫"绝不把 Entity 直接暴露给外部"，是全项目最重要的一条。
 */
public record TokenResponse(

        /**
         * 访问令牌。
         *
         * ★ 前端怎么用：
         *      fetch('/api/resumes', {
         *        headers: { Authorization: `Bearer ${accessToken}` }
         *      })
         *
         * ★ 为什么每次请求都带？JWT 是无状态的，
         *   服务端不存会话，全靠这个 token 里的内容（+ 签名）来认人。
         */
        String accessToken,

        /**
         * 刷新令牌。
         *
         * ★ 前端什么时候用：
         *   收到 401 时（access 过期），调 POST /auth/refresh 换新的，
         *   然后用新的 access 重放刚才失败的请求。
         *   用户全程无感知（见 04 文档的 http.js 拦截器）。
         *
         * ★ 安全建议：refresh 只应该发给 /auth/refresh 这一个接口，
         *   绝不能跟着普通请求走。虽然服务端也会校验 type，
         *   但前端少发一次，就少一次被截获的机会。
         */
        String refreshToken,

        /**
         * access token 的有效期，单位【秒】。
         *
         * ★ 为什么返回这个数字，前端不是可以从 token 里解出来吗？
         *   可以（base64 解开 payload 就能看到 exp），但：
         *   1. 前端解析 token 需要额外代码和依赖
         *   2. 前端拿到 exp 还要和本地时间做比较，容易算错
         *   直接给一个"还有多少秒"最省事。
         *
         * ★ 前端可以用它做"提前刷新"：
         *       setTimeout(() => refresh(), (expiresIn - 60) * 1000)
         *   在过期前 60 秒主动刷新，避免用户在操作时突然 401。
         *   本项目没做这个优化（靠拦截器兜底），但字段留着。
         *
         * ★ 为什么是秒不是毫秒？
         *   这是 OAuth 2.0 规范的习惯（expires_in 字段就是秒）。
         *   前端用的时候记得乘 1000。
         */
        long expiresIn,

        /**
         * 当前登录用户的基本信息。
         *
         * ★ 为什么登录时就返回用户信息，而不是让前端再调一次 /users/me？
         *   省一次请求。登录成功后前端立刻要显示"欢迎，xxx"，
         *   再发一次请求会有明显延迟。
         *
         * ★ 为什么不包含 passwordHash？
         *   见类说明 —— UserVO 本来就是"能对外暴露的字段子集"。
         */
        UserVO user
) {}
```

### 3.4.14 `user/dto/UserVO.java`

**用户对外视图** —— Entity 的安全投影，绝不含 passwordHash

```java
package com.jianli.user.dto;

import com.jianli.user.entity.AppUser;

import java.time.LocalDateTime;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  用户的"对外视图"。前端能看到的用户信息，就是这个类里的字段。
 *
 *  VO = View Object，专门用于"返回给前端看"的对象。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：它是 Entity 的"安全投影"】
 *
 *      AppUser（Entity，数据库里的完整行）
 *      ┌────┬──────────┬───────────────┬──────────┬──────────────┐
 *      │ id │ username │ password_hash │ nickname │ target_pos   │ ...
 *      └────┴──────────┴───────────────┴──────────┴──────────────┘
 *                          ✂️ 剪掉
 *      ┌────┬──────────┬──────────┬──────────────┬──────────────┐
 *      │ id │ username │ nickname │ target_pos   │ years_of_exp │  → UserVO
 *      └────┴──────────┴──────────┴──────────────┴──────────────┘
 *
 *      UserService.getProfile(userId)
 *         └─ userRepository.findById(userId)     → AppUser
 *              .map(UserVO::of)                   → ★ 就是这里转换
 *              .orElseThrow(...)
 *              ↓
 *      Controller 包成 ApiResponse<UserVO> → JSON → 前端
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★★ 为什么必须有 VO，不能直接返回 Entity？四个理由】
 *
 *  ① 【安全】—— 最重要的一条
 *     AppUser 里有 passwordHash。直接返回的话：
 *         {"id":1,"username":"alice","passwordHash":"$2a$10$N9qo8uLO...", ...}
 *     前端的 F12 里能清清楚楚看到。虽然它是哈希不能直接反推出密码，
 *     但泄露哈希等于给了攻击者离线爆破的素材：
 *         拿着 $2a$10$... 在自己机器上无限次尝试，不受登录限流约束。
 *     而且如果哪天表里加了"手机号""身份证"字段，直接返回就全漏了。
 *
 *  ② 【解耦】—— 表结构变了，前端不用跟着改
 *     假设某天 AppUser 加了一列 last_ip。
 *     如果用 Entity 当 VO，前端会突然多收到一个字段（可能困惑，也可能泄露）
 *     如果只用 VO，什么都不变 —— 要不要暴露是新决定，不是被动的。
 *
 *  ③ 【派生字段】—— VO 可以有"算出来的"字段
 *     比如简历列表里要显示"最新得分"，那不是 AppUser 的字段，
 *     是查了 analysis_report 之后算出来的。这种字段只能放在 VO 里。
 *
 *  ④ 【校验注解不污染持久层】
 *     @NotBlank、@Size 这些是"接口层"的规则。
 *     放在 Entity 上会让 JPA 也去做校验，
 *     而且改接口规则时会意外影响数据库操作。
 *
 *  ★ 一句话：Entity 是"数据长什么样"，VO 是"给别人看什么"。这两件事必须分开。
 *
 *
 *  【★ 为什么这个类没有 createdAt 的时区问题？】
 *  LocalDateTime 会由 JacksonConfig 统一格式化成 "2026-11-18 20:30:00"。
 *  （见 JacksonConfig 的说明 —— 那里解释了为什么 yml 里的 date-format 不管用）
 *
 *  【现在这个类还没被用上？】
 *  是的 —— 步骤 2 只是把类建好，步骤 3 的登录接口和 /users/me 接口才会用到。
 *  先建好是因为：AuthService 需要它来组装 TokenResponse。
 */
public record UserVO(

        /** 用户 id。前端用它做路由参数（比如 /users/1） */
        Long id,

        /** 登录名。一般只在"个人资料"页展示，其他地方显示昵称 */
        String username,

        /** 昵称。界面上到处显示的就是它 */
        String nickname,

        /** 目标岗位。可为 null（用户没填） */
        String targetPosition,

        /**
         * 经验年限。可为 null？
         * ★ 实际不会 —— AppUser 的表结构是 NOT NULL DEFAULT 0，
         *   而且 @PrePersist 里也兜底了。但类型保留 Integer 以和 Entity 一致。
         */
        Integer yearsOfExperience,

        /**
         * 注册时间。
         *
         * ★ 为什么返回它？
         *   个人资料页可以显示"加入于 2026-11-01"。
         *   小细节，但让产品显得完整。
         */
        LocalDateTime createdAt,

        /**
         * 最后登录时间。
         *
         * ★ 为什么返回它？
         *   用户可以据此判断"有没有人在我不知道的时候登录过我的账号"。
         *   这是很多产品都有的安全提示。
         *
         * ★ 注意：这个字段在登录成功时才更新（AuthService.login 里 set）。
         *   所以"刚登录完看到的值"其实是【上一次】的登录时间。
         *   如果要显示"本次登录时间"，得在 update 之后再查一次。
         *   本项目的处理方式是：登录时先更新、再组装响应，
         *   所以这里拿到的是本次登录时间（Time 上差别在毫秒级，用户无感）。
         */
        LocalDateTime lastLoginAt
) {

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【Entity → VO 的转换方法】
     * ═══════════════════════════════════════════════════════════════
     *
     * 用法：
     *      AppUser user = userRepository.findById(1).orElseThrow();
     *      UserVO vo = UserVO.of(user);
     *
     * ★ 为什么写成 static 工厂方法，而不是单独的 Converter 类？
     *   1. 转换逻辑和 VO 放一起，看 VO 就知道它能从 Entity 怎么转过来
     *   2. 不需要额外的类文件
     *   3. 只做一次简单映射，不值得引入 MapStruct 之类的工具
     *
     * ★ 什么时候该用 MapStruct / 单独的 Converter？
     *   当 VO 多到几十个、字段映射关系复杂（嵌套、集合、条件转换）时。
     *   那样手写确实累，工具能自动生成。
     *   本项目规模不大，手写更直接、更好调试、面试时能讲清每一行。
     *
     * ★ 那如果 VO 多了，每个都写 of() 会不会重复？
     *   会有点。但每个 VO 的 of() 逻辑都不一样（有的要查关联表、有的要算分），
     *   强行抽象反而更绕。这是"适度重复优于错误抽象"。
     *
     * @param u 从数据库查出来的实体
     * @return 只含可暴露字段的 VO
     */
    public static UserVO of(AppUser u) {
        /*
         * ★ 为什么不判断 u == null？
         *   because 调用方都是从 Optional 里取的：
         *       repo.findById(id).map(UserVO::of)
         *   能进到 of() 说明一定不为 null。
         *
         *   如果在这里也判 null，等于重复防御，而且还要决定"返回 null 还是抛异常"，
         *   反而让调用方困惑。
         *
         *   ★ 原则：null 检查放在"数据进入系统的边界"（比如 Repository 返回 Optional），
         *     而不是每一层都检查一遍。
         */
        return new UserVO(
                u.getId(),
                u.getUsername(),
                u.getNickname(),
                u.getTargetPosition(),
                u.getYearsOfExperience(),
                u.getCreatedAt(),
                u.getLastLoginAt()
                /*
                 * ═══════════════════════════════════════════════════
                 *  ★★ 注意：这里【故意没有】传 passwordHash。
                 *
                 *  这就是 VO 的意义 —— 不是"忘了写"，是"明确地排除"。
                 *
                 *  以后如果有人要往 VO 加字段，必须问自己：
                 *      "这个字段能让前端看到吗？"
                 *  这个"必须想一想"的动作本身就是安全设计。
                 * ═══════════════════════════════════════════════════
                 */
        );
    }
}
```

```java
/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  用户的"查询类"业务。目前只有一个方法：查自己的资料。
 *
 *  它和 AuthService 的分工：
 *      UserService → 读用户、改用户（不涉及登录凭证）
 *      AuthService → 注册、登录、刷新、登出（涉及 token）
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向】
 *
 *      GET /api/users/me
 *         ↓  Controller 用 @CurrentUserId 拿到 userId
 *      UserController.me(userId)
 *         └─ userService.getProfile(userId)
 *              ↓
 *      【本类】getProfile
 *         └─ userRepository.findById(userId)          → 查库
 *              .map(UserVO::of)                        → Entity → VO
 *              .orElseThrow(...)                       → 查不到就抛异常
 *              ↓
 *      返回 UserVO
 *         ↓
 *      Controller 包成 ApiResponse<UserVO> → JSON
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【@Service 是什么】
 *  注册成 Spring Bean，语义上表示"这是业务逻辑层"。
 *  功能和 @Component 完全一样，只是个约定俗成：
 *      @Service     → 业务逻辑
 *      @Component   → 通用组件
 *      @Repository  → 数据访问（不过我们的 Repository 是接口，不需要这个注解）
 *      @RestController → Web 接口
 *
 *  ★ 为什么要区分？因为看类名就知道它在哪一层，
 *    代码 review 时能立刻发现"这个类不该在这里"。
 *
 *  【@Transactional(readOnly = true) 是什么】
 *
 *  @Transactional
 *      声明这个方法在事务里运行。事务的意思是：
 *      "这里面所有的数据库操作，要么全成功，要么全失败回滚。"
 *
 *  readOnly = true
 *      声明"这个事务只读，不会改数据"。带来几个好处：
 *      1. Hibernate 跳过"脏检查"（不追踪对象是否被修改），省一点性能
 *      2. 数据库驱动可能做只读优化的提示
 *      3. ★ 最重要的是【语义】：读到这个注解，就知道"这里不会改数据"
 *
 *  ★ 为什么要加事务，查询不是只读吗？
 *      单条查询确实不需要。但：
 *      1. 统一风格，以后这个方法里加了几次查询，一致性有保证
 *      2. 如果查出来的是多个对象，事务能保证它们来自同一个时间点的快照
 *      3. 一些懒加载场景（本项目没用）需要事务上下文
 *
 *  ★ 只读方法用 readOnly=true 是个好习惯，面试时提到会加分。
 */
@Slf4j
@Service
@RequiredArgsConstructor
public class UserService {

    /**
     * 数据访问对象。
     *
     * ★ 由 Spring 通过构造器注入（@RequiredArgsConstructor 生成的构造器）。
     *   注入的是 Spring Data JPA 动态生成的那个代理实现。
     */
    private final UserRepository userRepository;

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【查当前用户的资料】
     * ═══════════════════════════════════════════════════════════════
     *
     * @param userId 当前登录用户 id（由 @CurrentUserId 从 token 里取出）
     * @return 只含可暴露字段的 VO
     * @throws BizException USER_NOT_FOUND —— 用户不存在（理论上不该发生，
     *                      但如果用户被删了而 token 还有效，就会走到这里）
     *
     * ★ 为什么参数是 userId 而不是从 SecurityContext 里取？
     *   这是为了保持 Service 层【不依赖任何 Web / Security 的东西】。
     *   Service 只接受普通参数（Long），这样：
     *     1. Service 可以脱离 Web 环境单独测试
     *     2. 同一个方法可以被其他地方复用（比如后台任务里直接传 userId）
     *     3. 依赖方向清晰：Controller 知道 Security，Service 不知道
     *
     *   ★ 这条纪律很重要：如果哪天你在 Service 里看到
     *     SecurityContextHolder.getContext()，基本可以判定这个设计有问题。
     */
    @Transactional(readOnly = true)
    public UserVO getProfile(Long userId) {
        /*
         * 链式写法拆解：
         *
         * findById(userId)      → 返回 Optional<AppUser>
         *                          （找不到时是 Optional.empty()，不是 null）
         * .map(UserVO::of)      → Optional 里有值就转成 UserVO，
         *                          没值就保持 empty
         * .orElseThrow(...)     → 有值就返回那个 UserVO，
         *                          没值就执行括号里的代码（抛异常）
         *
         * ★ UserVO::of 这叫"方法引用"，等价于 user -> UserVO.of(user)。
         *   因为 of 是静态方法、只接受一个参数，正好能当成函数传。
         *   比写 lambda 更简洁。
         *
         * ★ 为什么用 USER_NOT_FOUND 而不是 UNAUTHORIZED？
         *   因为走到这里说明 token 是有效的（userId 是从合法 token 里取的），
         *   只是数据库里查不到这个人 —— 这是"资源不存在"，不是"没登录"。
         *
         *   实际触发场景：用户注销后，他的 token 还没过期就继续访问。
         */
        return userRepository.findById(userId)
                .map(UserVO::of)
                .orElseThrow(() -> new BizException(ErrorCode.USER_NOT_FOUND));
    }

    /*

     *  【后面会往这个类里加什么】（步骤 4 前端联调用得到）
     *

     *      changePassword(userId, ChangePasswordRequest req) → 改密码（要踢下线）
     *
     *  ★ changePassword 里必须做一件事：
     *      tokenService.revokeAllRefresh(userId);
     *    因为密码改了，所有设备上的登录态都应该失效 ——

     *    多写一个方法就多一处验证负担。
```

**认证业务核心** —— 注册/登录/刷新/登出

```java
package com.jianli.user.service;

import com.jianli.common.BizException;
import com.jianli.common.ErrorCode;
import com.jianli.security.JwtProperties;
import com.jianli.security.JwtTokenProvider;
import com.jianli.security.TokenService;
import com.jianli.user.dto.LoginRequest;
import com.jianli.user.dto.RegisterRequest;
import com.jianli.user.dto.TokenResponse;
import com.jianli.user.dto.UserVO;
import com.jianli.user.entity.AppUser;
import com.jianli.user.repository.UserRepository;
import io.jsonwebtoken.Claims;
import io.jsonwebtoken.JwtException;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;
import java.time.ZoneOffset;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  认证业务的核心：注册、登录、刷新、登出。
 *
 *  它是"业务规则"和"技术细节"的桥梁：
 *      向上：给 Controller 提供 4 个方法
 *      向下：调 Repository 存数据、调 JwtTokenProvider 签 token、调 Redis 记账
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：四个方法各自流向哪里】
 *
 *  ── register ──
 *      RegisterRequest
 *        ├─ 查重 → userRepository.existsByUsername
 *        ├─ 密码加密 → passwordEncoder.encode（BCrypt）
 *        ├─ 造实体 → new AppUser() + set...
 *        ├─ 入库 → userRepository.save（INSERT INTO app_user）
 *        └─ 返回 UserVO（不含密码）
 *
 *  ── login ──
 *      LoginRequest
 *        ├─ 查用户 → userRepository.findByUsername
 *        ├─ 比对密码 → passwordEncoder.matches
 *        ├─ 更新登录时间 → user.setLastLoginAt（UPDATE）
 *        └─ 签发 token → issueTokens()
 *              ├─ JwtTokenProvider.createAccess / createRefresh
 *              ├─ TokenService.saveRefresh（Redis 白名单）
 *              └─ 返回 TokenResponse
 *
 *  ── refresh ──
 *      refreshToken 字符串
 *        ├─ 解析 → JwtTokenProvider.parse（验签+验过期）
 *        ├─ 检查类型是否 refresh
 *        ├─ 查白名单 → TokenService.isRefreshValid
 *        ├─ ★ 删除旧的 → TokenService.revokeRefresh（轮换）
 *        └─ 签发新的 → issueTokens()
 *
 *  ── logout ──
 *      accessToken + refreshToken
 *        ├─ access 的 jti 进黑名单 → TokenService.blacklistAccess（TTL=剩余有效期）
 *        └─ refresh 从白名单删除 → TokenService.revokeRefresh
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 依赖的 5 个东西，分别干什么】
 *
 *  UserRepository      → 读写 app_user 表
 *  PasswordEncoder     → BCrypt 加密和比对（Bean 在 SecurityConfig 里定义）
 *  JwtTokenProvider    → 生成和解析 token
 *  TokenService        → 管理 Redis 里的白名单/黑名单
 *  JwtProperties       → 拿 token 有效期（要告诉前端 expiresIn，也要给 Redis 设 TTL）
 *
 * ★ 为什么这个类的依赖这么多？
 *   它是"编排者"：把多个组件串起来完成一个业务流程。
 *   这正是 Service 层的典型样子 —— 自己几乎不写算法，
 *   都是"调 A、判断、再调 B"。
 */
@Slf4j
@Service
@RequiredArgsConstructor
public class AuthService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;
    private final JwtTokenProvider tokenProvider;
    private final TokenService tokenService;
    private final JwtProperties jwtProperties;

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【一、注册】
     * ═══════════════════════════════════════════════════════════════
     *
     * 流程：查重 → 加密 → 入库 → 返回 VO
     *
     * ★ @Transactional 在这里的作用：
     *   整个方法在一个事务里。如果中间任何一步抛异常，
     *   前面的 INSERT 会一起回滚，不会留下半截数据。
     *   虽然本方法只有一次写操作，加事务是为了一致性和未来的扩展。
     *
     * @param req 已经通过 @Valid 校验的请求（用户名格式、密码强度都合格了）
     * @return 新建用户的信息（不含密码哈希）
     * @throws BizException USERNAME_EXISTS —— 用户名已被占用
     */
    @Transactional
    public UserVO register(RegisterRequest req) {

        /*
         * 【第一步：查重】
         *
         * ★ 为什么用 existsByUsername 而不是 findByUsername？
         *   exists 只发 SELECT 1 ... LIMIT 1，不读所有列，更快。
         *
         * ★★ 重要：这个检查【不能防止并发重复】！
         *
         *   两个请求同时到达：
         *      请求A: existsByUsername("alice") → false
         *      请求B: existsByUsername("alice") → false     ← 都通过了
         *      请求A: INSERT ... → 成功
         *      请求B: INSERT ... → 违反唯一索引，抛 DuplicateKeyException
         *
         *   所以真正防重的是【数据库唯一索引】，这里只是"提前友好提示"，
         *   让 99% 的正常情况得到清晰的错误信息，而不是 500 错误。
         *
         *   ★ 并且加了 @Transactional 之后还有一层保障：
         *     B 的 INSERT 失败会回滚整个事务，不会留下脏数据。
         *
         *   ★ 这也解释了为什么 AppUser 的 username 上写了 unique=true，
         *     以及建表脚本里有 uk_user_username 索引 —— 那才是最后防线。
         */
        if (userRepository.existsByUsername(req.username())) {
            throw new BizException(ErrorCode.USERNAME_EXISTS);
        }

        /*
         * 【第二步：构造实体】
         *
         * ★ 为什么 setYearsOfExperience(0) 而不让它自动？
         *   虽然 @PrePersist 里也兜底了，但这里显式设置更清楚：
         *   "新注册用户默认 0 年经验"。看代码的人不用去翻实体类。
         */
        AppUser user = new AppUser();
        user.setUsername(req.username());

        /*
         * 【第三步：密码加密】★ 关键
         *
         * passwordEncoder.encode("Passw0rd1")
         *   → "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy"
         *
         * ★ BCrypt 的三个特点（面试常问）：
         *   1. 每次加密结果【都不一样】！
         *      因为内置了随机 salt。同一个密码加密两次，得到两个不同的哈希。
         *      验证时不需要知道 salt —— 它存在哈希串里面。
         *
         *   2. 无法反推。
         *      matches(明文, 哈希) 的做法是：从哈希里取出 salt，
         *      用同样的 salt 再算一次，比较结果。
         *
         *   3. 慢。cost=10 意味着 2^10 = 1024 轮计算，约 50-100ms。
         *      对登录来说这点延迟无感，但让爆破成本高几个数量级。
         *
         * ★ 为什么不能自己写加密？
         *   自己用 MD5/SHA256 + 手写 salt 极易出错（比如 salt 复用、
         *   拼接顺序错、忘了加盐）。直接用 Spring 的标准实现。
         */
        user.setPasswordHash(passwordEncoder.encode(req.password()));

        user.setNickname(req.nickname());

        /*
         * yearsOfExperience 不设置：@PrePersist 会兜底成 0。
         * ★ 但这里显式写更好读：
         */
        user.setYearsOfExperience(0);

        /*
         * 【第四步：入库】
         *
         * save() 的语义：
         *   id 为 null → 执行 INSERT
         *   id 有值   → 执行 UPDATE
         * 这里 id 是 null，所以是 INSERT。
         *
         * ★ 返回值 saved 和 user 是同一个对象（JPA 会把生成的 id 回填到 user）。
         *   用返回值接一下只是为了语义清楚。
         *
         * ★ createdAt / updatedAt 不用设置 —— @PrePersist 会处理。
         */
        AppUser saved = userRepository.save(user);

        log.info("新用户注册成功, userId={}, username={}", saved.getId(), saved.getUsername());

        /*
         * 【第五步：转成 VO 返回】
         *
         * ★ 这里返回 UserVO 而不是 AppUser，是因为 Controller 会直接
         *   把它放进响应体。如果返回 AppUser，passwordHash 就会泄露。
         *
         * ★ 注册后【不自动登录】。
         *   前端会在注册成功后立刻调一次 login（见 04 文档的 register）。
         *   也可以在这里直接签发 token，但那样注册接口的职责就变重了，
         *   而且前端要处理两套返回结构。分开更清晰。
         */
        return UserVO.of(saved);
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【二、登录】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 这是全项目最重要的一个方法，涉及的核心是"如何安全地验证身份"。
     *
     * @param req 用户名 + 密码
     * @return 两个 token + 有效期 + 用户信息
     * @throws BizException BAD_CREDENTIALS —— 用户名不存在 或 密码错误
     */
    @Transactional
    public TokenResponse login(LoginRequest req) {

        /*
         * ═══════════════════════════════════════════════════════════
         *  【第一步：查用户 + 比对密码，两步合一】
         * ═══════════════════════════════════════════════════════════
         *
         * 这段链式调用值得逐段拆开看：
         *
         * ① userRepository.findByUsername(req.username())
         *      返回 Optional<AppUser>
         *      用户不存在 → Optional.empty()
         *      用户存在   → Optional.of(user)
         *
         * ② .filter(u -> passwordEncoder.matches(...))
         *      如果 Optional 里有值，执行判断：
         *          密码对 → 原样返回这个 Optional
         *          密码错 → 变成 Optional.empty()
         *      如果本来就是 empty，filter 不执行判断，还是 empty
         *
         * ③ .orElseThrow(...)
         *      empty → 抛 BAD_CREDENTIALS
         *      有值  → 返回那个 AppUser
         *
         * ★★ 这个写法的精妙之处：用户不存在 和 密码错误，
         *    走的是【同一个出口】，抛出的是【同一个异常】，
         *    返回给前端的是【同一句话】。
         *
         *    如果分开写：
         *        if (user == null) throw new BizException("用户不存在");
         *        if (!match) throw new BizException("密码错误");
         *    攻击者就能通过提示语判断哪些用户名存在，然后针对性爆破 ——
         *    这叫【用户名枚举攻击】。
         *
         *    合在一起之后，攻击者得不到任何额外信息。
         *
         * ★ matches(明文, 哈希) 的参数顺序：
         *    第一个是用户输入的明文
         *    第二个是数据库里存的哈希
         *   ★ 顺序写反了编译不会报错（都是 String），但永远返回 false。
         *     这是个很隐蔽的坑。
         */
        AppUser user = userRepository.findByUsername(req.username())
                .filter(u -> passwordEncoder.matches(req.password(), u.getPasswordHash()))
                .orElseThrow(() -> {
                    // ★ 日志里记一下尝试失败，便于发现异常登录。
                    //   但注意：只记用户名，【绝不记密码】。
                    log.warn("登录失败, username={}", req.username());
                    return new BizException(ErrorCode.BAD_CREDENTIALS);
                });

        /*
         * ═══════════════════════════════════════════════════════════
         *  【第二步：更新最后登录时间】
         * ═══════════════════════════════════════════════════════════
         *
         * ★ 为什么用 LocalDateTime.now(ZoneOffset.UTC)？
         *   全项目统一存 UTC 时间（见 AppUser 的 @PrePersist 说明）。
         *   如果这里写 now()，就会和注册时的时间差 8 小时。
         *
         * ★ 需要显式 save 吗？
         *   不需要。因为 user 是"托管状态"（managed）—— 它来自当前事务里的
         *   一次查询，Hibernate 会追踪它的变化，
         *   事务提交时自动发一条 UPDATE。
         *   这叫"脏检查"（dirty checking）。
         *
         *   ★ 但如果你把 user 传给别的方法、或者在事务外修改，就需要手动 save。
         *     为了明确，本项目在有些地方会显式 save（无害），
         *     这里省略是因为它就在同一个方法里，一眼能看出是在事务内。
         */
        user.setLastLoginAt(LocalDateTime.now(ZoneOffset.UTC));

        /*
         * ═══════════════════════════════════════════════════════════
         *  【第三步：签发 token】
         * ═══════════════════════════════════════════════════════════
         */
        log.info("登录成功, userId={}, username={}", user.getId(), user.getUsername());
        return issueTokens(user);
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【三、刷新 token】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★★ 这个方法的核心设计叫"轮换"（rotation），务必理解：
     *
     *   每次刷新，旧 refresh token 立即作废，发一个新的。
     *
     *   为什么？
     *   1. 【限制泄露危害】攻击者偷到 refresh token，最多也只能用一次。
     *      因为他用完之后，这个 token 就作废了。
     *
     *   2. 【留下异常信号】如果攻击者先用掉了，真用户下次刷新就会失败
     *      （因为旧的已作废）→ 用户被迫重新登录 → 这是一个"被盗"的信号。
     *
     *   3. 【防止长期潜伏】不轮换的话，一个 stolen refresh 可以反复刷新 7 天，
     *      你永远发现不了。
     *
     * ★ 这就是为什么这个方法的最后要"先删旧的，再发新的"，
     *   顺序不能反。
     *
     * @param refreshToken 前端存的刷新令牌
     * @return 一对新的 token
     * @throws BizException TOKEN_INVALID —— 任何环节不对都返回这个
     */
    @Transactional
    public TokenResponse refresh(String refreshToken) {

        /*
         * 【第一步：解析 token】
         *
         * ★ 为什么要 try-catch？
         *   parse() 会抛 JwtException（过期、签名错、格式错）。
         *   这些都是"用户凭证不可用"，应该统一变成 TOKEN_INVALID，
         *   而不是让它冒到 GlobalExceptionHandler 变成 500。
         *
         * ★ 为什么 catch 两个类型？
         *   JwtException          → jjwt 抛的（签名/过期/格式）
         *   IllegalArgumentException → 字符串为 null 或空时抛的
         *   两个都要接，否则空字符串会导致 500。
         */
        Claims claims;
        try {
            claims = tokenProvider.parse(refreshToken);
        } catch (JwtException | IllegalArgumentException e) {
            log.debug("refresh token 解析失败: {}", e.getMessage());
            throw new BizException(ErrorCode.TOKEN_INVALID);
        }

        /*
         * 【第二步：确认这是 refresh token，不是 access token】
         *
         * ★ 为什么要检查？
         *   防一种攻击/误用：用户拿 access token 来调 refresh 接口。
         *   如果放行了，等于把 2 小时的 access 变成了 7 天的新 access
         *   （因为每次刷新都会发新的），短有效期的意义就没了。
         *
         * ★ 同样地，JwtAuthenticationFilter 里也会检查"必须是 access"，
         *   两边都检查，双向封闭。
         */
        if (!JwtTokenProvider.TYPE_REFRESH.equals(tokenProvider.type(claims))) {
            throw new BizException(ErrorCode.TOKEN_INVALID);
        }

        /*
         * 【第三步：从 claims 里取出 userId 和 jti】
         */
        Long userId = tokenProvider.userId(claims);
        String jti = tokenProvider.jti(claims);

        /*
         * ═══════════════════════════════════════════════════════════
         *  【第四步：★ 检查白名单 —— 这一步是整个撤销机制的核心】
         * ═══════════════════════════════════════════════════════════
         *
         * 为什么签名对、没过期的 token 还要查白名单？
         *
         *   因为 JWT 是自包含的：只要签名对、没过期，服务端就认。
         *   但我们需要能【主动撤销】：
         *      - 用户登出         → 删掉白名单记录
         *      - 改密码/被禁用     → revokeAllRefresh 清空
         *      - 已经轮换过一次    → 旧记录被删，自然查不到
         *
         *   查白名单就是"我承认这个 token 是我发过并且还没撤销的"。
         *
         * ★ 如果一个 refresh token 被偷了，用户登出后：
         *   攻击者拿着它来刷新 → 白名单里查不到 → 401
         *   这就是"登出后立即失效"的实现原理。
         */
        if (!tokenService.isRefreshValid(userId, jti)) {
            log.warn("refresh token 不在白名单（可能已登出/已被轮换）, userId={}", userId);
            throw new BizException(ErrorCode.TOKEN_INVALID);
        }

        /*
         * 【第五步：确认用户仍然存在】
         *
         * ★ 为什么还要查一次？
         *   token 可能签发后被删除了（本项目不提供注销，但理论上可能）。
         *   查一下更稳妥，成本很低（主键查询）。
         */
        AppUser user = userRepository.findById(userId)
                .orElseThrow(() -> new BizException(ErrorCode.TOKEN_INVALID));

        /*
         * ═══════════════════════════════════════════════════════════
         *  【第六步：★ 轮换 —— 删掉旧的，再发新的】
         * ═══════════════════════════════════════════════════════════
         *
         * ★ 这一行必须在 issueTokens 之前！
         *   否则如果发新 token 的过程中出错，旧 token 还能用，
         *   就变成了"两个 refresh 都有效"，破坏了轮换的安全性。
         *
         * ★ 更严谨的写法应该是"先发新的、再删旧的"吗？
         *   不。如果先发新后删旧，中间崩溃了会留下两个有效 token。
         *   而先删后发，中间崩溃了用户就得重新登录 ——
         *   安全优先于可用性，选前者。
         */
        tokenService.revokeRefresh(userId, jti);

        log.info("token 刷新成功（已轮换）, userId={}", userId);
        return issueTokens(user);
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【四、登出】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 为什么参数是字符串而不是 Claims？
     *   因为调用方（Controller）手里只有请求头里的原始字符串。
     *   让它先解析一遍再传进来，等于把"解析"这件事散到 Controller 里。
     *   在这里统一解析，职责更清楚。
     *
     * ★ 为什么这个方法不加 @Transactional？
     *   因为它【完全不碰数据库】，只操作 Redis。
     *   事务是管理数据库连接的，对 Redis 没有作用。
     *   加了反而多一层无用开销。
     *
     * @param accessToken  请求头里的 access token（可能为 null）
     * @param refreshToken 请求体里的 refresh token（可能为 null）
     */
    public void logout(String accessToken, String refreshToken) {

        /*
         * ═══════════════════════════════════════════════════════════
         *  【第一步：把 access token 拉黑】
         * ═══════════════════════════════════════════════════════════
         *
         * ★ 为什么可能为 null？
         *   理论上登出接口需要登录才能调，但万一前端实现有问题
         *   （比如 token 已过期还想登出），我们也应该让它"成功"，
         *   不能因为 token 过期就报错 —— 用户点"退出登录"却没退出，体验很差。
         *
         * ★ 为什么要 try-catch？
         *   如果 token 已经过期，parse 会抛 ExpiredJwtException。
         *   这时候它已经无效了，不需要拉黑，直接忽略即可。
         *   静默吞掉是合理的 —— 结果（这个 token 不能用了）已经达成。
         *
         * ★ remainingTtl 算的是什么？
         *   这个 token 还有多久过期。黑名单 TTL 设成这个值，
         *   意味着 token 自然过期时黑名单记录也一起消失（见 RedisKeys.blacklist）。
         */
        if (accessToken != null && !accessToken.isBlank()) {
            try {
                Claims claims = tokenProvider.parse(accessToken);
                tokenService.blacklistAccess(
                        tokenProvider.jti(claims),
                        tokenProvider.remainingTtl(claims));
            } catch (JwtException | IllegalArgumentException ignored) {
                // token 本来就无效，不需要拉黑
                log.debug("登出时 access token 已失效，跳过拉黑");
            }
        }

        /*
         * 【第二步：从白名单删除 refresh token】
         *
         * ★ 这一步之后，这个 refresh token 就彻底不能用了。
         *   即使它在 7 天有效期内。
         */
        if (refreshToken != null && !refreshToken.isBlank()) {
            try {
                Claims claims = tokenProvider.parse(refreshToken);
                tokenService.revokeRefresh(tokenProvider.userId(claims), tokenProvider.jti(claims));
            } catch (JwtException | IllegalArgumentException ignored) {
                log.debug("登出时 refresh token 已失效，跳过删除");
            }
        }

        /*
         * ═══════════════════════════════════════════════════════════
         *  【★ 为什么登出要传两个 token，而前端可能只有 access？】
         *
         *  前端在 localStorage 里两个都存着（见 04 文档），所以都能传。
         *
         *  如果只传 access 会怎样？
         *      access 被拉黑 → 2 小时内不能用了 ✅
         *      但 refresh 还在白名单里 → 攻击者可以用它换一个新的 access ❌
         *      等于"登出"没有真正生效！
         *
         *  ★ 所以登出必须两个都处理，缺一个就有漏洞。
         *    这是安全检查清单里必查的一条。
         * ═══════════════════════════════════════════════════════════
         */
        log.info("用户登出");
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【内部方法：签发一对 token 并登记白名单】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 为什么抽出来？
     *   login 和 refresh 都要做同样的事（签发 + 登记 + 组装响应），
     *   抽出来只写一次。以后改逻辑（比如加设备 id）只改一处。
     *
     * ★ 为什么是 private？
     *   这是内部实现细节，外部不该直接调。
     *   外部应该走 login / refresh，那样才有完整的业务校验。
     *
     * @param user 已经通过身份验证的用户
     * @return 完整的登录响应
     */
    private TokenResponse issueTokens(AppUser user) {

        /*
         * 【第一步：生成两个 token】
         *
         * 两个 token 的内容几乎一样（同样的 userId、username），
         * 只有两点不同：
         *   type → access / refresh
         *   ttl  → 2 小时 / 7 天
         *
         * ★ 为什么要区分？见 JwtTokenProvider.TYPE_ACCESS 的详细说明。
         */
        String access = tokenProvider.createAccess(user.getId(), user.getUsername());
        String refresh = tokenProvider.createRefresh(user.getId(), user.getUsername());

        /*
         * ═══════════════════════════════════════════════════════════
         *  【第二步：把 refresh 的 jti 存进 Redis 白名单】
         * ═══════════════════════════════════════════════════════════
         *
         * ★★ 这里有个"绕"的地方，值得说明：
         *
         *   我们刚生成了 refresh 字符串，但需要的是它的 jti。
         *   jti 是在生成时随机产生的 UUID，生成后没有直接返回。
         *   所以唯一的办法是【再解析一次】把 jti 读出来。
         *
         *   ★ 这确实有点笨 —— 多了一次解析开销。
         *     更干净的写法是让 createRefresh 返回一个包含 (token, jti) 的小 record：
         *         record IssuedToken(String token, String jti) {}
         *         IssuedToken refresh = tokenProvider.createRefresh(...);
         *
         *     这里保留现在的写法是为了让流程更直白（能一眼看出"存的是哪个 jti"），
         *     你可以自己改成上面那种更优雅的版本。
         *
         * ★ 为什么只存 refresh 的 jti，不存 access 的？
         *   因为 access 用的是黑名单（默认放行），
         *   存了反而会让白名单膨胀（见 TokenService 类注释里的对比表）。
         */
        Claims refreshClaims = tokenProvider.parse(refresh);
        tokenService.saveRefresh(
                user.getId(),
                tokenProvider.jti(refreshClaims),
                jwtProperties.refreshTtl()     // TTL 和 token 有效期一致
        );

        /*
         * 【第三步：组装响应】
         *
         * ★ expiresIn 用 jwtProperties.accessTtl().toSeconds()
         *   而不是写死 7200。
         *   这样改 yml 里的配置就自动生效，不用改代码。
         *
         * ★ UserVO.of(user) —— 又出现了这个转换。
         *   记住：只要数据要"出系统"，就必须经过 Entity → VO 这一步。
         */
        return new TokenResponse(
                access,
                refresh,
                jwtProperties.accessTtl().toSeconds(),
                UserVO.of(user)
        );
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ 这个类的设计要点小结（面试可讲）】
     *
     *  1. 登录失败统一返回 BAD_CREDENTIALS，防用户名枚举
     *  2. access 短有效期 + 黑名单；refresh 长有效期 + 白名单 + 轮换
     *  3. 登出必须同时处理两个 token，否则"登出"不彻底
     *  4. 密码只以 BCrypt 哈希形式落库，永不返回、永不记录日志
     *  5. 所有返回给前端的用户数据都经过 UserVO 投影
     *
     *  ★ 如果被问"JWT 无状态怎么实现登出"：
     *     答："access 用 jti 黑名单，TTL 对齐剩余有效期；
     *          refresh 用 Redis 白名单，登出时删除记录。
     *          这样既能立即失效，又不会让 Redis 无限膨胀。"
     * ═══════════════════════════════════════════════════════════════
     */
}
```

**认证接口** —— 4 个接口，几乎没有逻辑

```java
package com.jianli.user.controller;

import com.jianli.common.ApiResponse;
import com.jianli.user.dto.LoginRequest;
import com.jianli.user.dto.RefreshRequest;
import com.jianli.user.dto.RegisterRequest;
import com.jianli.user.dto.TokenResponse;
import com.jianli.user.dto.UserVO;
import com.jianli.user.service.AuthService;
import io.swagger.v3.oas.annotations.Operation;
import io.swagger.v3.oas.annotations.tags.Tag;
import jakarta.validation.Valid;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  认证相关的 4 个接口：注册、登录、刷新、登出。
 *
 *  ★ 这个类几乎没有逻辑 —— 全部委托给 AuthService。
 *    这是 Controller 的正确形态：它只负责"接活"和"交货"。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：它站在哪个位置】
 *
 *      浏览器 POST /api/auth/login
 *         ↓
 *      过滤器链（TraceIdFilter 贴 id、JwtAuthenticationFilter 尝试认人——
 *               登录请求本来就没 token，认不出，不影响）
 *         ↓
 *      不需要登录（SecurityConfig 里放行了 /api/auth/login）
 *         ↓
 *      DispatcherServlet 路由匹配 → 【本类】login()
 *         ├─ @RequestBody + @Valid 把 JSON 变成 LoginRequest 并校验
 *         ├─ 调 authService.login(req)
 *         └─ 包成 ApiResponse<TokenResponse>
 *         ↓
 *      Jackson 序列化 → HTTP 响应
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【@RestController + @RequestMapping("/api/auth") 干什么】
 *
 *  @RestController
 *      = @Controller + @ResponseBody，返回值会被转成 JSON 写进响应体
 *      （详细解释见 DemoController 的类注释）
 *
 *  @RequestMapping("/api/auth")
 *      给本类所有接口加路径前缀。
 *      方法上的 @PostMapping("/login") 最终路径 = /api/auth/login
 *
 *  【@Tag(name = "认证") 干什么】
 *      Swagger 分组名。在 Swagger 页面上会看到"认证"这一组，
 *      里面就是这 4 个接口。纯文档作用，不影响功能。
 *
 *
 *  【★ 为什么这 4 个接口都不需要登录？】
 *
 *  ★ 关键：它们必须在 SecurityConfig 里被放行，否则会死锁：
 *      - 登录需要 token 吗？不需要（还没登录哪来的 token）
 *      - 但如果 /api/auth/login 需要认证，用户就永远登录不了
 *
 *  所以 SecurityConfig 里有：
 *      .requestMatchers("/api/auth/register", "/api/auth/login", "/api/auth/refresh").permitAll()
 *
 *  ★ 但 logout 是例外 —— 它需要登录（或者至少需要传一个 token）。
 *    不过我们也把它放行了，因为登出时 token 可能已过期，
 *    这时候也应该让用户"成功登出"（前端清掉本地状态）。
 *    所以 logout 在 SecurityConfig 里也是 permitAll，
 *    它自己内部判断 token 有效就拉黑、无效就忽略。
 */
@RestController
@RequestMapping("/api/auth")
@Tag(name = "认证")
@RequiredArgsConstructor
public class AuthController {

    /**
     * 由 Spring 通过构造器注入。
     *
     * ★ Controller 只依赖 Service，【绝不直接依赖 Repository】。
     *   原因：业务规则都在 Service 里，如果 Controller 能直接查库，
     *   就会出现"某个接口跳过了归属校验"这类漏洞。
     */
    private final AuthService authService;

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【一、注册】POST /api/auth/register
     * ═══════════════════════════════════════════════════════════════
     *
     * 请求：
     *      POST /api/auth/register
     *      Content-Type: application/json
     *      {"username":"alice","password":"Passw0rd1","nickname":"Alice"}
     *
     * 响应（201 Created）：
     *      {
     *        "code": 0, "message": "ok",
     *        "data": {"id":1,"username":"alice","nickname":"Alice",...},
     *        "traceId": "...", "timestamp": ...
     *      }
     *
     * 错误：
     *      400 + code=10000  参数校验失败（用户名太短、密码没数字等）
     *      409 + code=20001  用户名已被占用
     *
     * ★ 为什么返回 201 而不是 200？
     *   HTTP 语义：201 Created 表示"创建了新资源"，并且通常带 Location 头
     *   指向新资源。200 表示"请求成功"但不特指创建。
     *   ★ 严格说返回 201 更规范，面试时能讲出这个区别是加分项。
     *     不过前端一般不区分（都是 2xx），所以实际影响很小。
     *
     * ★ 为什么返回 ResponseEntity 而不是直接返回 ApiResponse？
     *   因为要自定义状态码（201）。直接返回 ApiResponse 的话，
     *   Spring 默认给 200，无法表达"创建成功"这个语义。
     *   本类只有这个方法需要 201，其他三个用默认 200 就够了。
     */
    @PostMapping("/register")
    @Operation(summary = "注册", description = "创建新账号，注册后需要单独调登录接口")
    public ResponseEntity<ApiResponse<UserVO>> register(
            @RequestBody @Valid RegisterRequest req) {

        /*
         * @RequestBody
         *     告诉 Spring："从请求体里读 JSON，反序列化成 RegisterRequest"。
         *     ★ 如果少了这个注解，Spring 会以为 req 是查询参数，得到 null。
         *
         * @Valid
         *     触发 RegisterRequest 里那些 @NotBlank / @Size / @Pattern 的校验。
         *     ★ 少了它，校验注解完全不生效 —— 空用户名也能注册进来。
         *     这是很常见的疏漏，加注解时一定要成对加。
         *
         * ★ 校验失败会怎样？
         *   在进入方法体之前就抛 MethodArgumentNotValidException，
         *   被 GlobalExceptionHandler.handleValid 接住，返回 400。
         *   所以方法体里不需要写任何判空代码。
         */
        UserVO vo = authService.register(req);

        return ResponseEntity.status(HttpStatus.CREATED)
                .body(ApiResponse.ok(vo));
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【二、登录】POST /api/auth/login
     * ═══════════════════════════════════════════════════════════════
     *
     * 请求：
     *      {"username":"alice","password":"Passw0rd1"}
     *
     * 响应（200）：
     *      {
     *        "code": 0,
     *        "data": {
     *          "accessToken":  "eyJhbGciOi...",
     *          "refreshToken": "eyJhbGciOi...",
     *          "expiresIn": 7200,
     *          "user": {"id":1,"username":"alice",...}
     *        }
     *      }
     *
     * 错误：
     *      401 + code=20002  用户名或密码错误
     *      （★ 故意不区分是用户名错还是密码错，防枚举）
     *
     * ★ 注意这个方法返回的 token 里【明文可解出 userId 和 username】。
     *   所以不要把 token 当秘密 —— 它是"防伪凭证"，不是"加密容器"。
     */
    @PostMapping("/login")
    @Operation(summary = "登录", description = "返回 access token(2小时) 与 refresh token(7天)")
    public ApiResponse<TokenResponse> login(@RequestBody @Valid LoginRequest req) {

        /*
         * ★ 这里直接返回 ApiResponse（不包 ResponseEntity），
         *   所以 HTTP 状态码是默认的 200。
         *
         * ★ 为什么不在这里打日志？
         *   AuthService 里已经打了（登录成功/失败都会打）。
         *   Controller 再打一遍就重复了。
         *   ★ 原则：同一个事件只在一处记录，否则日志会重复且难读。
         */
        return ApiResponse.ok(authService.login(req));
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【三、刷新 token】POST /api/auth/refresh
     * ═══════════════════════════════════════════════════════════════
     *
     * 请求：
     *      {"refreshToken":"eyJhbGciOi..."}
     *
     * 响应（200）：和登录一样的结构（一对全新的 token）
     *
     * 错误：
     *      401 + code=20003  token 无效（过期、被轮换、已登出、类型不对）
     *
     * ★ 这个接口什么时候被调用？
     *   前端拦截器收到 401 时自动调用，用户完全无感。
     *   详见 04 文档里 http.js 的"刷新单例"实现。
     *
     * ★★ 为什么返回新的 refreshToken，而不是沿用旧的？
     *   因为"轮换"：旧的已经在 AuthService.refresh 里被删了。
     *   如果这里返回旧的，前端下次刷新就会失败。
     *   前端必须用响应里的新 refreshToken 替换本地的。
     */
    @PostMapping("/refresh")
    @Operation(summary = "刷新令牌", description = "用 refresh token 换一对新 token，旧的立即作废")
    public ApiResponse<TokenResponse> refresh(@RequestBody @Valid RefreshRequest req) {
        return ApiResponse.ok(authService.refresh(req.refreshToken()));
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【四、登出】POST /api/auth/logout
     * ═══════════════════════════════════════════════════════════════
     *
     * 请求：
     *      POST /api/auth/logout
     *      Authorization: Bearer eyJ...          ← access token 在请求头
     *      {"refreshToken":"eyJ..."}             ← refresh token 在请求体
     *
     * 响应（200）：
     *      {"code":0,"message":"ok","data":null}
     *
     * ★★ 关键设计：登出需要【两个】token
     *
     *   只传 access：access 被拉黑，但 refresh 还能换新 access → 登出不彻底
     *   只传 refresh：refresh 被删，但 access 在 2 小时内还能用 → 不安全
     *   两个都传：   access 进黑名单 + refresh 出白名单 → 立即完全失效
     *
     *   这是安全检查清单里必查的一条。
     *
     * ★ 为什么 access 从请求头取，refresh 从请求体取？
     *   1. access 本来就是每个请求都放请求头，登出请求也不例外，
     *      从请求头取是"顺其自然"
     *   2. refresh token 不应该出现在请求头里（它只该出现在刷新接口的请求体），
     *      这是个安全约定 —— 减少它被中间设备记录的机会
     *
     * ★ @RequestHeader(required = false) 为什么要 false？
     *   如果用户 token 已过期还想登出，前端可能没带 Authorization 头。
     *   这时候也应该让他"成功登出"（清掉本地状态）。
     *   所以 access 允许为空，AuthService 内部会判断。
     *
     * ★ @RequestBody(required = false) 同理 ——
     *   万一前端没传请求体，也不该 400 报错，而应该按"只处理 access"来。
     *   ★ 这样设计让登出接口"永远成功"，符合用户体验预期：
     *     用户点了"退出"，就一定要退出，不能因为技术原因失败。
     */
    @PostMapping("/logout")
    @Operation(summary = "登出", description = "access 进黑名单、refresh 出白名单，两者都必须处理")
    public ApiResponse<Void> logout(
            @RequestHeader(value = HttpHeaders.AUTHORIZATION, required = false) String authHeader,
            @RequestBody(required = false) RefreshRequest req) {

        /*
         * 【从请求头里剥出裸 token】
         *
         * Authorization 头长这样：
         *      "Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxIn0.xxx"
         *
         * ★ 为什么要判断 startsWith("Bearer ")？
         *   万一前端传了个格式不对的头（或者别的认证方案），
         *   直接 substring(7) 会截出错误的内容。
         *   判一下更安全，格式不对就当"没传"。
         *
         * ★ 用三元表达式而不是 if：
         *   这是一个简单的二选一赋值，三元更紧凑。
         *   如果里面有多个逻辑分支，还是用 if 更清楚。
         */
        String access = (authHeader != null && authHeader.startsWith("Bearer "))
                ? authHeader.substring(7)
                : null;

        /*
         * 【refresh 从请求体里取】
         *
         * ★ req == null 的判断必要，因为 @RequestBody(required = false)。
         *   前端可能压根没传请求体。
         */
        String refresh = (req == null) ? null : req.refreshToken();

        /*
         * 【交给 Service 处理】
         *
         * ★ 注意：这个方法【永远返回成功】。
         *   即使两个 token 都无效，也返回 code=0。
         *   因为"登出"这个动作的目标是"让本地状态清空"，
         *   服务端这边能做的都做了（能拉黑就拉黑），
         *   没必要因为 token 已过期就报错让用户困惑。
         */
        authService.logout(access, refresh);

        /*
         * ★ ApiResponse.ok() 不传参数 → data 为 null
         *   前端只需要看 code === 0 就知道成功了。
         */
        return ApiResponse.ok();
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ Controller 的职责边界（再强调一次）】
     *
     *  ✅ 该做：
     *      - 用 @RequestBody / @PathVariable / @RequestParam 接参数
     *      - 用 @Valid 触发校验
     *      - 调 Service 的【一个】方法
     *      - 包成 ApiResponse / ResponseEntity
     *
     *  ❌ 不该做：
     *      - if/else 业务判断（"这个用户能不能注册"）
     *      - 直接调 Repository
     *      - try/catch（GlobalExceptionHandler 管）
     *      - 拼装复杂的数据结构（那是 Service 的事）
     *
     *  ★ 本类 4 个方法都是"一行调用 + 一行返回"，
     *    这就是健康的 Controller 长什么样。
     *    如果你发现某个 Controller 方法超过 20 行，多半是业务逻辑漏在这儿了。
     * ═══════════════════════════════════════════════════════════════
     */
}
```

```java
 *
 *  ✅ GET /api/users/me
 *      "me" 由服务端从 token 里推导出来，用户无法指定。
 *      从根本上不可能越权 —— 你没有传 id 的机会。
 *
 *  ★ 这是"用 API 设计消除安全隐患"的典型例子：
 *    与其写代码去防止错误用法，不如让错误用法根本表达不出来。
 *
 *  【什么时候才需要 /users/{id}？】
 *  当确实要看别人的资料时（比如社区里点进某个人的主页）。
 *  那时候返回的字段应该更少（只有昵称和帖子数，不能有目标岗位等隐私）。
 *  本项目暂时不需要。
```

```java
import com.fasterxml.jackson.databind.ObjectMapper;
import com.jianli.common.ApiResponse;
import com.jianli.common.ErrorCode;
import com.jianli.security.JwtAuthenticationFilter;
import jakarta.servlet.http.HttpServletResponse;

import org.springframework.security.config.annotation.web.builders.HttpSecurity;

import org.springframework.security.crypto.password.PasswordEncoder;

import org.springframework.web.cors.CorsConfigurationSource;

import java.util.List;

/**
 * ═══════════════════════════════════════════════════════════════════════
 *  【这个类是什么】
 *  安全总配置。决定三件事：
 *      1. 哪些接口需要登录、哪些公开
 *      2. 密码怎么加密
 *      3. JWT 过滤器插在哪一环、认证失败返回什么
 *
 *  ★ 这是步骤 3 对整个系统的"安全总开关"，
 *    也是把步骤 1 的临时全放行版本替换掉的地方。
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【★ 数据流向：一个请求经过这里的完整过程】
 *
 *      请求进入
 *         ↓
 *      TraceIdFilter（贴 traceId）
 *         ↓
 *      CorsFilter（处理跨域预检）
 *         ↓
 *      JwtAuthenticationFilter（★ 本类注册的）
 *         ├─ 有 token 且有效 → 设置认证信息
 *         └─ 没 token / 无效 → 保持未登录（不拦，继续往下）
 *         ↓
 *      FilterSecurityInterceptor / AuthorizationFilter
 *         └─ 按本类的 authorizeHttpRequests 规则判断：
 *              公开接口             → 直接放行
 *              需要登录 且 已认证   → 放行
 *              需要登录 但 未认证   → 调用 authenticationEntryPoint → 401
 *              已认证 但 权限不足   → 调用 accessDeniedHandler → 403
 *         ↓
 *      DispatcherServlet → Controller
 *         ↓
 *      如果抛异常 → GlobalExceptionHandler → 统一响应
 * ═══════════════════════════════════════════════════════════════════════
 *
 *  【@EnableWebSecurity 是什么】
 *  开启 Spring Security 的 Web 安全功能。
 *
 * ★ 严格说 Spring Boot 自动配置已经帮我们开了（引了 starter 就有）。
 *   显式写出来是为了"意图明确" —— 看到这个注解就知道这个项目用了 Security。
 *
 * ★ 二期做 RBAC 时，这里还要加 @EnableMethodSecurity，
 *   才能用 @PreAuthorize("hasAuthority('POST:HIDE')") 这种注解式权限控制。
 */
@Configuration
@EnableWebSecurity
@RequiredArgsConstructor
public class SecurityConfig {

    /**
     * JWT 过滤器。由 Spring 注入（它自己也是个 @Component）。
     *
     * ★ 为什么这里要注入它、而不是在 filterChain 方法里 new 一个？
     *   因为它自己还有两个依赖（JwtTokenProvider、TokenService），
     *   手动 new 就得自己处理依赖，很麻烦。
     *   注入进来复用容器里那个就行了。
     */
    private final JwtAuthenticationFilter jwtAuthenticationFilter;

    /**
     * Jackson 的对象映射器。用来把 ApiResponse 转成 JSON 字符串。
     *
     * ★ 为什么这里需要它？
     *   因为在"认证失败"的处理里，我们要手写响应体
     *   （那是 Filter 层，不是 Controller 层，用不上 HttpMessageConverter）。
     *   需要手动把对象序列化成 JSON 写进 response。
     *
     * ★ 为什么不自己 new 一个 ObjectMapper？
     *   那样会丢掉全局配置（比如 JacksonConfig 里配的时间格式）。
     *   用容器里那个，格式和正常响应一致。
     */
    private final ObjectMapper objectMapper;

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【密码加密器】BCrypt
     * ═══════════════════════════════════════════════════════════════
     *
     * 定义成一个 @Bean 之后，AuthService 就可以注入它用：
     *      passwordEncoder.encode(明文)          → 哈希
     *      passwordEncoder.matches(明文, 哈希)   → true / false
     *
     * ★ 为什么用 BCrypt 而不是 MD5/SHA256？（面试必问）
     *
     *   MD5/SHA256 是"快哈希"：
     *       GPU 每秒能算几十亿次 → 8 位密码几小时就被爆破出来
     *
     *   BCrypt 是"慢哈希"：
     *       单次计算 50-100ms（可调），爆破成本高几个数量级
     *       内置随机 salt（所以不需要单独存盐字段）
     *       哈希串自带 cost 因子和 salt，验证时自己解析
     *
     * ★ 参数 10 是什么？
     *   cost factor（代价因子），表示 2^10 = 1024 轮计算。
     *      往上升一级，计算时间翻倍：
     *          10 → 约 50-100ms（本项目）
     *          12 → 约 200-400ms
     *          14 → 约 1 秒（太慢，登录体验差）
     *
     *   ★ 怎么选？
     *     目标是"单次验证 100ms 左右" —— 用户无感，攻击者很痛。
     *     硬件升级后可以调大（所以 cost 存在哈希串里，
     *     老用户的哈希用旧 cost 验，新注册的用新 cost 存，可平滑升级）。
     *
     * ★ 为什么不注入 PasswordEncoder 而是自己 new？
     *   因为这就是"定义 Bean 的地方" —— 由它来 new，其他地方注入使用。
     *   如果这里也注入，就循环依赖了。
     */
    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder(10);
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【安全过滤器链配置】—— 本类最核心的方法
     * ═══════════════════════════════════════════════════════════════
     *
     * @param http Spring Security 提供的配置器
     * @return 构建好的过滤器链
     * @throws Exception 构建失败（配置写错时抛）
     */
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http

                /*
                 * ═══════════════════════════════════════════════════
                 *  【1. 禁用 CSRF】
                 * ═══════════════════════════════════════════════════
                 *
                 * CSRF（跨站请求伪造）的攻击场景：
                 *     你登录了银行网站，浏览器存着 Cookie。
                 *     这时你点开一个恶意网页，那个网页偷偷向银行发转账请求 ——
                 *     浏览器会自动带上 Cookie，银行以为是本人操作。
                 *
                 * 防御方式是每个请求带一个攻击者猜不到的 token。
                 *
                 * ★ 我们为什么可以关掉？
                 *   我们的认证靠 Authorization: Bearer <token> 请求头，
                 *   【不用 Cookie】。
                 *   浏览器不会自动给任何网站带上自定义请求头 ——
                 *   它只会自动带 Cookie。
                 *   所以恶意网页没法伪造我们的请求，天然免疫 CSRF。
                 *
                 * ★ AbstractHttpConfigurer::disable 是什么写法？
                 *   方法引用，等价于：
                 *       csrf -> csrf.disable()
                 *   只是更短。能这么写是因为 csrf(方法) 接受的参数
                 *   正好是一个"接收配置器并调用 disable"的函数。
                 *
                 * ★ 如果以后改成 Cookie 认证，这行【必须删掉】，
                 *   否则就是 CSRF 漏洞。
                 */
                .csrf(AbstractHttpConfigurer::disable)

                /*
                 * ═══════════════════════════════════════════════════
                 *  【2. 跨域配置】
                 * ═══════════════════════════════════════════════════
                 *
                 * ★ 为什么跨域要配在 Security 里，而不是 WebMvcConfigurer 里？
                 *   因为 Security 的过滤器链比 Spring MVC【更早执行】。
                 *   如果只在 MVC 里配，当请求被 Security 拒绝（401）时，
                 *   响应里不会带跨域头 —— 浏览器会报 CORS 错误而不是 401，
                 *   让你误判问题原因。
                 *
                 * ★ 实际开发中会触发跨域吗？
                 *   开发时：前端走 Vite 代理（5173 → 8080），浏览器看到的是同源，不跨域
                 *   生产时：前端走 Nginx 反代（同域），也不跨域
                 *   所以这段配置主要是为了 Postman / 其他前端联调时能用。
                 */
                .cors(c -> c.configurationSource(corsSource()))

                /*
                 * ═══════════════════════════════════════════════════
                 *  【3. 无状态会话】★ 关键
                 * ═══════════════════════════════════════════════════
                 *
                 * STATELESS 的意思是："不要创建 HttpSession，不要从 Session 里读认证信息"。
                 *
                 * ★ 为什么？
                 *   我们用 JWT，认证信息在 token 里，不需要服务端会话。
                 *   如果不禁用 Session：
                 *       - Spring 会创建一个 JSESSIONID Cookie（多余）
                 *       - 每个请求都会去检查 Session（浪费）
                 *       - 多实例部署时会话不同步（麻烦）
                 *
                 * ★ 设成 STATELESS 后：
                 *   SecurityContext 只存在于【当前请求的 ThreadLocal】里，
                 *   请求结束就没了 —— 下一个请求必须重新验 token。
                 *   这既是无状态的体现，也是安全的保证
                 *   （token 被拉黑后，下一个请求立刻失效）。
                 */
                .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))

                /*
                 * ═══════════════════════════════════════════════════
                 *  【4. ★★ 授权规则 —— 本类最重要的一段】
                 * ═══════════════════════════════════════════════════
                 *
                 * 规则是【从上往下匹配，第一个匹配上的生效】。
                 * 所以顺序很重要：越具体的放前面。
                 */
                .authorizeHttpRequests(a -> a

                        /*
                         * 【4.1 放行所有 OPTIONS 请求】
                         *
                         * ★ 为什么要单独放行？
                         *   浏览器发"跨域且带自定义头"的请求前，会先发一个
                         *   OPTIONS 预检请求（preflight），问服务端"我能发吗"。
                         *   预检请求【不带 Authorization 头】。
                         *
                         *   如果预检被 401 拦了，浏览器就不会发真正的请求，
                         *   你会看到"请求根本没到后端"的诡异现象。
                         *
                         * ★ HttpMethod.OPTIONS 加 "/**" 表示所有路径的 OPTIONS 都放行。
                         */
                        .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()

                        /*
                         * 【4.2 公开接口】
                         *
                         * ★ 这一组是最需要想清楚的 —— 放错了就是安全漏洞。
                         *
                         * 逐个说明为什么必须公开：
                         *
                         *   /api/auth/register  → 还没账号，哪来的 token？
                         *   /api/auth/login     → 要登录才能调登录接口？死锁
                         *   /api/auth/refresh   → access 过期才调它，此时没有效 access
                         *   /api/auth/logout    → token 可能已过期，也应该允许"退出"
                         *                          （否则用户永远退不出去，体验很差）
                         *
                         *   /api/meta/**        → 功能开关，前端启动时就要读
                         *                          （比如 AI 关闭时隐藏面试模块入口）
                         *
                         *   /v3/api-docs/**     → Swagger 的接口描述 JSON
                         *   /swagger-ui/**      → Swagger 页面本身
                         *   /swagger-ui.html    → 旧版路径（重定向）
                         *   ★ 生产环境建议关掉 Swagger，或者加访问限制 ——
                         *     因为它会把所有接口、参数结构都暴露出来。
                         *
                         *   /actuator/health    → 健康检查，Docker healthcheck 要用。
                         *                          ★ 只放行 health，不放行 actuator/** ——
                         *                          actuator 还有其他端点（env、beans 等）
                         *                          会泄露配置和内部结构。
                         */
                        .requestMatchers(
                                "/api/auth/register",
                                "/api/auth/login",
                                "/api/auth/refresh",
                                "/api/auth/logout",
                                "/api/meta/**",
                                "/v3/api-docs/**",
                                "/swagger-ui/**",
                                "/swagger-ui.html",
                                "/actuator/health"
                        ).permitAll()

                        /*
                         * 【4.3 社区内容公开可读】
                         *
                         * ★ 为什么要公开 GET 请求？
                         *   社区的价值在于"没登录的人也能看" ——
                         *   能搜到、能分享给朋友、能被搜索引擎收录。
                         *
                         * ★ 为什么只放 GET？
                         *   POST（发帖）、DELETE（删帖）当然要登录。
                         *   用 HttpMethod.GET 限定，比写 "/api/posts/**" 更精确。
                         *
                         * ★ Controller 里怎么处理"未登录"的情况？
                         *   用 @CurrentUserId(required = false) Long userId
                         *   → 未登录时 userId 为 null → Service 跳过"我的投票"查询
                         *   详见 13 步骤的 PostController。
                         */
                        .requestMatchers(HttpMethod.GET, "/api/posts/**").permitAll()

                        /*
                         * 【4.4 兜底：其他全部需要登录】
                         *
                         * ★ 这是"默认拒绝"原则（deny by default）：
                         *   新加的接口如果忘了配置规则，默认是【受保护】的，
                         *   而不是默认公开。
                         *
                         *   ★ 安全设计里这条极其重要：
                         *     宁可让某个该公开的接口意外要求登录（用户反馈后很快能发现），
                         *     也不要让某个该保护的接口意外公开（可能几个月都发现不了）。
                         *
                         * ★ 对比一下"默认放行"的写法：
                         *     .anyRequest().permitAll()
                         *   如果哪天新增了 DELETE /api/users/{id} 但忘了配规则，
                         *   任何人不登录就能删用户 —— 灾难。
                         */
                        .anyRequest().authenticated())

                /*
                 * ═══════════════════════════════════════════════════
                 *  【5. ★ 认证失败的处理（两个 handler）】
                 * ═══════════════════════════════════════════════════
                 *
                 * ★ 为什么必须自定义？
                 *   Spring Security 默认返回的是一个【空响应体】的 401/403。
                 *   前端拦截器拿到空响应体，无法解析 code，只能显示"未知错误"。
                 *
                 *   自定义之后，401 也会返回：
                 *       {"code":10001,"message":"请先登录","traceId":"...",...}
                 *   前端就能统一处理。
                 */
                .exceptionHandling(e -> e

                        /*
                         * 【5.1 未登录 / token 无效】→ 401
                         *
                         * ★ 什么时候触发？
                         *   请求打到了一个"需要登录"的接口，但 SecurityContext 里没有认证信息。
                         *   原因可能是：没带 token、token 过期、token 被拉黑、token 类型不对。
                         *
                         * ★ 注意：这是【最后一道判断】。
                         *   JwtAuthenticationFilter 只是"尝试认人"，认不出来也不拦；
                         *   真正决定"拦不拦"的是这里的授权规则。
                         */
                        .authenticationEntryPoint((req, res, ex) ->
                                writeError(res, ErrorCode.UNAUTHORIZED))

                        /*
                         * 【5.2 已登录但没权限】→ 403
                         *
                         * ★ 什么时候触发？
                         *   现在还用不到（因为还没有权限体系，登录了就是 ROLE_USER）。
                         *   二期加了 RBAC 之后，@PreAuthorize 失败会走到这里。
                         *
                         * ★ 401 和 403 的区别（面试常问）：
                         *   401 Unauthorized = "我不认识你"       （没登录 / 凭证无效）
                         *   403 Forbidden    = "我认识你，但你不能干这个"（权限不足）
                         */
                        .accessDeniedHandler((req, res, ex) ->
                                writeError(res, ErrorCode.FORBIDDEN)))

                /*
                 * ═══════════════════════════════════════════════════
                 *  【6. ★ 把 JWT 过滤器插入过滤器链】
                 * ═══════════════════════════════════════════════════
                 *
                 * addFilterBefore(要插入的过滤器, 插在谁前面)
                 *
                 * ★ 为什么插在 UsernamePasswordAuthenticationFilter 前面？
                 *   那是"用户名密码认证"的过滤器，是传统表单登录用的。
                 *   我们要在 Spring Security 做任何认证判断【之前】
                 *   就把 JWT 解析好、把认证信息设置好，
                 *   这样后面的授权判断才能读到"已登录"这个状态。
                 *
                 *   ★ 顺序错了会怎样？
                 *     如果插在后面，授权判断时 SecurityContext 还是空的，
                 *     所有需要登录的接口都会返回 401 —— 即使带了合法 token。
                 */
                .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);

        /*
         * build() 生成最终的过滤器链。
         * ★ 前面所有配置都只是"设置"，这一行才真正生效。
         *   忘了 return 或者忘了 build，配置就完全不工作。
         */
        return http.build();
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【认证失败时手写 JSON 响应】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 为什么要手写，不能像 Controller 那样 return ApiResponse？
     *   因为这里在【Filter 层】，不在 Controller 层。
     *   Filter 拿到的只有 HttpServletResponse（原生的 Servlet 对象），
     *   没有 Spring MVC 那套"返回值自动转 JSON"的机制。
     *   所以必须自己：设置状态码 → 设置 Content-Type → 写 JSON 字符串。
     *
     * ★ 为什么需要用 ObjectMapper 序列化？
     *   因为要保证输出格式和正常响应完全一致（同样的字段、同样的时间格式）。
     *   用容器里的那个 ObjectMapper（本类注入了）就能保证一致。
     *
     * ★ 为什么方法签名写 throws IOException？
     *   因为 getWriter().write() 可能抛 IOException（客户端断开连接等）。
     *   这个异常会被 Tomcat 记录，不需要特别处理 ——
     *   反正响应也发不出去了。
     *
     * @param res 响应对象
     * @param ec  要返回的错误码（决定状态码和业务码）
     */
    private void writeError(HttpServletResponse res, ErrorCode ec) throws IOException {
        /*
         * 【设置 HTTP 状态码】
         * 401 或 403，来自 ErrorCode 里定义的值
         */
        res.setStatus(ec.getHttpStatus());

        /*
         * 【设置 Content-Type】
         *
         * ★ 这一行必须写，否则浏览器不知道这是 JSON，
         *   前端 res.json() 会失败。
         *
         * ★ 为什么加 charset=UTF-8？
         *   因为响应体里有中文（"请先登录"）。
         *   不指定字符集时，某些浏览器会用 ISO-8859-1 解析，中文变乱码。
         */
        res.setContentType("application/json;charset=UTF-8");

        /*
         * 【写响应体】
         *
         * ApiResponse.fail(ec, null) 会构造：
         *     {code:10001, message:"请先登录", data:null, traceId:"...", timestamp:...}
         *
         * ★ traceId 能取到吗？
         *   能 —— 因为 TraceIdFilter 排在最前面，此时 MDC 里已经有值了。
         *   所以前端收到的 401 响应里也带 traceId，排查一样方便。
         *
         * ★ 为什么 data 传 null？
         *   认证失败没有额外数据要给前端。
         *   前端只需要知道 code 和 message。
         */
        res.getWriter().write(objectMapper.writeValueAsString(ApiResponse.fail(ec, null)));
    }

    /**
     * ═══════════════════════════════════════════════════════════════
     *  【跨域配置】
     * ═══════════════════════════════════════════════════════════════
     *
     * ★ 逐项解释为什么要这么配：
     *
     * setAllowedOriginPatterns(List.of("http://localhost:*", "http://127.0.0.1:*"))
     *      允许哪些来源访问。
     *      ★ 为什么用 Pattern 而不是 setAllowedOrigins？
     *        setAllowedOrigins 不支持通配符，只能写完整域名（http://localhost:5173）。
     *        用 Pattern 可以匹配任意端口，本地开发时前端换端口不用改配置。
     *      ★ 生产环境应该写具体域名（https://yourdomain.com），
     *        绝对不能用 "*"（那样任何网站都能调你的接口）。
     *
     * setAllowedMethods(...)
     *      允许哪些 HTTP 方法。
     *      ★ 为什么没有 PATCH？因为项目里不用 PATCH。
     *        用不到的方法不开放，减少攻击面。
     *
     * setAllowedHeaders(List.of("*"))
     *      允许请求带哪些头。
     *      ★ 用 "*" 是因为要允许 Authorization（自定义头）。
     *        精确写法是 List.of("Authorization", "Content-Type", "X-Trace-Id")，
     *        但用 "*" 更省事，且风险不大（头是客户端主动设的，骗不了服务端）。
     *
     * setAllowCredentials(false)
     *      ★ 关键：不使用 Cookie，所以设 false。
     *      如果设成 true，浏览器就允许跨域请求带 Cookie，
     *      那就要重新启用 CSRF 防护了。
     *      而且 allowCredentials=true 时，allowedOrigins 不能用通配符 ——
     *      两条规则冲突，这也是我们选 false 的原因之一。
     *
     * ★ 最后返回一个 CorsConfigurationSource：
     *   这就是 Spring Security 需要的类型。registerCorsConfiguration("/**", cfg)
     *   表示"所有路径都用这套配置"。
     */
    private CorsConfigurationSource corsSource() {
        CorsConfiguration cfg = new CorsConfiguration();
        cfg.setAllowedOriginPatterns(List.of("http://localhost:*", "http://127.0.0.1:*"));
        cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
        cfg.setAllowedHeaders(List.of("*"));
        cfg.setAllowCredentials(false);

        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", cfg);
        return source;
    }

    /*
     * ═══════════════════════════════════════════════════════════════
     *  【★ 这个类的设计要点（面试可讲）】
     *
     *  1. 无状态会话（STATELESS）：不建 Session，认证信息只活在请求内
     *  2. 默认拒绝（anyRequest().authenticated()）：新接口默认受保护
     *  3. 公开接口列清楚，每个都能说出"为什么必须公开"
     *  4. 自定义 401/403 响应体，让前端能统一处理
     *  5. JWT 过滤器插在 UsernamePasswordAuthenticationFilter 之前
     *  6. CSRF 可以关（无 Cookie），跨域配在 Security 里（执行顺序更早）
     *
     *  ★ 如果被问"你的接口安全怎么保证"，就按这 6 条答。
     * ═══════════════════════════════════════════════════════════════
     */
}
```

### ⑧ ★ 真实踩到的坑：schema 校验失败

这一步值得单独讲，因为它是本项目唯一一个"启动就炸"的真实 bug。

**现象**：写完步骤 2 的 `AppUser` 后启动，直接失败：

```
Schema-validation: wrong column type encountered in column [years_of_experience]
in table [app_user];
found [tinyint unsigned (Types#TINYINT)], but expecting [integer (Types#INTEGER)]
```

**原因**：建表脚本里 `years_of_experience` 是 `TINYINT UNSIGNED`，
而 Java 实体里写的是 `Integer`。

Hibernate 的类型映射关系：

| MySQL 类型 | 对应的 Java 类型 |
|---|---|
| `TINYINT` / `TINYINT UNSIGNED` | `Byte` / `Short` |
| `SMALLINT` | `Short` |
| `INT` | `Integer` |
| `BIGINT` | `Long` |

`Integer` 期待的是 `INT`，所以不匹配。

**解决**：新增 `V2__fix_years_of_experience.sql`：

```sql
ALTER TABLE `app_user`
  MODIFY COLUMN `years_of_experience` INT NOT NULL DEFAULT 0 COMMENT '经验年限（年，0-50）';

ALTER TABLE `post`
  MODIFY COLUMN `years_of_experience` INT NOT NULL DEFAULT 0 COMMENT '经验年限（冗余，用于筛选）';
```

**为什么改成 INT，而不是把 Java 改成 Short？**
`TINYINT UNSIGNED` 范围 0-255，确实对应 `Short`。但用 `Short` 意味着：
```java
user.setYearsOfExperience((short) 3);   // 到处要强转，很别扭
```
而 `INT` 占 4 字节 vs `TINYINT` 1 字节 —— 一张用户表几千行，多占几十 KB，
**完全没意义**。可读性优先。

**为什么新开 V2 而不改 V1？**
Flyway 的规矩：**已执行的脚本不能再改**。改了会 checksum 不匹配，
其他环境（比如服务器）也会处于不同状态。正确做法永远是追加新脚本。

> ★ 这个坑完美说明了 `ddl-auto=validate` 的价值：
> **花 30 秒修一个启动错误，比上线后花 3 小时查"为什么这个字段读出来是 null"划算得多。**

### ⑩ 登出后用旧 refresh（期望失败）

```bash
curl -s -X POST http://localhost:8080/api/auth/refresh   -H "Content-Type: application/json" -d "{"refreshToken":"$REFRESH"}"
```

**实际输出**：

```json
{"code":20003,"message":"登录状态失效，请重新登录","traceId":"5e500872eec541f4",...}
```

★ 为什么？
登出时 `TokenService.revokeRefresh` 把它从白名单删掉了。
虽然它的签名仍然有效、7 天有效期也没过，但**白名单里查不到** → 拒绝。

### ⑪ refresh 轮换

```bash
# 重新登录拿一对新 token
curl -s -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json"   -d '{"username":"alice","password":"Passw0rd1"}' -o login2.json
R1=$(python -c "import json;print(json.load(open('login2.json'))['data']['refreshToken'])")

# 用 R1 刷新
curl -s -X POST http://localhost:8080/api/auth/refresh   -H "Content-Type: application/json" -d "{"refreshToken":"$R1"}"

# 再用同一个 R1 刷新一次
curl -s -X POST http://localhost:8080/api/auth/refresh   -H "Content-Type: application/json" -d "{"refreshToken":"$R1"}"
```

**实际输出**：

```
第一次刷新：code=0, expiresIn=7200, 返回的 refreshToken 与旧的不同 ✓
第二次刷新：{"code":20003,"message":"登录状态失效，请重新登录"}
```

★ 这就是"轮换"：**旧的一次性用完就作废**。
即使用户的 refresh token 被偷，攻击者也只能用一次 ——
而且真用户下次刷新会失败，这是个明确的"被盗"信号。

- **TTL 604800** —— 和数据生命周期对齐，到期自动回收，不需要清理任务

## 3.6 报错怎么办

| 现象 | 原因 | 解决 |
|---|---|---|
| 注册返回 500 且日志 `No qualifying bean of type PasswordEncoder` | `SecurityConfig` 里没定义 `@Bean PasswordEncoder` | 补上 |
| 所有请求都 401 | 过滤器抛异常被吞 / `addFilterBefore` 没加 | 检查 `SecurityConfig` 最后一行 |
| 登录成功但访问接口 401 | token 里 `type` 不是 `access` / 被黑名单 | 用 jwt.io 解一下 payload 看 `type` |
| `JwtProperties` 注入失败 | 启动类没加 `@ConfigurationPropertiesScan` | 补上 |
| `WeakKeyException: The signing key's size is ... bits` | `secret` 不足 32 字节 | 换成长一点的默认值 |
| CORS 报错（浏览器） | 步骤 4 才用得到，但可以先确认 `corsSource` 生效 | 用 curl 测（curl 不校验 CORS） |
| Redis 连不上导致登录失败 | Redis 没启动 | 双击 `start-redis.bat` |
| `@CurrentUserId` 拿到 null | `WebConfig` 没注册 resolver | 检查 `addArgumentResolvers` |
| 改密码后老 token 还能用 | 还没实现 `revokeAllRefresh` 的调用 | 步骤 4 的改密码接口里调 |
| `Schema-validation: wrong column type ... [years_of_experience]` | 建表是 `TINYINT UNSIGNED`，实体是 `Integer` | 已用 `V2__fix_years_of_experience.sql` 修好；换机器时确认 V2 也执行了 |
| 401 响应体是空的（前端解析失败） | `SecurityConfig` 少了 `authenticationEntryPoint` | 补上，让它也返回 `ApiResponse` |
| `@ConfigurationPropertiesScan` 没加 | `JwtProperties` 不会被创建 | 启动类补注解 |
| 登出后 refresh 还能用 | 只处理了 access，没删白名单 | `AuthService.logout` 里两个 token 都要处理 |

## 3.7 自测题

1. **JWT 无状态，为什么还需要 Redis？** → 为了"可撤销"：登出/改密后旧 token 必须立刻失效，靠 jti 黑名单实现，TTL 对齐剩余有效期。
2. **为什么 refresh 要轮换？** → 泄露后只能用一次；且真实用户下次刷新失败可作为异常信号。
3. **登录失败为什么统一错误码？** → 防用户名枚举。
4. **为什么角色不放进 JWT？** → 签发后不可改，撤权会延迟到 token 过期；正确做法是每次请求从服务端加载权限。
5. **过滤器解析失败为什么不直接返回 401？** → 过滤器只负责识别身份，是否要求登录由 Security 规则决定，这样公开接口带坏 token 也能访问。
6. **BCrypt 为什么比 MD5 安全？** → 慢哈希 + 内置 salt + 可调 cost，让离线爆破的成本高几个数量级。
