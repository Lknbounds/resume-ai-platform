# 01B · 分层架构对照：Controller / Service / Mapper 都去哪了？

> 你学的传统写法是 **Controller → Service → Mapper（DAO）**，而本项目里你看到的是：
> **Controller → Service → Repository + Entity + DTO**，还多了一堆 `calculator` / `ai` / `privacy` 包。
>
> 这篇把两套体系**一一对上号**，然后回答最重要的一个问题：**数据在每一层之间是怎么流动的、下一步去哪。**

---

## 一、先看两套分层并排对比

### 传统写法（你熟悉的那套）

```
Controller  →  Service  →  Mapper  →  MySQL
（收请求）     （业务）     （SQL）      （数据）
```

- **Controller**：接参数，调 Service，返回结果
- **Service**：业务逻辑
- **Mapper**：接口 + XML（或注解）里手写 SQL
- **Entity/PO**：和表一一对应的类

### 本项目

```
         ┌──────────────────────────────────────────────┐
         │  Controller    接请求、校验、返回统一响应      │
         └───────────────────┬──────────────────────────┘
                             ↓
         ┌──────────────────────────────────────────────┐
         │  Service       业务规则、事务、归属校验        │
         │   ├─ 普通 Service        （CRUD 编排）        │
         │   ├─ Domain Service      （calculator/ai/privacy，纯计算）
         │   └─ Async Service       （异步任务，步骤 8/15）│
         └───────────────────┬──────────────────────────┘
                             ↓
         ┌──────────────────────────────────────────────┐
         │  Repository    数据访问（替代 Mapper）         │
         └───────────────────┬──────────────────────────┘
                             ↓
         ┌──────────────────────────────────────────────┐
         │  Entity        映射表结构的类                  │
         └───────────────────┬──────────────────────────┘
                             ↓
                        MySQL 8
```

**一句话总结差异：**

| 传统 | 本项目 | 差别 |
|---|---|---|
| Mapper + XML | **Repository 接口** | 不写 SQL，靠**方法名**自动生成 |
| Entity/PO | **Entity** | 一样，但不用写任何 getter/setter（Lombok） |
| Service | **Service** | 一样，但拆出了三种类型 |
| Controller | **Controller** | 一样，但禁止写业务逻辑 |
| （通常没有） | **DTO / VO** | 专门用于"对外传输"的类，不把 Entity 直接给前端 |

## 二、逐层对照：每一层在哪、干什么、禁止什么

### ① Controller 层 —— 对应你的 `xxxController`

**位置**：`com.jianli.xxx.controller`
**文件示例**：`user/controller/AuthController.java`

```java
@RestController
@RequestMapping("/api/auth")
public class AuthController {

    private final AuthService authService;

    @PostMapping("/login")
    public ApiResponse<TokenResponse> login(@RequestBody @Valid LoginRequest req) {
        return ApiResponse.ok(authService.login(req));
    }
}
```

| 它做 | 它不做 |
|---|---|
| 接参数（`@RequestBody` / `@PathVariable` / `@RequestParam`） | ❌ 写业务逻辑（if/else 判断、组装数据） |
| 触发参数校验（`@Valid`） | ❌ 直接注入 Repository |
| 调 Service 一个方法 | ❌ 直接返回 Entity |
| 包成 `ApiResponse` 返回 | ❌ 写 try/catch（`GlobalExceptionHandler` 管） |

**为什么禁止直接注入 Repository？**
因为一旦允许，就会有人写 `controller → repository` 跳过 Service，业务规则（比如"只能删自己的简历"）就散落在 Controller 里。
我们要求：**所有跨表的业务规则都在 Service**。Controller 只是"门卫 + 传话筒"。

---

### ② Service 层 —— 对应你的 `xxxService`

**位置**：`com.jianli.xxx.service`
**本项目拆成三种，这是和传统写法最大的不同：**

#### 2.1 普通 Service（业务编排）

**示例**：`resume/service/ResumeService.java`

```java
@Service
public class ResumeService {

    private final ResumeRepository resumeRepository;
    private final ResumeVersionRepository versionRepository;
    private final ResumeTextNormalizer normalizer;

    @Transactional
    public ResumeDetailVO create(Long userId, CreateResumeRequest req) {
        String content = normalizeChecked(req.content());     // ① 校验 + 归一化
        Resume resume = saveResume(userId, req.title());      // ② 落库
        ResumeVersion v1 = saveVersion(resume, content);      // ③ 落库
        resume.setCurrentVersionId(v1.getId());               // ④ 回写指针
        return detailOf(resume);                              // ⑤ 组装返回
    }
}
```

**它做**：
- 业务规则（"内容少于 50 字要拒绝"）
- 事务边界（`@Transactional` 写在这一层，而不是 Controller）
- 归属校验（"这份简历是不是你的"）
- 编排多个 Repository（一次操作可能涉及多张表）

**它不做的**：
- ❌ 直接处理 HTTP（拿不到 `HttpServletRequest`）
- ❌ 返回 Entity 给 Controller（必须转成 VO）

---

#### 2.2 Domain Service（纯计算 / 领域逻辑）★ 传统写法里没有这类

**位置**：`analysis/calculator/`、`privacy/`、`ai/parser/`

**示例**：`analysis/calculator/ScoreCalculator.java`

```java
@Service
public class ScoreCalculator {

    public ScoreResult calculate(ScoringContext ctx) {
        List<SkillMatch> matches = skillMatcher.match(...);
        DimensionScore d1 = skillCoverage(matches);
        DimensionScore d2 = experienceMatch(ctx);
        ...
    }
}
```

**为什么单独拆出来？**
因为这个类里**没有一行数据库操作、没有一行 HTTP 处理**。它是个纯函数：输入两个解析结果，输出一个分数。

好处：
1. **能单测** —— 不需要启动 Spring、不需要连数据库，`new ScoreCalculator()` 就能测
2. **能复现** —— 同样的输入永远同样的输出，这是"分数可解释"的基础
3. **能复用** —— 步骤 10 的"预计提升"、步骤 9.5 的"板块得分"都会调它

**这就是"领域服务"和"应用服务"的区别：**
- 应用服务（普通 Service）：管流程、管事务、管 IO
- 领域服务（Domain Service）：管规则、管计算，不碰 IO

---

#### 2.3 Async Service（异步任务）★ 传统写法里也没有

**位置**：`analysis/service/AnalysisAsyncService.java`

```java
@Service
public class AnalysisAsyncService {

    @Async("analysisExecutor")
    public void run(Long reportId) {
        // 解析 → 评分 → 建议 → 落库
    }
}
```

**为什么要单独一个类？**

因为 `@Async` 有个致命陷阱：**在同一个类里自己调用自己，异步不生效**（不走 Spring 代理）。

```java
// ❌ 错误写法：这样 run() 是同步执行的
@Service
public class AnalysisService {
    public void create() {
        this.run();          // ← 自己调自己，@Async 失效
    }
    @Async
    public void run() { ... }
}

// ✅ 正确写法：拆成两个类
@Service
public class AnalysisService {
    private final AnalysisAsyncService asyncService;
    public void create() {
        asyncService.run();  // ← 走代理，异步生效
    }
}
```

### ③ Repository 层 —— **替代你的 Mapper**，这是你最关心的

**位置**：`com.jianli.xxx.repository`
**文件示例**：`user/repository/UserRepository.java`

```java
public interface UserRepository extends JpaRepository<AppUser, Long> {

    Optional<AppUser> findByUsername(String username);

    boolean existsByUsername(String username);
}
```

**注意：这里没有实现类，没有 SQL，没有 XML。**

### 那 SQL 从哪来？

这是 Spring Data JPA 的核心机制 —— **方法名即查询**。

Spring 启动时扫描到 `UserRepository`，看到：
1. 它继承了 `JpaRepository`
2. 有一个方法叫 `findByUsername`
3. 泛型参数 `AppUser` 里有字段 `username`

于是它在内存里**动态生成一个实现类**，等价于：

```sql
SELECT * FROM app_user WHERE username = ?
```

### 方法名 → SQL 的对照表（项目里会用到的全部）

| 方法名写法 | 生成的 SQL | 用在哪个模块 |
|---|---|---|
| `findById(Long id)` | `WHERE id = ?` | 全部 |
| `findByUsername(String u)` | `WHERE username = ?` | 用户 |
| `existsByUsername(String u)` | `SELECT 1 ... WHERE username = ? LIMIT 1` | 注册判重 |
| `findByIdAndUserId(Long id, Long uid)` | `WHERE id = ? AND user_id = ?` | 简历/JD/报告的归属校验 |
| `findByUserIdOrderByUpdatedAtDesc(...)` | `WHERE user_id = ? ORDER BY updated_at DESC` | 列表 |
| `findFirstByResumeIdAndContentHash(...)` | `... LIMIT 1` | 版本去重 |
| `countByPostIdAndStatus(...)` | `SELECT COUNT(*) ...` | 评论计数 |
| `deleteByReportId(Long id)` | `DELETE ... WHERE report_id = ?` | 重新生成建议前清空 |

### 那复杂的 SQL 怎么办？

项目里确实有几个不好用方法名表达的，就用 `@Query` 手写 JPQL（注意不是原生 SQL）：

```java
@Query("select coalesce(max(v.versionNo), 0) from ResumeVersion v where v.resumeId = :resumeId")
int findMaxVersionNo(@Param("resumeId") Long resumeId);
```

这已经是 JPA 里最接近 Mapper 的写法了。

### 总结：Mapper 在本项目里的三个"化身"

| 你想要的能力 | 传统 Mapper | 本项目 |
|---|---|---|
| 简单 CRUD | `<select>` 标签 | **继承 JpaRepository 自动获得**（save/findById/delete） |
| 条件查询 | 手写 SQL | **方法名推导** |
| 复杂查询 | 手写 SQL | `@Query` 写 JPQL |
| 多表 JOIN | XML 里写 | **基本不用**（见下面第四节，实体之间不建关联） |

### ④ Entity 层 —— 对应你的 PO / DO

**位置**：`com.jianli.xxx.entity`
**文件示例**：`user/entity/AppUser.java`

```java
@Entity
@Table(name = "app_user")
public class AppUser {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "password_hash", nullable = false, length = 100)
    private String passwordHash;
}
```

**和传统 PO 的区别：**

| 项 | 传统 PO | 本项目 Entity |
|---|---|---|
| getter/setter | 手写或用 IDE 生成 | `@Getter @Setter` 一行搞定 |
| 和表的关系 | 靠 Mapper XML 里的 resultMap | **靠注解**（`@Table` / `@Column`），启动时自动校验 |
| 表结构变更 | 手动改 PO，运行时才发现不匹配 | `ddl-auto=validate`，**启动就报错** |

**★ 最重要的一条：Entity 绝不直接返回给前端。**

见下一节 DTO/VO。

---

### ⑤ DTO / VO 层 —— 传统写法里通常没有，但必须有

**位置**：`com.jianli.xxx.dto`

**两类，职责完全不同：**

| 类型 | 命名 | 方向 | 例子 |
|---|---|---|---|
| **DTO**（Data Transfer Object / Request） | `XxxRequest` | 前端 **→** 后端 | `LoginRequest`、`CreateResumeRequest` |
| **VO**（View Object / Response） | `XxxVO` | 后端 **→** 前端 | `UserVO`、`ResumeDetailVO` |

```java
// 前端传进来的
public record LoginRequest(@NotBlank String username, @NotBlank String password) {}

// 返回给前端的
public record UserVO(Long id, String username, String nickname,
                     String targetPosition, Integer yearsOfExperience) {
    public static UserVO of(AppUser u) {
        return new UserVO(u.getId(), u.getUsername(), u.getNickname(),
                u.getTargetPosition(), u.getYearsOfExperience());
    }
}
```

**为什么不直接用 Entity 当请求/响应？**

1. **安全**：`AppUser` 里有 `passwordHash`，直接返回等于把密码哈希泄露出去
2. **解耦**：表加了列，前端不用跟着改
3. **校验**：`@NotBlank` 这类注解放在 Entity 上会污染持久化层
4. **派生字段**：VO 可以有"计算出来的字段"（比如 `latestScore`），Entity 不行

> **这就是 `UserVO.of(AppUser u)` 这个方法存在的意义** —— 把 Entity "投影"成能对外暴露的形状。

## 三、数据在层之间怎么流动（**你最关心的那部分**）

### 场景 A：查询 —— `GET /api/resumes/31`

```
① 浏览器
   fetch('/api/resumes/31')
        ↓  HTTP 报文：GET /api/resumes/31
        ↓
② Tomcat → Filter 链 → DispatcherServlet → 路由到 ResumeController.detail()
        ↓
③ ResumeController
   @GetMapping("/{id}")
   public ApiResponse<ResumeDetailVO> detail(@CurrentUserId Long userId,
                                             @PathVariable Long id)
   ── 参数怎么来的：@PathVariable 从路径抠出 31，@CurrentUserId 从 token 抠出 userId
        ↓  调用 Service，传两个 Long
        ↓
④ ResumeService.detail(userId, resumeId)
   @Transactional(readOnly = true)
   public ResumeDetailVO detail(Long userId, Long resumeId) {
       Resume resume = resumeRepository.findByIdAndUserId(resumeId, userId)   ← 调 Repository
               .orElseThrow(() -> new BizException(ErrorCode.RESUME_NOT_FOUND));
       List<ResumeVersion> versions = versionRepository.findByResumeIdOrderByVersionNoDesc(resumeId);
       ...
       return new ResumeDetailVO(...);     ← ★ 组装成 VO 返回
   }
        ↓  调用 Repository，传 Long
        ↓
⑤ ResumeRepository.findByIdAndUserId(31, 7)
   ── 没有实现类！Spring 生成的 SQL：SELECT * FROM resume WHERE id=31 AND user_id=7
        ↓  JDBC 执行 SQL
        ↓
⑥ MySQL 返回结果集
        ↓  JPA 把行映射成 AppUser/Resume 对象
        ↓
⑦ Repository 返回 Optional<Resume>（★ Entity）
        ↓
⑧ Service 拿到 Entity，组装成 VO（★ 这一步是必须的）
        ↓
⑨ Controller 拿到 VO，包成 ApiResponse
        ↓
⑩ Jackson 把 ApiResponse 序列化成 JSON
        ↓
⑪ 浏览器拿到：
   {"code":0, "data":{"id":31, "title":"Java 后端简历", "versions":[...]}, ...}
```

### 数据在各层传递的类型（**记住这张表**）

| 层次 | 传进去 | 传出来 |
|---|---|---|
| 浏览器 → Controller | JSON 文本 | — |
| **Controller** | `Long userId`, `Long id`（基本类型） | `ApiResponse<ResumeDetailVO>` |
| **Service** | `Long`, `Request` 对象 | **`VO`**（不是 Entity！） |
| **Repository** | `Long`, `String` 等查询条件 | **`Entity`**（或 `Optional<Entity>`、`List<Entity>`） |
| **Entity ↔ 数据库** | — | 行 ↔ 对象映射 |

**★ 转换发生在哪两处（必须记住）：**

```
Entity ──(Service 里手动转)──> VO        ← 向后端返回值转
JSON   ──(Jackson 自动转)──>  Request    ← 向前端提交值转
```

> **第二条是 Spring 自动的**（`@RequestBody`）。
> **第一条是你手写的**（`UserVO.of(user)`），因为"哪些字段能对外暴露"是业务决策，不能自动决定。

### 场景 B：写入 —— `POST /api/resumes`

```
① 浏览器
   http.post('/api/resumes', { title: "Java 简历", content: "..." })
        ↓  Content-Type: application/json + JSON 请求体
        ↓
② Controller
   @PostMapping
   public ResponseEntity<ApiResponse<ResumeDetailVO>> create(
           @CurrentUserId Long userId,
           @RequestBody @Valid CreateResumeRequest req)          ← ★ JSON → 对象
   ── 此时 req 已经是 Java 对象，@Valid 已经校验过
        ↓
③ Service
   @Transactional                        ← ★ 事务从这里开始
   public ResumeDetailVO create(Long userId, CreateResumeRequest req) {
       String content = normalizeChecked(req.content());      // 业务校验
       Resume resume = new Resume();                          // ★ 造 Entity
       resume.setUserId(userId);
       resumeRepository.save(resume);                          // ← INSERT
       ...
       return detailOf(resume);                                // ★ Entity → VO
   }
        ↓
④ Repository.save(entity)
   ── 内部：把对象字段拼成 INSERT INTO resume (...) VALUES (...)
        ↓
⑤ MySQL 插入，返回自增 id
        ↓  JPA 把 id 回填到 entity.getId()
        ↓
⑥ 一路返回 VO → ApiResponse → JSON
        ↓
⑦ 浏览器拿到 201 + {"code":0,"data":{"id":31,...}}
        ↓
⑧ 事务在任何一层抛 RuntimeException 时自动回滚
```

**几个关键点：**

1. **`@Transactional` 写在 Service，不写在 Controller** —— Controller 不该关心事务
2. **Entity 是 Service 里 `new` 出来的**，不是 Repository 里 new 的
3. **返回时又转成 VO** —— 入站出站都要转换

## 四、为什么实体之间不写 `@ManyToOne` 关联？

传统 JPA 教程都会教你：

```java
@Entity
public class ResumeVersion {
    @ManyToOne
    @JoinColumn(name = "resume_id")
    private Resume resume;        // ← 关联对象
}
```

**本项目刻意不这样做**，只存 id：

```java
@Entity
public class ResumeVersion {
    @Column(name = "resume_id")
    private Long resumeId;        // ← 只有 id
}
```

### 三个理由

**① 避免 `LazyInitializationException`（最常见的坑）**

`@ManyToOne(fetch = LAZY)` 的意思是"用到时才去查数据库"。
但本项目配了 `open-in-view: false`（生产环境的正确做法），意味着**事务一结束，Session 就关了**。

```java
// 事务里
Resume resume = repo.findById(1);
// 事务结束，Session 关闭

// 事务外
resume.getVersions().size();   // ❌ LazyInitializationException: could not initialize proxy
```

用 `Long resumeId` 就没有这个问题 —— id 是普通字段，永远可用。

**② 显式控制查询，避免隐式 N+1**

如果用关联对象写 `resume.getVersions()`，在循环里就会变成：

```java
for (Resume r : resumes) {
    r.getVersions().size();     // ← 每循环一次发一条 SQL，10 条简历就是 10 次查询
}
```

存 id 之后，必须在 Service 里显式决定"要不要多查一次"，反而更可控。

**③ 外键的完整性由数据库保证**

有人会担心"只存 id 怎么保证不出现脏数据"。答案是：**数据库层面建外键**。

```sql
CONSTRAINT `fk_version_resume` FOREIGN KEY (`resume_id`)
    REFERENCES `resume` (`id`) ON DELETE CASCADE
```

删简历时版本自动级联删除 —— 这个保证比 JPA 的关联更可靠。

> **一句话**：用 `Long` + 数据库外键，换 ORM 的简洁与可控。

- **`common` / `config` / `security` / `infra` 是横切关注点**，不属于任何业务模块

## 六、常见疑问

**Q：为什么不用 MyBatis？Mapper 不是更直观吗？**

三个理由：
1. 这个项目的 SQL 都很简单（单表条件查询为主），方法名推导完全够用，省掉写 XML 的功夫
2. `ddl-auto=validate` 能保证实体和表结构永远一致，MyBatis 不行
3. 面试时"为什么选 JPA"比"为什么选 MyBatis"更容易讲出深度（实体关系、事务、脏检查）

**Q：方法名推导真的够用吗？复杂的怎么办？**

看这个项目里最难的一个查询：

```java
Optional<AnalysisReport> findFirstByCacheKeyAndStatusInOrderByIdDesc(
        String cacheKey, Collection<String> statuses);
```

生成的 SQL：
```sql
SELECT * FROM analysis_report
WHERE cache_key = ? AND status IN (?, ?)
ORDER BY id DESC LIMIT 1
```

够用。真的不够时用 `@Query` 写 JPQL，和 Mapper 里的 `<select>` 本质一样。

**Q：Service 会不会越来越大？**

会。所以本项目按"职责"拆：
- `ResumeService` 只管简历和版本
- `AnalysisService` 只管创建和查询报告（同步部分）
- `AnalysisAsyncService` 只管异步执行
- `SuggestionService` 只管生成建议
- `RewriteService` 只管改写

**一个 Service 超过 300 行就该考虑拆了。**

**Q：Domain Service（比如 `ScoreCalculator`）为什么不是静态工具类？**

因为它需要注入配置（`ScoringProperties` 权重、`SkillDictionary` 词典）。
如果是纯静态方法，就得把配置传进去，调用处会很难看。

但它**不需要任何 IO**，所以依然可以单独 `new` 出来测（把依赖 mock 掉）。

**Q：DTO 和 VO 能合并吗？**

技术上能（都叫 Request/Response），但分开更清楚：
- DTO 有校验注解，是"输入契约"
- VO 有 `of()` 工厂方法，是"输出投影"
混在一起时，你会不确定"这个注解是给输入用的还是给输出用的"。
