# 步骤 09.5：对齐 ResumeIQ 的四个分析增强（3 小时）

> 这几个是同类产品的"标配"，实现成本低但**分析页看起来专业很多**。放在步骤 9 之后、步骤 10 之前做（纯规则，不依赖 AI）。做完之后 AI 打开时会自动让这些结果更准。
>
> 参考对象：`getresumeiq.com/ats-resume-checker` 的返回结构 `{overallScore, scoreBreakdown, keywordDensity, feedback[]}`。

---

## 9.5.1 四项增强对照

| ResumeIQ | 我们加什么 | 需要 AI 吗 |
|---|---|---|
| `keywordDensity` | **关键词密度表**：每个 JD 关键词在简历中出现次数 + 目标区间提示 | ❌ |
| "missing keywords commonly required for your target roles" | **岗位常见关键词**：除 JD 抽出的词外，按岗位类别补一份"行业标配词" | ❌ |
| 按板块给建议（Summary / Skills / Experience / Projects / Education） | **分板块得分**：5 个板块各一个 0-100 分 | ❌ |
| Skills gap + course recommendations | **技能差距 + 学习资源**：缺失技能 → 静态推荐资源 | ❌ |

## 9.5.2 关键词密度

### 为什么要看密度？

只判断"有没有出现"是不够的：
- **出现 0 次** → 缺失；
- **出现 1 次** → 勉强通过关键词筛选，但招聘方扫一眼看不出来重点；
- **出现 2-4 次** → 理想（技能栏 + 项目里各提一次）；
- **出现 8 次以上** → 堆砌，会被认为"为了过 ATS 硬塞"，HR 观感差，AI 检测也可能判定为 keyword stuffing。

所以输出三态：`MISSING / LOW（1 次）/ OK（2-4 次）/ OVER（≥5 次）`。

### 实现

```java
package com.jianli.analysis.calculator;

public record KeywordDensity(
        String keyword,
        String importance,
        int count,
        String level          // MISSING / LOW / OK / OVER
) {}
```

```java
@Component
@RequiredArgsConstructor
public class KeywordDensityAnalyzer {

    private static final int OK_MIN = 2;
    private static final int OVER = 5;

    private final SkillDictionary dictionary;

    public List<KeywordDensity> analyze(JdParsed jd, String resumeText) {
        List<KeywordDensity> out = new ArrayList<>();
        for (SkillItem s : jd.requiredSkills()) {
            int count = countOccurrences(resumeText, s.name());
            out.add(new KeywordDensity(s.name(), s.importance(), count, level(count)));
        }
        out.sort(Comparator
                .comparingInt((KeywordDensity d) -> importanceRank(d.importance())).reversed()
                .thenComparingInt(KeywordDensity::count));
        return out;
    }

    /** 用词典别名一起数，避免 "k8s" 不算 Kubernetes */
    private int countOccurrences(String text, String canonical) {
        if (text == null) return 0;
        String lower = text.toLowerCase(Locale.ROOT);
        int total = 0;
        for (String alias : dictionary.aliasesOf(canonical)) {
            int from = 0;
            while (true) {
                int i = lower.indexOf(alias.toLowerCase(Locale.ROOT), from);
                if (i < 0) break;
                if (isBoundary(lower, i, alias.length())) total++;
                from = i + alias.length();
            }
        }
        return total;
    }

    private String level(int count) {
        if (count == 0) return "MISSING";
        if (count == 1) return "LOW";
        if (count >= OVER) return "OVER";
        return "OK";
    }
}
```

存进 `analysis_report.keyword_json` 的新字段：

```json
{
  "hits": [...], "partials": [...], "missing": [...],
  "density": [
    { "keyword": "Java", "importance": "HIGH", "count": 3, "level": "OK" },
    { "keyword": "Redis", "importance": "HIGH", "count": 0, "level": "MISSING" },
    { "keyword": "MySQL", "importance": "HIGH", "count": 6, "level": "OVER" }
  ]
}
```

**前端展示**：一张小表，`OVER` 用橙色 + 提示"出现 6 次，可能被视为堆砌，建议合并表述"。

## 9.5.3 岗位常见关键词（超越 JD 本身）

### 为什么需要？

用户常常只粘了 JD 的"职责"部分，漏了"要求"部分；或者 JD 写得很简略。这时只按 JD 关键词算，覆盖率会虚高（"我全命中了"），但实际投递仍会被筛。
补一份**按岗位类别的行业标配词**：即使 JD 没写，这些词也是这类岗位的常见要求。

### 数据文件

`src/main/resources/dict/position-keywords.json`：

```json
{
  "Java 后端": {
    "aliases": ["java", "后端", "服务端"],
    "common": ["Spring Boot", "MySQL", "Redis", "Git", "Linux", "RESTful", "单元测试", "MQ"],
    "differentiator": ["高并发", "分布式事务", "JVM调优", "微服务"]
  },
  "前端": {
    "aliases": ["前端", "web", "vue", "react"],
    "common": ["JavaScript", "TypeScript", "Git", "CSS", "HTTP", "构建工具"],
    "differentiator": ["性能优化", "工程化", "SSR"]
  },
  "测试": {
    "aliases": ["测试", "qa"],
    "common": ["单元测试", "接口测试", "SQL", "Linux"],
    "differentiator": ["自动化测试", "性能测试"]
  }
}
```

### 使用方式

1. 根据 JD 的 `jobTitle` 匹配到"岗位类别"（关键词命中数最多者）；
2. `common` 里**简历未命中**的词 → 归入"行业常见但简历缺失"，标 `source=POSITION`；
3. `differentiator` 里的词**只做提示**，不计入技能覆盖率（避免过度惩罚）。

```json
"keywordAnalysis": {
  "hits": [...],
  "partials": [...],
  "missing": [
    { "name": "Redis", "importance": "HIGH", "source": "JD" },
    { "name": "RESTful", "importance": "MEDIUM", "source": "POSITION" }
  ]
}
```

**这一点要和 ResumeIQ 一致，但要讲清边界**：行业词只是"提示"，**不参与 ATS 总分计算**，否则等于用一个通用标准去惩罚所有简历。总分仍然只基于 JD。

## 9.5.4 分板块得分

ResumeIQ 的 breakdown 是按简历板块给的。我们保留 6 个"评分维度"（更可解释），**额外**给 5 个"板块得分"（更直观）。

```json
"sectionScores": [
  { "section": "BASIC_INFO", "score": 90, "weight": 0, "note": "联系方式完整" },
  { "section": "SKILLS",     "score": 70, "note": "技能清单覆盖 5/7 项 JD 要求" },
  { "section": "EXPERIENCE", "score": 65, "note": "4 段经历中仅 1 段有量化结果" },
  { "section": "PROJECT",    "score": 80, "note": "2 个项目技术栈与 JD 重合度较高" },
  { "section": "EDUCATION",  "score": 100, "note": "本科满足要求" }
]
```

### 每个板块怎么打分（纯规则）

| 板块 | 计算方式 |
|---|---|
| `BASIC_INFO` | 有标题 +20；有目标岗位 +20；有工作年限/教育 +20；非空行 ≥ 3 +20；总篇幅合理（<300 字）+20 |
| `SKILLS` | `skillCoverage` 维度的分数（复用） |
| `EXPERIENCE` | 经历数量 ≥ 2 +20；每段有起止时间 +20；量化 bullet 占比 ≥ 30% +30；bullet 平均长度 ≥ 15 字 +30 |
| `PROJECT` | `projectRelevance` 维度分数（复用） |
| `EDUCATION` | `educationMatch` 维度分数（复用）；未识别到教育板块直接 0 |

> **为什么不把 sectionScores 计入总分**：它们和 6 个维度高度相关，同时计入会**重复计权**。它们只是"看板"——帮用户定位"哪个板块最该改"。

```json
"skillGaps": [
  { "skill": "Redis", "importance": "HIGH",
    "why": "JD 明确要求，且是 Java 后端高频考点",
    "resources": [
      { "title": "Redis 官方文档", "url": "https://redis.io/docs/latest/" },
      { "title": "Redis 设计与实现（书）", "url": null }
    ] }
]
```

映射表 `src/main/resources/dict/skill-resources.json`：

```json
{
  "Redis": [{ "title": "Redis 官方文档", "url": "https://redis.io/docs/latest/" }],
  "Kafka": [{ "title": "Apache Kafka Documentation", "url": "https://kafka.apache.org/documentation/" }],
  "Docker": [{ "title": "Docker 官方入门", "url": "https://docs.docker.com/get-started/" }],
  "Kubernetes": [{ "title": "Kubernetes 官方文档", "url": "https://kubernetes.io/zh-cn/docs/" }],
  "分布式事务": [{ "title": "Seata 官方文档", "url": "https://seata.apache.org/zh-cn/" }]
}
```

规则：
- 只为**缺失的 HIGH 技能**给资源（最多 5 条）；
- 没有映射的技能只显示名字，不硬凑链接（**不给不存在的链接**）；
- 这是**纯静态数据**，不调用任何外部服务，无失败风险。

## 9.5.6 落库与接口变更

`analysis_report` 不需要改表（都放进已有的 JSON 列）：

| 列 | 新增内容 |
|---|---|
| `keyword_json` | 增加 `density[]`；`missing[]` 增加 `source` 字段 |
| `dimension_json` | 不变（保持 6 维度） |
| `semantic_json` | 不变 |
| **新增** `section_score_json` | 需要一条 `V2__add_section_score.sql` |

```sql
-- V2__add_section_score.sql
ALTER TABLE `analysis_report`
  ADD COLUMN `section_score_json` JSON DEFAULT NULL COMMENT '分板块得分看板（不计入总分）' AFTER `dimension_json`;
```

`GET /api/analyses/{id}` 增加 4 个字段：

```json
{
  "keywordAnalysis": { "hits": [], "partials": [], "missing": [], "density": [] },
  "sectionScores": [ ... ],
  "skillGaps": [ ... ],
  "positionCategory": "Java 后端"
}
```

## 9.5.8 验证

| 检查点 | 期望 |
|---|---|
| 简历里写 3 次 Java | `density` 中 Java 的 `count=3, level=OK` |
| 简历里写 6 次 MySQL | `level=OVER` |
| 简历完全没提 Redis | `level=MISSING`，且 `skillGaps` 里有 Redis + 资源链接 |
| JD 是 Java 后端岗 | `positionCategory="Java 后端"`，`missing` 中出现 `source=POSITION` 的词 |
| `sectionScores` | 5 项，0-100，`SKILLS` 的分数 = `skillCoverage` 维度分 |
| 关掉 AI 再跑 | 以上四项**全部仍然有效**（纯规则） |

## 9.5.9 自测题

1. **为什么要看关键词密度而不是只看有无？** → 1 次容易被忽略，≥5 次会被视为堆砌，2-4 次最理想。
2. **行业常见词为什么不参与总分？** → 它不来自用户投的这份 JD，用来扣分会不公平；只作提示。
3. **分板块得分为什么不计入总分？** → 与 6 个维度高度相关，同时计权会重复计算；它只是定位问题的看板。
4. **学习资源为什么用静态映射？** → 零外部依赖、零失败风险；没有映射就不给链接，不编造。
